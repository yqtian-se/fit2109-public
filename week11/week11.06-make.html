Tool focus: Make

11.6 Make and Build Automation for Compiled Projects

For compiled languages such as C and C++, GNU Make is one of the classic ways to automate a build. (The Makefile below is for a C program built with gcc; -Wall -Wextra turn on extra compiler warnings and -O2 turns on optimisation.) A Makefile is a collection of rules explaining when and how to remake files, which suits projects where derived files (objects, executables, generated code) depend on sources and headers.

A complete Makefile

Makefile
CC = gcc
CFLAGS = -Wall -Wextra -O2

app: main.o math_utils.o
	$(CC) $(CFLAGS) -o app main.o math_utils.o

main.o: main.c math_utils.h
	$(CC) $(CFLAGS) -c main.c

math_utils.o: math_utils.c math_utils.h
	$(CC) $(CFLAGS) -c math_utils.c

.PHONY: clean
clean:
	rm -f app *.o

Several ideas appear together:

  • Variables (CC, CFLAGS) hold details once. To add a flag, or switch compiler, you change one line.
  • The first target in the file (app) is the default goal that a bare make builds.
  • app depends on object files, and each object depends on its source and header (the graph from 11.5).
  • .PHONY: clean marks clean as a task rather than a file, so its recipe runs even if a file called clean exists.

A typical session

$ make
gcc -Wall -Wextra -O2 -c main.c
gcc -Wall -Wextra -O2 -c math_utils.c
gcc -Wall -Wextra -O2 -o app main.o math_utils.o
$ ./app
$ make
make: 'app' is up to date.
$ make clean
rm -f app *.o
$ make
(rebuilds everything from source)

The first make builds the project. Running it again immediately should find nothing to do, because every target is up to date. make clean removes the build artifacts, and the next make rebuilds them from source. Make echoes each recipe line before it runs it, so the build log doubles as a record of what was run.

Make as a task runner

Make is useful well beyond compilation. Many projects use it for formatting, linting, testing, or packaging, and the concept does not change: whether the target is app, test, or clean, the Makefile is a structured description of project tasks. A test target that depends on the build looks like this:

Makefile (added target)
.PHONY: test
test: app
	./app

Because test lists app as a prerequisite, make test builds the program first if it is missing or out of date, then runs it. That "build before you test" guarantee is the kind of knowledge that otherwise lives in someone's head.

Common first-day errors missing separator: a recipe line is indented with spaces instead of a tab. No rule to make target 'x.o': a prerequisite names a file that does not exist and that Make has no rule to build, often because of a typo. make: 'app' is up to date (or Nothing to be done, for a target with no recipe): not an error — nothing needed rebuilding.

In short, make expresses build relationships and reusable project tasks in a form that lives in the repository and that anyone with make installed can run. The exact syntax matters, but the bigger lesson is the build model it conveys: declare relationships, and let the tool work out the steps.
