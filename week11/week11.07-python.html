Tool focus: Python

11.7 Python Automation Workflows

Python programs are usually run by an interpreter: python app.py executes the source directly, with no separate compile-and-link step like the one in C (11.4). Python projects therefore need little "building", but they still need automation. The repeated work is mostly about the environment: making sure the right Python packages are installed before the code is run and tested.

Background: virtual environments and packages

Week 6 (6.3) introduced virtual environments; here is the short version you need for this page.

  • Packages. Most Python projects use third-party libraries (packages) such as requests. They are installed with pip, Python's package installer.
  • The problem. If every project installs packages into the one system-wide Python, two projects that need different versions of the same package can break each other.
  • The fix. A virtual environment is a folder (by convention .venv) holding its own python and pip commands (the python is usually a link to the Python it was created from) and its own package directory. Packages installed there belong to this project only. venv, the module that creates it, is part of Python's standard library.
  • Activating. On macOS and Linux, source .venv/bin/activate mainly puts .venv/bin at the front of your PATH, so that typing python or pip runs the environment's copies. deactivate undoes it. Activation is a convenience: running .venv/bin/python directly uses the environment without activating it.

A project lists the packages it needs in a plain text file, conventionally called requirements.txt, one per line, often with an exact version:

requirements.txt
requests==2.32.3
python-dateutil==2.9.0

The starting workflow

$ python3 -m venv .venv
$ source .venv/bin/activate
$ python -m pip install -r requirements.txt
$ python app.py
CommandWhat it does
python3 -m venv .venvCreates the virtual environment in the folder .venv. (-m runs a Python module, here venv, as a program. Before activation, many systems only have the command python3, not python.)
source .venv/bin/activateActivates the environment in the current shell
python -m pip install -r requirements.txtInstalls every package listed in the file. python -m pip runs the pip that belongs to this python, so packages land in the environment you meant
python app.pyRuns the program with the environment's Python and packages

This is already a small automation workflow: create a local environment, install what the project needs, then run inside that environment instead of depending on whatever happens to be installed globally. The problem is that it lives in someone's memory or a README. The next step is to make it executable.

Making it executable: a bootstrap script

Suppose the repository looks like this:

.
├── app.py
├── requirements.txt
├── scripts/
│   └── bootstrap.sh
└── tests/
    ├── __init__.py
    └── test_app.py

Instead of describing the setup steps in a README, put them in scripts/bootstrap.sh. bootstrap.sh is not a Python feature: it is an ordinary shell script, and "bootstrap" is just a common name for "get a fresh clone ready to work". It is Python-specific only because of its contents; a Java project would have different contents, or none.

scripts/bootstrap.sh
#!/usr/bin/env bash
set -e
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest

The first line (the shebang line) asks for the script to be run by Bash (11.2). set -e tells the script to exit as soon as a command fails (with some exceptions, such as commands tested by if), so a failed install does not carry on to run tests against a half-built environment. The last line runs the tests with unittest, the testing framework built into Python's standard library.

Run the script from the top folder of the repository, because its paths (requirements.txt, .venv) are relative to where you run it:

$ bash scripts/bootstrap.sh
# or, after making it executable once:
$ chmod +x scripts/bootstrap.sh
$ ./scripts/bootstrap.sh

Now the setup and test workflow are executable. If another student clones the repository and runs the script, the same environment and checks are attempted in the same order.

How python -m unittest finds tests With no arguments, unittest searches from the current folder for files whose names start with test (such as test_app.py). It only looks inside a sub-folder like tests/ if that folder contains an __init__.py file, which may be empty. Without it, unittest prints NO TESTS RAN, and in Python 3.12 and later it exits with an error status, so set -e stops the script.
Activation inside a script does not last A script runs in its own child shell. The source .venv/bin/activate line activates the environment for the rest of the script only; when the script ends, your own terminal is not activated. To keep working in the environment afterwards, run source .venv/bin/activate yourself.
Idempotence check Running bootstrap.sh twice should be safe: venv reuses the existing .venv (installed packages are kept), and pip sees that the packages are already installed. Contrast this with a script that appended lines to a config file each time (11.5).

Make as a lightweight task runner

Python does not need Make, and Make knows nothing about Python, but Make's phony targets (11.4) can give any project short, memorable commands. Add this Makefile to the repository:

Makefile
.PHONY: setup test run

VENV_PYTHON := .venv/bin/python

setup:
	python3 -m venv .venv
	$(VENV_PYTHON) -m pip install -r requirements.txt

test:
	$(VENV_PYTHON) -m unittest discover

run:
	$(VENV_PYTHON) app.py

Teammates now type make setup once, and then make test or make run, instead of remembering a long command sequence. All three targets are phony because they name actions, not files.

LineMeaning
VENV_PYTHON := .venv/bin/pythonDefines a Make variable holding the path of the environment's Python, so it is written once (like CC = gcc in 11.6)
$(VENV_PYTHON) -m pip install …Make replaces $(VENV_PYTHON) with .venv/bin/python, so pip installs into the environment
$(VENV_PYTHON) -m unittest discoverRuns the tests with the environment's Python. discover asks for test discovery explicitly; plain python -m unittest does the same

The Makefile never activates the environment. It does not need to: activation mainly puts .venv/bin at the front of PATH, so calling .venv/bin/python by its path has the same effect, and is clearer.

Why activation does not work across recipe lines Make normally runs each recipe line in a separate shell. So this version looks reasonable but does not work:
Makefile (does not work)
setup:
	python3 -m venv .venv
	. .venv/bin/activate
	python -m pip install -r requirements.txt

The activation happens in the shell that runs the second line, and that shell exits before the third line starts. The third line therefore runs python outside the environment and installs the packages in the wrong place. Activating can be made to work by keeping everything in one shell: join the commands with && ("run the next command only if this one succeeded") and continue the line with a backslash (\), as in . .venv/bin/activate && \. Calling $(VENV_PYTHON) directly avoids the issue altogether.

Things to know about this Makefile

  • Run make setup first. make test and make run fail until the environment exists, with an error such as make: .venv/bin/python: No such file or directory.
  • Re-running make setup is harmless. Because setup is phony, its recipe runs every time. venv reuses the existing .venv, and pip checks the requirements again but skips packages that are already installed (Requirement already satisfied).
  • The path is for macOS and Linux. On native Windows, the environment's Python is .venv\Scripts\python.exe instead.
  • Make is one option among several. Many Python developers use Make as a task runner, especially in projects that also involve shell commands, containers, documentation, or compiled parts. Python-specific tools such as tox, nox, Poetry, Hatch, and uv cover similar ground.

Python automation centres on environment reproducibility, dependency installation, and task orchestration. The runner may be a shell script, a Makefile, or another tool, but the goals are the same: define the environment, install dependencies, run checks, and make the workflow repeatable for others.
