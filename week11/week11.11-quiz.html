Quiz — 10 questions

11.11 Check Your Understanding

These questions check concepts, not syntax recall. Think through each one — and commit to an answer — before opening the answer key at the bottom.

Question 1
In Bash, what does echo "x{a,b}" print?
Question 2
A script contains cat <<'EOF', followed by the line user=$USER and then EOF. What does cat output for that line?
Question 3
With src="lib/util.c", what does echo "${src%.c}.o" print?
Question 4
A Makefile for a C project has the rule %.o: %.c with the recipe gcc -c $< -o $@. Make needs util.o. What command does it effectively run?
Question 5
A C project's Makefile contains app: main.o util.o (linking with gcc -o $@ $^) and the pattern rule %.o: %.c. main.c includes util.h. After a successful build, only util.h is edited and make is run. What happens?
Question 6
Which of these setup steps is not safe to run repeatedly on the same machine?
Question 7
A Makefile target contains the recipe line echo "Built on $(date +%F)". Running make prints Built on with no date. Why?
Question 8
A test target has two recipe lines: first . .venv/bin/activate, then python -m unittest on the next line. The tests run, but using the system Python rather than the virtual environment. Why?
Question 9
In a standard Maven project, what does mvn package do?
Question 10
A .gitlab-ci.yml (using the Docker executor) has a build job that runs make app, and a later test job whose script is ./app. The build job succeeds, but the test job fails with ./app: No such file or directory. What is the most likely explanation?
Answer key — open only after committing to your answers
  1. x{a,b}
    Brace expansion happens only in unquoted text. Inside double quotes the braces are ordinary characters, so the word is passed through unchanged. Without the quotes, x{a,b} would become xa xb before echo ran (11.2).
  2. The text user=$USER, unchanged
    Quoting the here-document delimiter (<<'EOF') turns off expansion inside the body, so the text is written literally. With an unquoted <<EOF the shell would substitute the login name. The quoted form is what you want when generating a script or Makefile that has its own $ signs (11.3).
  3. lib/util.o
    ${src%.c} removes the shortest matching suffix .c, leaving lib/util; the literal .o is then appended. The directory part is untouched, which is why the result is not just util.o (11.3).
  4. gcc -c util.c -o util.o
    % matches the stem util, so the prerequisite is util.c. $< is the first prerequisite and $@ is the target, so the recipe becomes gcc -c util.c -o util.o. One rule generates the concrete command for every object file (11.4).
  5. Make reports that app is up to date and rebuilds nothing
    The pattern rule only says an object depends on its .c file. Nothing tells Make that the objects depend on util.h, so editing the header changes no prerequisite it knows about and the stale objects stay. Add a line such as main.o util.o: util.h so a header edit rebuilds both objects and relinks app (11.4, 11.5).
  6. echo 'export PATH=$PATH:$HOME/bin' >> ~/.profile
    The >> operator appends, so each run adds another copy of the line and the file keeps changing. mkdir -p and venv converge on the same state however often they run, and a second make with nothing edited does nothing because every target is up to date (11.5).
  7. Make expands $(date +%F) as one of its own variables before the shell sees it
    In a recipe, $(...) is Make's variable syntax, and a variable named date +%F does not exist, so it expands to nothing. To hand a literal $(date +%F) to the shell, escape the dollar: $$(date +%F). The tab/space issue would produce a missing separator error rather than a quiet blank (11.4).
  8. Each recipe line runs in its own shell, so the activation is lost before the second line
    Make starts a separate shell for every recipe line, so environment changes such as activate do not carry over. The simplest fix is not to activate at all and call the environment's Python by its path: .venv/bin/python -m unittest. Alternatively, keep both commands in one shell by chaining them on one logical line: . .venv/bin/activate && python -m unittest. Make does run every line, and . is the portable way to load the script (11.7).
  9. Runs the lifecycle phases in order up to and including package, including compile and test
    In Maven's default lifecycle, asking for a phase runs every earlier phase first: validate, compile, test, then package. A failing test therefore stops the build before a JAR is made (unless tests are deliberately skipped with -DskipTests). The later phases, install and deploy, are not run (11.8).
  10. Each job runs in a separate container, so the executable built in one job is not present in the other unless it is passed on
    With the Docker executor, each job starts in its own fresh container with a checkout of the repository. Files produced by build are not there when test starts, unless the build job declares them as artifacts (later-stage jobs download those by default) or the test job rebuilds them (for example with make test, which depends on app). Nothing is wrong with running ./app in CI itself, and stages run in the order listed (11.9).
