11.3 Shell Templates and Parameter Expansion

One of the most useful forms of metaprogramming is generating files from templates. Real projects often need a README, a config file, a starter script, or a repeated folder structure. Instead of writing each by hand every time, let the shell generate it. Bash supports this with here-documents, which supply a block of text to a command, and with parameter expansion and command substitution, which fill in the parts that change. Setup becomes repeatable and less error-prone.

Here-documents: a block of text for a command

A here-document feeds several lines of text to a command's standard input. You choose a delimiter word after <<, write the text, and end it with a line containing only that delimiter:

cat <<END
Hello, $USER
END

The shell, not cat, processes the here-document:

  1. It sees <<END (or <<'END') and notes the delimiter.
  2. It reads lines until it finds a line containing exactly that delimiter.
  3. If the delimiter was unquoted, it performs expansions on the text (details below).
  4. It sends the resulting text to the command through standard input.

EOF ("end of file") is only a popular name for the delimiter; END works equally well. Any word is fine, provided the closing line repeats it.

A project scaffold

project="demo_app"
mkdir -p "$project"/{src,tests,docs}

cat > "$project/README.md" <<EOF
# $project

Created on $(date +%F)

## Structure
- src/
- tests/
- docs/
EOF

Three ideas combine here. The variable $project avoids repeating the name. Brace expansion creates the directories in one step. And the here-document, written to README.md by cat >, has $project and $(date +%F) filled in before the file is written. The script does not merely make directories; it writes a document whose contents are partly generated.

A generated configuration file

app_name="inventory-service"
port="8080"

cat > config.env <<EOF
APP_NAME=$app_name
APP_PORT=$port
EOF

File generation is not an advanced trick reserved for large systems. You already do it whenever you copy, edit, and rename similar text files; here-documents make that process reusable.

Quoting the delimiter: expansion on or off

The quotes do not change the delimiter's name: in both forms below, the closing line is plain EOF. What the quotes change is whether the shell expands the text before cat receives it.

<<EOF — expansion enabled. The shell expands variables ($HOME), command substitutions ($(date +%F)), and arithmetic ($((2 + 3))):

$ cat <<EOF
home=$HOME
today=$(date +%F)
result=$((2 + 3))
EOF
home=/Users/alice
today=2026-10-10
result=5

<<'EOF' — expansion disabled. The text reaches cat exactly as written:

$ cat <<'EOF'
home=$HOME
today=$(date +%F)
result=$((2 + 3))
EOF
home=$HOME
today=$(date +%F)
result=$((2 + 3))

The shell removes the single quotes when it works out the delimiter, so the closing line is still written EOF, not 'EOF'.

Opening lineDelimiter on the closing lineContents of the here-document
<<EOFEOFExpanded by the shell: variables, $(…), $((…))
<<'EOF'EOFPassed through literally
When to quote Use <<EOF for a template, where you want the shell to fill values in. Use <<'EOF' when you are generating another script or a Makefile that contains its own $ signs, which must be written into the file untouched.
The closing delimiter must stand alone The closing line must contain only the delimiter: no leading text, trailing spaces, or comment. A line such as EOF # done is not recognised as the end. Bash then keeps reading to the end of the input and warns that the here-document was delimited by end-of-file. Put explanations outside the here-document.

Deriving one filename from another

Templates also need names that follow a pattern. Bash parameter expansion can transform strings without calling any external tool:

src="main.c"
obj="${src%.c}.o"
echo "$obj"

This prints main.o. The pattern ${src%.c} removes the shortest matching suffix .c, then .o is appended. Build automation constantly converts source names into output names, and this tiny example prepares you for the same logic in Make's pattern rules (11.4).

FormMeaningExample result for src=lib/main.c
${src%.c}Remove the shortest matching suffixlib/main
${src#lib/}Remove the shortest matching prefixmain.c
${src%.c}.oSwap an extensionlib/main.o

Extended into a small generator (*.c means "C source files", a stand-in for whatever files your project has):

for src in src/*.c; do
  obj="${src%.c}.o"
  echo "Would compile $src into $obj"
done

Even though this only prints messages, it shows the core automation pattern: derive output names systematically rather than inventing them one at a time. Once names are generated consistently, they can be handed to compilers, linkers, test runners, or reporting scripts.

Watch for overwriting cat > file replaces whatever was there. A scaffold script that is run twice will silently overwrite a README you have since edited. A careful generator checks first, for example [ -e "$f" ] || cat > "$f" <<EOF ..., where $f holds the file name: the file is written only if it does not already exist — a theme that returns in 11.5.
