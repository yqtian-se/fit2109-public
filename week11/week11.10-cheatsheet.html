The same workflow in each ecosystem

C is compiled with gcc and driven by Make; Python has no separate compile step, so its automation is mostly about the environment; Java is built with Maven. Bash, Make, and CI are not tied to any one language.

For any of the three, a .gitlab-ci.yml can run the build and test commands as CI jobs on every push.

Bash expansions

SyntaxResult
mkdir -p p/{src,tests}Brace expansion: p/src p/tests (not inside quotes; not part of POSIX sh)
${name}Parameter expansion: the variable's value
$(cmd)Command substitution: the output of cmd
${f%.c}.oStrip a suffix, then append one
cat > f <<EOF … EOFHere-document: expands variables, $(…), and $((…)) inside; <<'EOF' passes the text literally. The closing EOF must be alone on its line

Make syntax

SyntaxMeaning
target: prerequisitesA rule; the next lines, indented with a tab, are the recipe. Each recipe line runs in its own shell
make (no target)Builds the first target in the file, the default goal
%.o: %.cPattern rule: any .o from the matching .c
$@ · $< · $^Target · first prerequisite · all prerequisites
CC = gcc … $(CC)Define and use a Make variable (:= also works, as in 11.7)
$$(date)A literal $(date) passed to the shell
.PHONY: cleanclean is an action, not a file, so its recipe runs whenever requested
main.o: util.hExtra prerequisite with no recipe, e.g. header dependencies

Maven lifecycle (default)

validate → compile → test → package → verify → install → deploy. Asking for a phase runs every earlier one. clean is a separate lifecycle and is never run automatically: use mvn clean package to rebuild from scratch.

I want to… → Do this

I want to…Do this
Make a task repeatable for my teamPut it in a script, a Makefile target, or the POM; commit it
Rebuild only what changedDeclare prerequisites in the Makefile and let make compare timestamps
Make sure a header change triggers a rebuildAdd main.o util.o: util.h (or list headers in each rule)
Run a setup script twice without harmUse mkdir -p, venv, and checks like [ -e f ] ||; avoid appending to config files with >>
Use $(date) in a Makefile recipeWrite $$(date)
Use a venv from a Make recipeCall its Python directly: .venv/bin/python -m unittest
Let python -m unittest find tests in tests/Add an (empty) tests/__init__.py and name files test_*.py
Run the checks on every pushAdd .gitlab-ci.yml with build and test jobs, each with a suitable image
Hand a built file to a later CI jobList it under artifacts: paths: in the job that creates it
The through-line Shell expansion, a Make pattern rule, a Maven phase, and a CI job are all the same move: describe the work once, let a tool generate and run the concrete steps. When you meet a new build tool, ask what it treats as targets, what as prerequisites, and what it uses to decide something is out of date.
