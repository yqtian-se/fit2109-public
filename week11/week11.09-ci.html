11.9 Continuous Integration and Repository-Based Automation

So far the automation has run on one developer's machine: make, mvn test, python -m unittest. Each check only helps if someone remembers to run it. Continuous integration (CI) moves those same commands onto a server, which runs them automatically whenever new code is pushed. The name comes from the practice it supports: team members integrate their changes into the shared code often, and each pushed change can be checked automatically.

This page uses GitLab CI/CD, which is configured by a file named .gitlab-ci.yml at the root of the repository. CI itself is not tied to a language or a service: a CI job just runs shell commands, so the same idea works for C, Python, or Java. Other services, such as GitHub Actions, use a different file format for the same idea.

Background: the vocabulary

TermMeaning
PipelineOne complete run of the CI configuration, usually triggered by a push
JobA named unit of work inside a pipeline: a list of shell commands to run
StageA group of jobs. Stages run in order; jobs within a stage may run at the same time
RunnerGitLab Runner is the application that picks up jobs and executes them. It can run on a server, a cloud machine, or even a developer's computer; GitLab.com also provides shared runners
ImageA container image (Week 6, 6.5) that provides the job's operating system and tools, such as gcc or Python. With a container-based runner (see below), each job runs in a fresh container created from it

Background: reading YAML

.gitlab-ci.yml is written in YAML, a format for structured settings. Three rules cover everything on this page:

  • key: value sets a value, for example stage: build.
  • Indentation shows nesting: lines indented under a key belong to it. Indent with spaces, never tabs — the opposite of a Makefile.
  • A line starting with a dash and a space (-) is one item in a list, such as one command under script.

A Make-based C project

Assumption for the examples Runners can execute jobs in different ways, called executors: directly in a shell on the runner machine, in Docker containers, on Kubernetes, and others. The examples on this page assume a Linux runner using the Docker executor, which is how GitLab.com's hosted Linux runners work. With this executor, the image setting chooses the container each job runs in; with a plain shell executor, image has no effect and the tools must already be installed on the runner machine.

For the C project from 11.6, whose Makefile has an app target and a test target that depends on it:

.gitlab-ci.yml
stages:
  - build
  - test

build_app:
  stage: build
  image: gcc:14
  script:
    - make app

test_app:
  stage: test
  image: gcc:14
  script:
    - make test
LineMeaning
stages:The stages, in the order they run: build, then test
build_app:, test_app:Job names, chosen by you
stage: buildWhich stage the job belongs to
image: gcc:14Run the job in the official gcc container image, which provides gcc and make
script:The commands to run. If any command fails, the job stops and is marked as failed

What happens when you push

  1. You push commits to GitLab. GitLab finds .gitlab-ci.yml and creates a pipeline.
  2. For each job in the first stage, a runner starts a fresh container from the job's image, checks out the repository's code into it, and runs the script commands.
  3. If every job in a stage succeeds, the next stage starts. By default, if a job fails, the later stages do not run (GitLab can be configured to let particular jobs fail, or to run jobs only after a failure).
  4. The result appears in GitLab: a success or failure status on the commit, on the project's pipelines page, and on any merge request (GitLab's equivalent of a pull request, Week 5). Each job's full terminal output is kept as a log, so you can see exactly which command failed.

By default, a pipeline runs on every push. Pipelines can also be configured to run for merge requests, on a schedule, or manually from the GitLab web page; those need extra settings not covered here.

Jobs run in separate environments With the Docker executor, each job runs in a separate container, so files created by one job are not automatically available to another. The executable app created by build_app is not there when test_app starts. The example still works because make test lists app as a prerequisite, so Make builds it again. To hand files from one job to a later one instead, declare them as artifacts of the job that creates them. By default, jobs in later stages automatically download the artifacts produced by jobs in earlier stages:
.gitlab-ci.yml (build_app with artifacts)
build_app:
  stage: build
  image: gcc:14
  script:
    - make app
  artifacts:
    paths:
      - app

A Python project

.gitlab-ci.yml
stages:
  - test

python_tests:
  stage: test
  image: python:3.12
  script:
    - python -m pip install -r requirements.txt
    - python -m unittest

These are the install and test steps of the bootstrap script in 11.7, run in the official python image. There is no virtual environment here: the job's container is already a throwaway environment used only by this project, so isolating packages a second time is unnecessary. (Running bash scripts/bootstrap.sh as the script line would also work, and would keep CI identical to local development.) Because the container is new for every pipeline, the packages are installed from scratch each time, which helps reveal dependencies missing from requirements.txt. It cannot catch every one: a package imported only by code that the tests never run can still be missing.

Unlike the lines of a Makefile recipe, the lines of a job's script run one after another in the same shell, so a variable set or a directory changed on one line still applies on the next.

A Maven project

.gitlab-ci.yml
stages:
  - build
  - test

maven_build:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn compile

maven_test:
  stage: test
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn test

The image provides Maven and Java 17 (Eclipse Temurin is a free build of Java). As with the Make example, maven_test starts in a fresh container, so mvn test compiles the code again before testing; the lifecycle (11.8) makes that automatic. This intentionally repeats compilation, so that a compile error and a failing test show up as different failed jobs. A small project could instead use a single job that runs mvn test. If mvn test fails in the pipeline for a merge request's branch, the team sees the failure before the code is merged.

From personal convenience to a shared contract

A local script helps you on one machine. A CI pipeline defines the project's expected behaviour for everyone who touches the repository, and it runs in a clean, controlled environment. That reduces the "works on my machine" problem: a build that only succeeds because of something installed on one laptop is likely to fail in CI, where the problem is visible to everyone.

Local commandThe same command in CI
make app, make testscript: lines in build_app and test_app
python -m unittestThe last script: line of python_tests
mvn compile, mvn testscript: lines in maven_build and maven_test

CI is not a separate topic from Make, Python environments, or Maven: it builds on them. The commands you run locally often become the commands in the pipeline, which is a strong reason to automate them locally first. Continuous integration then moves those workflows into a shared, automated, repository-driven context — automation maturing from personal convenience into collaborative software practice.
