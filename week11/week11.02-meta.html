11.2 Metaprogramming in Everyday Development

The word metaprogramming sounds abstract, but in this unit it means something practical: writing code, commands, or configuration that help generate, control, or organise other code or commands. Instead of performing each step yourself, you write something that produces those steps. In Bash this shows up as shell expansion; in Make it shows up as rules and patterns.

Brace expansion: one word becomes several

Suppose you want a project layout with three directories. You could type three mkdir commands, or one:

$ mkdir -p project/{src,tests,docs}
$ ls project
docs  src  tests

Bash performs brace expansion before the command runs. It is purely textual: the shell rewrites project/{src,tests,docs} into three separate words, project/src project/tests project/docs, and only then starts mkdir. By the time mkdir runs, the braces are gone: it receives three ordinary arguments.

$ echo project/{src,tests,docs}
project/src project/tests project/docs
$ echo "project/{src,tests,docs}"
project/{src,tests,docs}

The second command shows a catch: brace expansion does not happen inside quotes, so the braces are printed literally. Other expansions behave differently: as the next example shows, variables and $(…) are still expanded inside double quotes.

Variables and command substitution

Two more expansions let a command be partly generated from data:

name="week11-demo"
echo "Project: ${name}"
echo "Created on $(date +%F)"

${name} is parameter expansion, and $(date +%F) is command substitution: the shell runs date, captures its output, and splices it into the command line. The command you type is therefore not literally the command that executes. The shell first rewrites it into a more concrete form, and that rewriting is one of the simplest everyday examples of metaprogramming.

Brace expansion is not portable Brace expansion is a Bash feature that is not specified by POSIX. A portable POSIX sh script must not rely on {a,b} being expanded. If a script uses Bash-specific features such as brace expansion, it should declare Bash as its interpreter — for example, with #!/usr/bin/env bash rather than #!/bin/sh.

On macOS, /bin/sh has traditionally been Bash running in compatibility mode, and it may still perform brace expansion, making the script appear portable. On Debian and Ubuntu, /bin/sh normally points to dash, which treats {a,b} literally. Consequently, the script may behave differently on a teammate’s machine.

Why bother?

Many automation tasks are well-organised repetition: creating similar files, running similar commands, deriving one filename from another. If you can express the pattern once, the shell applies it many times, consistently. Compare:

for unit in 1 2 3; do
  mkdir -p "week${unit}"/{notes,examples,solutions}
done

This is not just fewer keystrokes. The structure of the task is described once: the loop runs mkdir three times, and brace expansion gives each run three directory names, so nine directories are created. Change the list of units or subfolders and the same script produces a different, equally consistent result.

Try this In a scratch directory, run the loop above, then ls -d week*/*. Then change 1 2 3 to 1 2 3 4 and run it again. Because of mkdir -p, the second run adds week 4 and does not complain about the rest — a first hint of the idempotence idea in 11.5.

A useful mental model: ordinary programming tells the computer what to do with data; metaprogramming tells it how to generate or organise the commands, files, or workflows themselves. The same idea reappears in shell templates, Makefiles, and CI configuration for the rest of the week.
