Tool focus: Make

11.4 Pattern Rules and Automatic Variables in Make

If Bash shows metaprogramming at the level of commands and small files, Make shows it at the level of whole builds. Make reads a file called a Makefile that describes how the files of a project are produced from one another, and then runs only the commands that are needed. This page first gives a little background on building a C program, then shows how a Makefile writes one rule that covers many files.

Background: how a C program is built

Make works with any language, but its classic use is building C programs, so this page and the next two use C. If you have not used C before, the picture below is all you need. A C project is made of several kinds of file:

File typeExtensionWhat it isExample
Source file.cC code written by a programmermain.c, util.c
Header file.hDeclarations (names and types of functions) that source files share by writing #include "util.h"util.h
Object file.oThe compiled machine code for one source file. It cannot be run on its ownmain.o, util.o
Executable(none)The runnable program, made by joining object files togetherapp

The tool that does the work is gcc, the GNU C compiler. Building takes two kinds of step: compiling each source file into an object file, then linking the object files into one executable.

$ gcc -c main.c -o main.o       # compile: main.c  -> main.o
$ gcc -c util.c -o util.o       # compile: util.c  -> util.o
$ gcc -o app main.o util.o      # link:    main.o + util.o -> app

In these commands, -c means "compile only, do not link" and -o names the output file. Because each source file is compiled separately, changing one .c file means only that file has to be compiled again. (A changed header is different, because every source file that includes it is affected; pitfall 2 below returns to this.) Deciding which steps are needed is exactly the job Make takes over. Languages such as Python, which run the source directly, do not have these compile and link steps.

A first Make rule

A Makefile is a plain text file, usually named Makefile, in the project folder. It is made of rules. Each rule names a target (the file to produce), its prerequisites (the files it is built from), and a recipe (the command that builds it):

Makefile
main.o: main.c
	gcc -c main.c -o main.o

Read it as: "main.o is built from main.c, by running this command". When you type make main.o, Make runs the recipe only if main.o is missing or older than main.c.

Recipe lines start with a tab Every recipe line must begin with a tab character, not spaces. A Makefile indented with spaces fails with missing separator. Configure your editor to insert real tabs in Makefiles.

Writing one such rule for every object file in a large project would be repetitive, which is where patterns come in.

Pattern rules: one rule for every object file

GNU Make lets a rule use % as a placeholder for a "stem", the part of the name that changes. This is a pattern rule, and it goes in the same Makefile:

Makefile
%.o: %.c
	gcc -c $< -o $@

It describes how to make any .o file from the matching .c file, not just main.o. The target pattern %.o means "any object file", and the prerequisite pattern %.c means "the C source file with the same stem". This is metaprogramming: the rule is not one concrete build step, but a description from which many concrete steps are generated.

Automatic variables: $@, $<, and $^

A pattern rule cannot write a fixed filename in its recipe, because the filename changes each time it is used. Instead it uses automatic variables, which Make fills in for the rule it is currently running: $@ is the target and $< is the first prerequisite. When Make is building main.o, the recipe above becomes, in effect:

$ gcc -c main.c -o main.o

and when it is building util.o it becomes gcc -c util.c -o util.o. One compact rule generates the right concrete command for every file.

A third variable, $^, means all the prerequisites. It is useful for the linking step:

Makefile
app: main.o util.o
	gcc -o $@ $^

Here $@ is app and $^ is main.o util.o, so the effective command is gcc -o app main.o util.o. Add a third object file to the prerequisites and the recipe adapts by itself.

VariableMeaningValue in app: main.o util.o
$@The target being builtapp
$<The first prerequisitemain.o
$^All prerequisitesmain.o util.o

This matters most in larger projects. If a repository has ten C files, you do not want ten near-identical compile rules. A single pattern rule plus automatic variables expresses the shared structure once. That reduces repetition, and it reduces mistakes: if the compile command changes, you edit one place instead of ten.

Two pitfalls with patterns and recipes

1. Make reads $ before the shell does Because $@ and $< are Make syntax, Make expands every $ in a recipe before handing the line to the shell. So in a recipe, $(date +%F) is read as a Make variable called date +%F, which does not exist and expands to nothing. Write $$(date +%F) to pass a literal $(...) through to the shell:
Makefile
show:
	echo "Today is $(date +%F)"      # prints: Today is
	echo "Today is $$(date +%F)"     # prints: Today is 2026-10-08
2. A pattern rule does not know about headers %.o: %.c says each object depends on its .c file, and nothing else. If main.c includes util.h and you edit only util.h, Make sees no changed prerequisite, reports that everything is up to date, and you may keep running a program built from the old header. Add the header dependency explicitly:
Makefile (added line)
main.o util.o: util.h

A rule written without a recipe only adds prerequisites to the named targets; Make still takes the recipe from the pattern rule.

Phony targets: actions, not files

So far every target has been a file that Make creates, such as main.o or app. A phony target is different: it names an action to run rather than a file to produce. Targets such as clean, test, and install usually describe commands, not outputs.

Makefile
.PHONY: clean

clean:
	rm -f app *.o

Run it with make clean. Make prints the recipe and runs it:

$ make clean
rm -f app *.o

Why .PHONY is needed

Make normally treats every target name as a filename. Without the .PHONY line, the rule above still works — until a file or directory named clean appears in the project. Make then sees that "the target clean" already exists, has no prerequisites that could be newer, and concludes there is nothing to do:

$ touch clean
$ make clean
make: 'clean' is up to date.

The rm command never runs. The line .PHONY: clean prevents this by telling Make: clean is an action, not a file; run its recipe whenever it is requested, regardless of what files exist.

Putting it together

Here is everything from this page combined into one Makefile for the C project with main.c, util.c, and util.h:

Makefile
app: main.o util.o
	gcc -o $@ $^

%.o: %.c
	gcc -c $< -o $@

main.o util.o: util.h

.PHONY: clean
clean:
	rm -f app *.o
Line(s)Role
app: main.o util.oThe first target, so a bare make builds it; links the objects with $@ and $^
%.o: %.cPattern rule: compiles any object file from its source, using $< and $@
main.o util.o: util.hExtra prerequisite, so editing the header rebuilds both objects
.PHONY: cleanclean is an action, so it always runs when asked

Together these rules describe which file is built from which. Those relationships form a dependency graph, the topic of the next section. Bash metaprogramming often generates commands directly; Make metaprogramming generates build logic from patterns, variables, and rules. Both describe reusable structure instead of repeating concrete steps by hand.
