Tool focus: Maven

11.8 Java Automation Workflows: Maven Lifecycle and Dependency-Driven Builds

This page automates a Java project with Apache Maven. Maven is primarily used for Java and other projects that run on the Java Virtual Machine (JVM); other ecosystems have their own equivalents, such as npm for JavaScript or cargo for Rust.

Background: what building Java involves

  • Classes and packages. Java code is written in classes. A .java file may contain several classes, but at most one of them can be public, and the file must be named after it: the public class App lives in App.java. Classes are grouped into packages with dotted names such as edu.monash.fit2109, and the folder path mirrors the package name: edu/monash/fit2109/App.java.
  • Compiling. The Java compiler, javac, turns each class into a .class file of bytecode. Bytecode is not machine code for your processor; it is run by a Java Virtual Machine (JVM), launched by the java command. That is why the same compiled program can run on any operating system, provided a compatible JVM is installed and the program does not rely on platform-specific features.
  • Packaging. The .class files are usually bundled into one JAR file (.jar, a ZIP-format archive) to share or run.
  • Libraries. Third-party libraries are also distributed as JARs. To compile or run, Java must be told where they are, via a list of locations called the classpath.

Done by hand, that means downloading the right JARs, then typing long javac and java commands with the classpath spelled out. Maven automates all of it: it downloads libraries, compiles, runs tests, and packages, driven by one file, pom.xml.

Three ideas to separate

IdeaWhat it isWhy it helps
The POMpom.xml, the Project Object Model: the project's identity, its dependencies, and plugin configurationOne declarative file describes the project

The standard layout

week11-demo/
├── pom.xml
├── src/
│   ├── main/java/edu/monash/fit2109/App.java
│   └── test/java/edu/monash/fit2109/AppTest.java
└── target/                 # created by Maven

Main code goes under src/main/java, tests under src/test/java, and anything Maven produces goes into target/, which is safe to delete (mvn clean does that). Because projects that follow Maven's standard layout use these locations, the POM does not have to list source files at all. (A POM can override the locations, but most projects keep the defaults.) The two Java files used on this page are:

src/main/java/edu/monash/fit2109/App.java
package edu.monash.fit2109;

public class App {
    public static int add(int a, int b) { return a + b; }

    public static void main(String[] args) {
        System.out.println("2 + 3 = " + add(2, 3));
    }
}
src/test/java/edu/monash/fit2109/AppTest.java
package edu.monash.fit2109;

import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class AppTest {
    @Test
    void addsNumbers() { assertEquals(5, App.add(2, 3)); }
}

main is where a Java program starts. The test uses JUnit, a widely used Java testing framework (a third-party library, not part of Java itself): @Test marks a test method, and assertEquals fails the test if the two values differ.

A small pom.xml

The POM is written in XML: information is held between matching opening and closing tags, such as <version>1.0-SNAPSHOT</version>, and tags nest inside one another.

pom.xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>edu.monash.fit2109</groupId>
  <artifactId>week11-demo</artifactId>
  <version>1.0-SNAPSHOT</version>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.0</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
PartMeaning
<project> attributes, <modelVersion>Standard boilerplate that identifies the file as a Maven POM; copy it as is
groupId, artifactId, versionThe project's coordinates: the group or organisation that publishes it (often written as a reversed domain name), the project's name, and its version. Together they identify one particular version of a project, whose build produces artifacts (published files such as a JAR). SNAPSHOT marks a version still in development
<properties>Settings for the build: compile for Java 17, and read source files as UTF-8 text. Without an explicit release setting, the compiler plugin falls back to Java 8 compatibility, which current Java compilers warn is obsolete. Declaring 17 makes the intended Java version explicit
<dependency>A library this project needs, named by its coordinates: here, JUnit
<scope>test</scope>The library is needed only to compile and run the tests, not by the program itself

The project is not just storing code; it is declaring which external libraries it needs and when. On the first build, Maven downloads each dependency, and the plugins the build uses, from a public online repository, Maven Central, and keeps a copy in a cache in your home folder (~/.m2/repository), so later builds work without downloading again.

The lifecycle: later phases include earlier ones

Maven's default lifecycle is an ordered list of phases. These are the main ones (Maven has a few finer-grained phases in between):

PhaseWhat happens
validateChecks that the project is correctly set up
compileCompiles the main code in src/main/java into target/classes
testCompiles the test code, then runs the tests
packageBundles the compiled code into a JAR in target/
verifyRuns configured checks to confirm that the package is valid. (Integration tests, if a project has them, run in an integration-test phase just before verify)
installCopies the JAR into your local cache ~/.m2/repository, so other projects on your machine can use it as a dependency
deployUploads the JAR to a shared remote repository for other people; used for releases

Asking for a phase runs every phase before it too. So mvn package does not merely "make a JAR": it validates, compiles, runs the tests, and then packages.

$ mvn compile        # validate → compile
$ mvn test           # validate → compile → test
$ mvn package        # validate → compile → test → package

If a test fails during mvn package, Maven stops at the test phase with BUILD FAILURE, before reaching package, so no JAR is produced. (Tests can be skipped deliberately with -DskipTests, and passing tests do not prove a program is free of bugs.) Because the layout, POM, and lifecycle follow conventions, you do not need to tell Maven where the Java files are.

clean is a separate lifecycle clean is not a phase of the default lifecycle above; it belongs to its own small clean lifecycle. Maven does not clean the project before every build, so files left in target/ by an earlier build stay there. To start from scratch, ask for it explicitly, for example mvn clean package, which deletes target/ and then runs the default lifecycle up to package.
Who actually does the work: plugins Maven is built around plugins: lifecycle phases coordinate the build, while plugin goals perform operations such as compiling, testing, and packaging. For a JAR project, Maven binds plugin goals to the relevant phases (not every phase has one): compile runs the compiler plugin, test runs the Surefire plugin (which runs JUnit tests), and package runs the JAR plugin. That is why a small POM with no plugins listed can still build, test, and package.

Running the program from Maven

Running a class normally means typing java with the right classpath. The Exec Maven Plugin adds a goal, exec:java, that runs a chosen class with the project's dependencies already on the classpath. To use it, add a <build> section inside <project>, after </dependencies>:

pom.xml (added section)
<build>
  <plugins>
    <plugin>
      <groupId>org.codehaus.mojo</groupId>
      <artifactId>exec-maven-plugin</artifactId>
      <version>3.6.3</version>
      <configuration>
        <mainClass>edu.monash.fit2109.App</mainClass>
      </configuration>
    </plugin>
  </plugins>
</build>

A plugin is identified by coordinates, like a dependency. <mainClass> gives the fully qualified name of the class to run: its package name plus its class name.

$ mvn compile exec:java
2 + 3 = 5
Phases vs. goals compile is a lifecycle phase; exec:java is a plugin goal, written plugin:goal. One command line can mix them, and Maven runs them left to right: first the lifecycle up to compile, then the exec:java goal. Running mvn exec:java on its own would not compile first.

Now the repository defines not just how to compile and test the code, but how to run it. Maven is more than "a tool that downloads Java libraries". It is a declarative automation system: the POM declares the project and its dependencies, the standard layout reduces guesswork, and the lifecycle gives the build a predictable shape. Like a Makefile, it encodes how a project should be built and run in a form that other tools and developers can execute consistently.
