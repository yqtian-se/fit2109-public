8.10 "Works on My Machine" — Environment Differences

One of the most frustrating debugging situations: a program runs perfectly on your laptop, crashes in CI, or behaves differently on a teammate's machine. The bug is real — but the cause is not in the code itself. It is in the environment the code runs in.

Understanding environment differences is essential because modern software runs in many places: developer laptops (macOS, Windows, Linux), CI servers, staging containers, and production servers. Each has its own combination of OS, runtime version, installed packages, file paths, and configuration.

Common root causes

Root causeExampleHow to detect
Python / runtime versionCode uses f-strings (Python 3.6+) but the server runs Python 3.5.python3 --version on both machines.
Library version mismatchYou have requests==2.31 locally; CI installs the latest, which has a breaking change.Compare pip freeze outputs side by side.
Missing environment variableCode reads os.environ["API_KEY"] — set on your machine via .bashrc, absent in CI.printenv | grep API; check CI secrets configuration.
Path differencesCode opens "data/input.csv" but the working directory differs in CI.Print os.getcwd() and os.path.abspath("data/input.csv") at startup.
OS behaviour differencesFile path uses \ on Windows, fails on Linux. os.path.join handles this correctly; string concatenation does not.Run on the target OS — or in a container that matches production.
File permissionsScript expects to write to /tmp/output, but the container runs as a restricted user.ls -la /tmp; check the user with whoami.
Locale and encodingFile contains UTF-8 characters; server uses ASCII locale and crashes on read.locale command; open files with encoding="utf-8" explicitly.

Diagnosing environment bugs

When a bug only appears in one environment, your first job is to diff the environments, not the code:

  1. Collect facts from both environments — runtime version, installed packages, relevant env vars, working directory.
  2. Compare — look for anything that differs.
  3. Reproduce the failing environment locally — use a container (Docker), a virtual environment (venv), or a CI job that you can inspect.
# Snapshot your environment -- share this when reporting the bug
$ python3 --version
Python 3.11.4
$ pip freeze > requirements_snapshot.txt
$ printenv | sort          # inspect all env vars
$ python3 -c "import sys; print(sys.path)"

Strategies for prevention

  • Pin your dependencies. Every ecosystem has a lockfile mechanism — use it. An unpinned dependency will silently upgrade and break things.
  • Use environment isolation. Keep each project's dependencies separate from the system and from other projects.
  • Use containers for CI. A Docker image that matches production eliminates OS and system-library differences. If it passes in the container, it will pass in production.
  • Never hardcode absolute paths. Use relative paths anchored to the source file's location — every language has a way to do this.
  • Validate required env vars at startup. Check for all required environment variables before the program does anything else, and fail with a clear message if any are missing.

Dependency management by language

LanguageDependency fileIsolation toolSnapshot command
Python requirements.txt python3 -m venv .venv pip freeze > requirements.txt
Java (Maven) pom.xml + pom.xml lock via Maven Wrapper Maven Wrapper (./mvnw) pins the Maven version itself Declare exact versions in <dependency> tags — avoid LATEST or ranges
JavaScript package.json + package-lock.json node_modules/ per project (auto-isolated) npm ci installs exactly what is in the lockfile
C/C++ No universal standard — CMakeLists.txt or Makefile System package versions; containers are the most reliable isolation Document exact library versions in a README or use conan.lock / vcpkg.json
Why containers solve this A container bundles the OS, runtime, libraries, and your code into a single image. When you run that image locally and in CI, both environments are byte-for-byte identical. "Works on my machine" becomes "works in this image" — and the image goes everywhere. This is especially powerful for C/C++ projects where system library versions are otherwise hard to control.
Try this In a project you are working on, snapshot its dependencies using the appropriate tool (pip freeze for Python, check pom.xml versions for Java, inspect package-lock.json for JavaScript). Compare with a classmate — how many differences do you find? Those differences are potential "works on my machine" bugs waiting to happen.
