5.6 Tracing Problems and Regressions with bisect

Some bugs are easy to trace because you already know roughly where they came from. Others are much harder: a project that worked last week now fails, but the code has changed many times in between. Looking through the log one commit at a time is possible, but slow. This is the kind of problem git bisect is designed to solve.

The situation has a name: a regression is behaviour that used to work and now does not. Because Git history is a series of snapshots taken over time, tracking one down is a search problem. Somewhere between a commit where the behaviour was still correct and one where it is not, a single commit changed it — and the job is to find which.

git bisect searches that range by binary search. You give it one commit known to be good and one known to be bad; it checks out the midpoint for you to test, and each verdict you give it discards half of what remains. The saving is exactly what binary search buys anywhere: the number of tests grows with the logarithm of the range rather than its length, so a span of 1,000 commits takes around 10 tests rather than 500.

A worked session

Suppose the login tests pass at release v1.0 but fail on today's main. You start a bisect by marking those two endpoints — the tag is usable here because, as Section 5.4 noted, Git accepts any commit reference where a commit is expected:

$ git bisect start
$ git bisect bad              # the commit I am on is broken
$ git bisect good v1.0         # this release was fine
Bisecting: 9 revisions left to test after this (roughly 3 steps)
[c3d4e5f] Refactor session handling

Notice what just happened to your files: Git has checked out commit c3d4e5f, so the working tree now contains the project exactly as it stood at that point. That is what makes the next step possible — you run your test against real code, not against a diff:

$ python -m pytest tests/test_login.py
... 4 passed
$ git bisect good             # this one is fine; the bug is later
Bisecting: 4 revisions left to test after this (roughly 2 steps)
[d4e5f6a] Add password reset

$ python -m pytest tests/test_login.py
... 1 failed
$ git bisect bad              # broken here; the cause is earlier
Bisecting: 1 revision left to test after this (roughly 1 step)

You continue answering good or bad until the range collapses to a single commit, which Git then names:

d4e5f6a is the first bad commit
commit d4e5f6a...
Author: Dave <dave@example.com>

    Add password reset

 auth.py | 12 +++++++-----

Four questions answered, and the culprit is identified out of a dozen candidates. Each verdict you gave was a plain yes-or-no about observed behaviour — at no point did you have to reason about what any commit's code was doing.

Bisect is only as reliable as your test Every step asks you the same question, so you must be able to answer it the same way every time. A test you run slightly differently at each step, or a bug that only appears intermittently, will produce a confident but wrong answer — one misjudged verdict sends the search into the wrong half and it never comes back. Decide exactly how you will reproduce the problem before you start, and use the same check at every step.

After bisect finds the culprit

First, a word about where you have been standing all this time. To hand you each commit to test, Git checked them out in a detached HEAD state — the same look-but-don't-commit mode you met with tags in Week 4. That is why none of this disturbed your work: you were never on a branch during the search, so no branch moved. It also means the bisect is not finished just because Git has named the culprit; you are still in bisect mode until you say otherwise.

The rest is a short, fixed routine: read the commit, leave bisect mode, then repair on a normal branch.

# bisect has named d4e5f6a as the first bad commit

# 1) Read what that commit actually did — this moves nothing
$ git show d4e5f6a

# 2) End the bisect and go back to where you started
$ git bisect reset
Previous HEAD position was d4e5f6a Add password reset
Switched to branch 'main'

# 3) Branch off the code you actually want to repair
$ git switch -c fix/login-regression

# 4) Edit the files, then commit the fix
$ git add auth.py tests/test_login.py
$ git commit -m "Fix login regression introduced by d4e5f6a"

Step 2 is the one to remember. git bisect reset ends the search and returns you to the branch you were on when you started it — skip it and you are left stranded at some midpoint commit, wondering why your files look wrong. Step 3 then branches from that restored branch, which is the current code, not from the old bad commit.

Inspect the bad commit, but fix on a normal branch The bad commit may be old, while your real target for repair is usually the current main branch or a maintenance branch. If the bad commit has already been shared with others, it is usually safer to add a new fixing commit rather than editing history.
bisect rewards good commit discipline When the result of a bisect is a non-merge commit, you should normally be able to discover the problem by examining just that commit — which is much easier if developers break changes into small, self-contained commits. A repository full of giant mixed commits is harder to debug historically.

It is helpful to contrast git bisect with git blame. Blame answers "which commit last changed this line?" Bisect answers "which commit introduced the behavior change I am observing?" A bug can appear because of interactions across multiple lines or files, so line-level annotation is not always enough — bisect works at the level of snapshots and observed behavior. Because every local clone has the full history, bisect is also a good example of why Git's distributed model makes debugging local, fast, and under your control.
