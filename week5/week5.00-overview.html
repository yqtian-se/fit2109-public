Week 5: Version Control with Git — Collaboration & History

Pre-reading · FIT2109 · Monash University

By the end of this week you should be able to

  1. Explain what a remote and a remote-tracking branch are, and state precisely what fetch, pull and push each change.
  2. Work in a shared repository day to day — clone, pull, commit, push, and publish a branch — and explain what a pull request adds on top of Git itself.
  3. Read conflict markers correctly, and either resolve a merge conflict or back out of it deliberately.
  4. Rebase a branch onto a newer base, and choose between merging and rebasing for a given situation.
  5. Investigate history with git log, git diff, git blame and git show, including comparing two branches with a commit range.
  6. Find the commit that introduced a regression using git bisect, and explain what makes a bisect trustworthy.
  7. Choose between git revert and git reset according to whether a commit has been shared, and describe what each reset mode keeps.

A scenario

Your group cloned the unit's project repository a fortnight ago, so all four of you have a complete copy of the project and its history sitting on your own laptop. Since then you have worked exactly the way Week 4 described: a branch for your part of the assignment, small commits with clear messages, and a local history you are honestly a bit proud of.

Tonight you need to combine everyone's work — and this is where Week 4 runs out.

Your commits exist on your laptop and nowhere else. Your teammate's exist on theirs. Running git log on your machine shows a project where you appear to have done all the work, because your machine has never seen a single one of their commits. And git merge is no help: it combines two branches that live in the same repository, but your teammate's branch simply is not in yours. Four complete copies of one project have quietly drifted into four different versions of the truth, and nothing in Week 4 can bring them back together.

Week 4 was Git on one machine. Week 5 is Git between machines, and it begins with the piece deliberately left out until now: how one copy of a repository exchanges commits with another. Once that exists, three further questions follow naturally.

  • How do you take in your teammates' commits without losing or overwriting your own?
  • How do you look over each other's work before it gets combined, rather than discovering the problems afterwards?
  • When a change everyone already has turns out to be wrong, how do you undo it without disrupting the copies they are working from?

Each one has a precise answer in Git, and this week works through them in that order.

Concept check — before you start You have already met a clue to this week's first idea without it being explained. In Week 4's Section 4.6, immediately after cloning a repository, git status reported "Your branch is up to date with 'origin/main'", and git log --oneline showed (HEAD -> main, origin/main). You know what the branch main is — so what is this second name, origin/main, sitting beside it? And how could your own laptop claim to know whether it is still up to date with anything? Section 5.1 answers exactly this.
