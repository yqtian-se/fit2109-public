5.4 Rebasing

Rebase is Git's second way of integrating one branch into another, alongside merge. Where a merge joins two lines of history with a new commit, a rebase moves one of them: it takes your commits and re-applies them, one at a time, on top of a different starting point.

The command, precisely

In its standard form, rebase takes the commits on the branch you are currently on and applies them to the tip of the branch you name:

$ git rebase <base>

Two details in that sentence do most of the work:

  • The branch that moves is the one you are on. git rebase never modifies the branch you pass to it — <base> is only the destination, and it is left exactly where it was.
  • <base> need not be a branch. It can be any commit reference: a local branch, a remote-tracking branch such as origin/main, a tag, or a raw commit hash.

The first point is the one people routinely get backwards, so it is worth committing a rule to memory:

Which branch goes where git switch <the branch I want to move>
git rebase <the branch I want to put it on top of>

For the ordinary feature-branch case — your branch was created from main, but main has moved ahead while you were working — that rule reads:

$ git switch feature      # the branch I want to move
$ git rebase main        # the branch I want to put it on top of

Git takes the commits that exist only on feature, sets them aside, fast-forwards feature to the tip of main, and then re-applies each of those commits in their original order. The result is a feature branch that looks as though it had been created from the latest main all along — a linear history, which many teams find easier to read than one broken up by small merge commits.

Merge vs. rebase

This is the main conceptual difference between the two. A merge preserves the fact that two branches diverged and were later combined, usually by creating a merge commit. A rebase, by contrast, changes the base of your branch by replaying its commits elsewhere, so the branch history appears linear.

Where rebase is actually used

Two situations account for most day-to-day rebasing, and they are worth telling apart.

1. Updating your feature branch before it is merged. This is the case in the diagram above, and the alternative to the "merge main into your branch" habit from Section 5.2. Instead of recording a merge, you move your branch on top of the newer main, so the eventual pull request contains only your commits and shows a clean diff:

$ git switch main
$ git pull                    # get main's newest commits
$ git switch feature
$ git rebase main

You can skip the round trip through main by rebasing onto the remote-tracking branch directly, which is possible precisely because <base> accepts any commit reference:

$ git fetch origin
$ git rebase origin/main

2. Pulling without creating a merge commit. When you and a teammate have both committed to the same branch, an ordinary git pull merges their work into yours and records a merge commit for it — often with a message like "Merge branch 'main' of …". A history full of these says nothing useful. git pull --rebase integrates by replaying your commits on top of theirs instead, leaving a straight line:

$ git pull --rebase

This is the "second way of integrating" that Section 5.1 mentioned when introducing git pull. Many developers prefer it often enough to make it the default for every repository on their machine:

$ git config --global pull.rebase true
Rebase rewrites commit history After a rebase, the rebased commits are not literally the same old commits moved somewhere else — Git creates new commits with new identities because their parent relationships have changed. Rebasing is usually appropriate for local, unpublished work, but dangerous for already shared history: rewriting commits you have already pushed can confuse other developers by creating alternate versions of the same change.

Resolving conflicts during a rebase

Rebase can conflict for the same reason merge can: a commit being re-applied touches lines that have changed underneath it. The markers in the file look exactly as they did in Section 5.3, and you edit them the same way. What differs is the shape of the process. A merge stops once, with everything on the table. A rebase re-applies your commits one at a time, so it stops at the first commit that conflicts, waits for you, then carries on to the next — and can stop again. A rebase of four commits may pause anywhere from zero to four times.

The normal path: resolve and continue

  1. See what stopped it. git status names the conflicted files, and also tells you which commit is being applied — useful, because the conflict belongs to that one commit rather than to the branch as a whole.
  2. Edit the conflicted files into the version you want and delete the markers, exactly as in Section 5.3.
  3. Stage what you fixed with git add <file>.
  4. Carry on with git rebase --continue. Git finishes applying that commit and moves to the next one. If it stops again, repeat these same four steps — that is the loop, not a sign that something has gone wrong.
$ git rebase main
# Git stops on the first conflicting commit
$ git status                    # which files, and which commit
# edit the files, delete the markers
$ git add conflicted-file.py
$ git rebase --continue        # repeat if it pauses again
Do not finish a rebase with git commit This is the habit to unlearn from merge conflicts. Resolving a merge ends with git commit (or git merge --continue), but a rebase is not building one new commit — it is re-applying yours in sequence. Running git commit mid-rebase creates a stray extra commit and leaves the rebase still in progress. Always finish each pause with git rebase --continue.

The other path: back out entirely

If the conflicts turn out to be more than you want to take on right now, you can stop the whole operation rather than fighting through it commit by commit:

$ git rebase --abort

This returns your branch to exactly where it stood before the rebase began — the original commits, with their original identities, on their original base. Any conflict resolution you had already done during this attempt is discarded along with it, which is the trade: aborting is completely safe for your existing history, but you do lose the work of the attempt itself. Aborting and merging main in instead is a perfectly reasonable response to a rebase that turns out badly.

In short Rebase is a history-shaping tool: useful for moving your work onto a newer base, keeping local branch history linear, and cleaning up unpublished commits before sharing them. If merge emphasizes preserving the exact branching history, rebase emphasizes rewriting your branch so its history is cleaner and more linear.
