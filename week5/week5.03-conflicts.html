5.3 Revisiting Merging and Conflict Resolution

Once two people work on the same project, their changes have to be combined. Most of the time Git does this silently and you never notice: if you edited one file and your teammate edited another, or you both edited the same file in different places, Git simply takes both. A merge conflict is the much narrower case where Git cannot decide on your behalf — where the same region of the same file was changed differently on each side, and any automatic choice would risk throwing away someone's work.

The same thing happens in a pull request. When the compare branch and the base branch conflict, the platform lists the files involved and the "Merge pull request" button stays disabled until the conflict has been resolved.

Conflicts become more likely the longer two lines of work stay apart, because more edits accumulate on each side. The habit that prevents most of them is therefore to synchronise often rather than once at the end of a long task: bring your local main up to date, and merge it into your feature branch while the differences are still small enough to reason about.

How a conflict actually arises

It is easier to reason about conflicts after watching one appear. Take the smallest possible case: you and one teammate share a project and both work on main, exactly as in the first workflow of Section 5.2. The repository contains a one-line file, greeting.py:

message = "Hello"

Your teammate gets there first. They change that line, commit, and push:

# teammate's machine — changes the line to: message = "Hello, world!"
$ git add greeting.py
$ git commit -m "Use a friendlier greeting"
$ git push

You know nothing about this, because their commit only reached the remote — not your machine. Working from the older version, you edit the same line differently and commit:

# your machine — changes the same line to: message = "Welcome"
$ git add greeting.py
$ git commit -m "Use Welcome as the greeting"

Now you try to publish your work. Your push is refused — the remote has your teammate's commit, which you do not have — so you pull first, as Section 5.2 described. That pull is where the two versions finally meet:

$ git pull
Auto-merging greeting.py
CONFLICT (content): Merge conflict in greeting.py
Automatic merge failed; fix conflicts and then commit the result.

Nothing has gone wrong, and nothing has been lost. Both commits exist; Git simply has two different replacements for one line and no basis for preferring either. Note how specific this is: had your teammate edited a different line of greeting.py — or a different file entirely — this pull would have completed silently. It is the overlap that Git cannot resolve, not the fact that you both edited the project.

Opening greeting.py now shows both versions, kept side by side:

<<<<<<< HEAD
message = "Welcome"
=======
message = "Hello, world!"
>>>>>>> 9d4e7b0 (Use a friendlier greeting)

Your own version is on top, under HEAD; the incoming version is below, labelled with the commit it came from. Deciding between them is your job, not Git's — and that is what the rest of this section is about.

Resolving a conflict, step by step

Git has paused the merge and marked greeting.py as conflicted. The merge is unfinished: Git will not record it, and will not let you move on, until you say what that line should contain. Before editing anything, make sure you can read the block precisely, because the two halves are not interchangeable:

  • Between <<<<<<< and ======= is the version from HEAD — the side you already had, on the branch you are currently on.
  • Between ======= and >>>>>>> is the version coming in. Git labels it after the closing marker with whatever you merged: a branch name if you ran git merge <branch>, or the incoming commit if the merge came from a git pull, as above.

Resolving does not have to mean picking one side. Often the right answer combines both, or is something new that neither side contained — Git is showing you a disagreement to settle, not a multiple-choice question. What Git requires is only that the markers are gone and the file makes sense before you stage it.

The normal path: resolve and finish the merge

  1. Find out what is conflicted. git status lists every affected file under Unmerged paths. Do this first: a single merge can stop on several files at once, and every one of them has to be dealt with before the merge can complete.
  2. Edit each conflicted file into the version you actually want, and delete all three marker lines as you go. Git does not strip them for you — a file still containing <<<<<<< is almost always broken code, and committing one is a common and embarrassing mistake.
  3. Stage each file you have finished with git add <file>. There is no separate "mark as resolved" command — staging is that signal. Running git status again now tells you whether anything is still unmerged.
  4. Complete the merge with git merge --continue, which records the merge commit. It refuses to run while any conflict remains, so it also acts as a final check that you have not missed a file. (git commit finishes the merge equally well; --continue simply states the intent more clearly.)

Applied to the greeting.py conflict above, that is:

$ git status                  # greeting.py is listed as unmerged
# edit greeting.py: settle on the final wording, delete the markers
$ git add greeting.py       # this one is resolved
$ git status                  # confirm nothing is left unmerged
$ git merge --continue       # record the merge commit

The result is an ordinary merge commit with two parents — your commit and your teammate's — recording that the two lines of work were brought back together, and containing whichever wording you settled on. You can then git push as usual.

The other path: back out and try later

Resolving immediately is not always the right call. If the conflict turns out to be larger than expected, or it touches code you did not write and would rather discuss first, you can abandon the merge entirely instead of resolving it under pressure:

$ git merge --abort

This discards the half-finished merge and restores your branch and working tree to the state they were in before you started it — as though the merge had never been attempted. Your own commits are untouched, and so is your teammate's work on the remote; only the in-progress merge disappears. You can then talk it over, or synchronise at a better moment, and run the merge again. One caveat: if you had uncommitted changes in your working tree when the merge began, Git cannot always reconstruct them, which is one more reason to start a merge from a clean working tree.

Prevention beats resolution Some conflicts are easier to prevent than to resolve. Clear task boundaries, smaller pull requests, frequent synchronization, and review before merge all reduce the chance of painful integration later. Conflict resolution is part technical skill and part collaboration skill: Git shows you where the disagreement is, and the team still has to decide what the software should actually do.
