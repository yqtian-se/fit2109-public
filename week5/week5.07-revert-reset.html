5.7 Recovering from Common Mistakes

Even careful Git users make mistakes. You may stage the wrong files, commit too much in one snapshot, merge the wrong branch, push a flawed change, or realise that the current working tree has drifted into a state you do not want to keep. Git's recovery tools exist precisely because version control workflows need structured ways to undo, repair, and recover.

Two of the most important tools for this are git revert and git reset, and they solve different problems. git revert records a new commit that reverses the effect of an earlier one. git reset moves your branch to point at a different commit, and depending on the mode may also update the staging area and working tree.

Which one? Ask whether the commit has left your machine

Choosing between them is not a matter of taste or of which you happen to remember. It follows from a single question:

  • Has the commit been pushed, or could anyone else already have pulled it? Then use git revert. It only ever adds to history, so your branch stays ahead of the remote and everyone else's copy stays valid.
  • Is it still only on your machine? Then git reset is available, and is often tidier — it can take the commit off the branch entirely instead of leaving a reversal in the permanent record.

Everything else in this section follows from that split, so it is worth settling before reaching for either command.

git revert — the safer choice for shared history

git revert is the safer mental model when you need to undo a bad commit while preserving visible history. Because it creates a new commit whose effect is the opposite of an earlier one, it does not remove the original commit from the historical record. That makes it especially appropriate once a bad commit has already been shared with others or incorporated into a common branch — you are saying "this happened, and now here is the explicit reversal," rather than pretending the earlier commit never existed.

The contrast with reset is concrete rather than a matter of taste. Moving a shared branch backwards with reset leaves your local branch behind the remote's, so an ordinary git push is refused — the same refusal you met in Section 5.2, because the remote now holds a commit that you do not. git revert only ever moves history forwards: it adds a commit rather than removing one, so a plain git push is enough and nobody else's work is disturbed.

In practice it is a two-command fix. Suppose the password-reset commit turns out to be broken, and it is already on origin/main where your teammates can see it:

$ git log --oneline -3
9d4e7b0 (HEAD -> main, origin/main) Add password reset
5c1f6a8 Fix off-by-one error in tokenizer
3f8a2c1 Add token scanner

$ git revert 9d4e7b0
[main 1a2b3c4] Revert "Add password reset"
 1 file changed, 5 insertions(+), 7 deletions(-)

$ git push

Git opens an editor with a message already filled in — Revert "Add password reset" — which you can accept as is. Looking at the log afterwards shows what makes this safe:

$ git log --oneline -3
1a2b3c4 (HEAD -> main) Revert "Add password reset"
9d4e7b0 Add password reset
5c1f6a8 Fix off-by-one error in tokenizer

Both commits are still there. The broken change is recorded, and so is the decision to undo it — which is usually what you want on a shared branch, because a teammate who already pulled 9d4e7b0 simply pulls one more commit and ends up in the same state as you. Nothing they have is invalidated. As a bonus, the reversal is itself an ordinary commit, so if it later turns out the change was fine after all, you can revert the revert.

git reset — for local cleanup

git reset is about moving your branch tip and optionally aligning the index and working tree with that moved tip. git reset [<mode>] <commit> sets the current branch head to point at a chosen commit and, depending on the mode, may also update the staged state and the working directory. This is powerful, but it is also why reset must be used thoughtfully.

$ git revert <bad-commit>
$ git reset --soft HEAD~1
$ git reset --mixed HEAD~1
$ git reset --hard HEAD~1

The first creates a new commit reversing an earlier commit. The other three all move the branch tip back by one commit, and differ only in how much else they bring with them:

Reading down that table, each mode simply reaches one step further: --soft moves only the branch pointer, --mixed also clears the staging area, and --hard additionally overwrites the files on disk. Only the last one destroys work, which is why it is the one to pause over.

--soft is the hardest of the three to picture, so here it is doing the job it is best at: splitting a commit that bundled two unrelated changes, which is exactly the habit Week 4 warned against. The commit has not been pushed, so reset is fair game:

$ git log --oneline -1
7c2d1e9 (HEAD -> main) Fix regex and reformat utils

$ git reset --soft HEAD~1   # undo the commit, keep everything staged

$ git status
On branch main
Changes to be committed:
        modified:   validators.py
        modified:   utils.py

The commit is gone but not one line of work is lost — both files sit staged, exactly as they were the moment before you committed. From here you can rebuild the history you meant to record, unstaging one file so that each commit covers one idea:

$ git restore --staged utils.py
$ git commit -m "Fix email regex rejecting valid addresses"

$ git add utils.py
$ git commit -m "Reformat utils.py to consistent indentation"

One muddled commit has become two reviewable ones. Note that this only worked because the original commit was still local — had it been pushed, the same tidying would have meant rewriting history other people already had, and the right answer would have been to leave it alone.

--hard is the only one of the three that destroys work When you run git reset --hard, two different things can disappear at once, and they are worth separating. Any edit you had never committed is gone permanently — Git never recorded it, so there is nothing for it to restore from. The commit you reset past is a milder case: its snapshot is still in the repository, but no branch points at it any more, so getting back to it means knowing its hash (which git log would have shown you beforehand). The practical rule is the same either way: run git status first, and treat --hard as irreversible unless you are certain.
The rule that ties it together Before sharing your work, local history is often flexible — local cleanup workflows using reset are common. Once commits are shared, teams need greater care, because branch rewriting affects what other collaborators see and base their work on. That is why revert is the safer recovery tool for shared history, and reset is the stronger, more local-history-oriented repair tool.
