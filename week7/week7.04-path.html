7.4 How Bash Finds a Command: $PATH and Environment Variables

When you type a command such as python, git, or ls, Bash does not simply look for a program with that name in one universal place. Command lookup follows a fixed order, and knowing it explains a surprising number of "why did that run?" moments.

First, before any searching happens at all, Bash expands aliases — the shorthand names covered in section 7.5. An alias is replaced textually, so if you have one, it wins outright. After that, if the command name contains no slash, Bash checks in this order:

  1. Is it a shell function? A named block of shell commands you define yourself, also covered in section 7.5.
  2. Is it a shell builtin — a command built into Bash itself, such as cd?
  3. Can it be found in one of the directories listed in $PATH? If so, Bash runs the program from the first directory that has it.

If the command name does contain a slash, Bash skips all of this searching and tries to execute exactly the file you specified.

This explains why cd behaves differently from most other commands. cd is a shell builtin, so it is handled directly by Bash rather than by searching the filesystem. It also explains why ./myscript.sh works even when myscript.sh alone does not. The ./ includes a slash, so Bash executes the file path directly instead of searching PATH for a command name. As a speed optimisation, Bash also remembers where it found each command the first time, so repeat runs do not have to search every PATH directory again.

A useful set of commands for exploring this is:

$ echo "$PATH"
$ type -a ls
$ type -a cd
$ command -v python3
$ command -v git

echo "$PATH" shows the colon-separated list of directories Bash searches. type -a is especially useful because it can show whether a name resolves to a builtin, function, alias, or executable path. command -v gives a concise way to ask whether a command can be found and where. These commands are practical diagnostic tools when something "works on one machine but not another."

A refresher: shell variables, environment variables, and export

You met this in Week 2, and it matters here because PATH is itself an environment variable. Briefly, to refresh:

  • Writing name=value creates a shell variable. It exists only in the shell you typed it in.
  • export name promotes it to an environment variable, which means every program the shell launches from then on inherits a copy of it.
  • The environment is just that collection of name-value pairs handed down to child processes.

This is why PATH has to be exported: the shell is not the only thing that needs it. Other environment variables shape how programs behave in the same way. HOME is your home directory, SHELL names the shell you are using, and EDITOR or VISUAL tell any program that needs a text editor which one to open — that is how git commit knows to launch Vim rather than something else.

Putting your own commands on the PATH

The classic use of all this is making your own scripts runnable by name. This is the scenario from the overview, start to finish:

$ mkdir -p "$HOME/bin"
$ echo 'echo "Hello from custom command"' > "$HOME/bin/hello-fit2109"
$ chmod u+x "$HOME/bin/hello-fit2109"
$ export PATH="$HOME/bin:$PATH"
$ hello-fit2109
Hello from custom command

export PATH="$HOME/bin:$PATH" puts ~/bin at the front of the search list, so Bash finds your script there before looking anywhere else. Note that the old value is included on the right — forgetting :$PATH replaces the search list instead of extending it, and suddenly even ls cannot be found.

That export applies only to the current shell, which is exactly the disappearing-setting problem from the overview. To make it permanent, put the line in a startup file — ~/.bashrc for interactive shells, as section 7.2 explains.

Command lookup is the mechanism; environment variables are the knobs that shape it. Between them they explain most cases of a command being found on one machine and not on another.
