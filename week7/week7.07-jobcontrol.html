7.7 Managing Long-Running Commands: Job Control, ps, Signals, and nohup

A command-line environment is not only about startup files and customisation. It is also about managing running programs. Almost every command you have run in this unit so far has finished while you sat and waited for it. This section is about what to do when you do not want to wait — when a command takes twenty minutes and you need your shell back — and about how to see and control what is running on the machine.

Three words you need first

Three terms come up constantly in this section, so it is worth pinning them down before anything else:

  • A running program is a process, and the operating system gives each one a process ID (or PID) — a number that uniquely identifies it while it runs.
  • A command runs in the foreground when it holds your terminal: you see its output, and you cannot type another command until it finishes.
  • A command runs in the background when it keeps running but hands the prompt straight back to you, so you can carry on working in the same terminal.

Bash's documentation defines job control as the ability to stop a process, resume it, and move it between the foreground and the background. Bash treats each pipeline you run as one job and keeps a table of the jobs currently running, which the jobs command displays.

Starting a command in the background

The easiest way to start a command directly in the background is to put & at the end of it:

sleep 300 &
[1] 48231
jobs
[1]+  Running                 sleep 300 &

When Bash starts a job in the background, it prints two numbers: the job number in square brackets ([1]) and the process ID (48231). The job number is small and local to your shell, which is what makes it convenient to type. The jobs command then lists the active jobs and their status. Backgrounding suits commands that do not need you to interact with them, such as a long find, a test run, or a build.

Suspending and resuming

Often you only realise you need the shell back after starting a command in the foreground. Pressing Ctrl-Z pauses the foreground command and returns you to the prompt. The command is now suspended: still loaded, but frozen and using no CPU. From there you can resume it in the background with bg, or bring it back to the foreground with fg:

python3 long_task.py
# press Ctrl-Z — the command pauses and you get the prompt back
[1]+  Stopped                 python3 long_task.py
bg %1          # resume it, but in the background
fg %1          # pull it back to the foreground

The %1 here is a jobspec: % followed by a job number refers to that job, so %1 means job 1. Typed on its own at the prompt, a jobspec such as %1 does the same thing as fg %1. This shorthand is a large part of why job control feels quick once you have used it a few times.

Seeing every process: ps

jobs has an important limit: it only knows about work this shell started. It cannot see a program you launched from another terminal, something started at login, or a process belonging to another user. For the full picture you need ps, which lists processes running on the machine.

On its own, ps is deliberately narrow — just your own processes attached to a terminal:

$ ps
  PID TTY           TIME CMD
77974 ttys000    0:00.02 -bash
78006 ttys000    4:56.29 python long_task.py

The two invocations you will actually see people type are ps aux and ps -ef. Both mean "show me everything"; they are simply two different option styles that ps has inherited from its history, and on Linux both work:

CommandWhat it gives you
psYour processes in the current terminal. A quick sanity check, nothing more.
ps auxEvery process on the machine, with CPU and memory columns. a = all users, u = user-friendly columns, x = include processes with no terminal (background services). Note there is no dash.
ps -efEvery process in "full" format, including PPID — the parent process ID, which shows what launched what.
ps -p 48231Just one process, by PID. Useful for checking whether something is still alive.
ps -u $USEREvery process belonging to one user, terminal or not.
ps -o pid,ppid,stat,%cpu,commChoose your own columns, when the default output is more than you want.

Because there is far too much output to read, ps is almost always paired with the tools from Week 1 and Week 2 — a pipe into grep:

$ ps aux | grep long_task
student  48231  99.0  1.2  ...  python long_task.py
student  48302   0.0  0.0  ...  grep long_task

Notice the second line: grep has found itself, because it is also a running process whose command line contains the word you searched for. This confuses everyone once. If it bothers you, pgrep long_task does the same search and prints just the PIDs, without matching itself.

Reading the STAT column

The STAT column in ps aux output is worth knowing, because it connects directly to what you just did with Ctrl-Z:

CodeMeaning
RRunning, or ready to run.
SSleeping — waiting for something, such as input or a timer. Most processes look like this.
TStopped — exactly what a job suspended with Ctrl-Z looks like from the outside.
ZZombie — finished, but its parent has not collected its exit status yet.
+Appended to another code (e.g. S+) to mean the process is in the foreground.
Try this Run sleep 300 &, then ps -o pid,stat,comm -p followed by the PID Bash printed. You should see S. Bring it to the foreground with fg, suspend it with Ctrl-Z, and run the same ps command again — the state should now be T.
Linux extras On Linux, GNU ps adds long options that are handy but not available on macOS: ps aux --sort=-%cpu sorts by CPU use (highest first), and --sort=-%mem by memory. If you try these on a Mac you will get an "illegal option" error. For watching resource use live, top — or htop, if installed — is the better tool on either system.

Stopping a job: what a signal actually is

To stop a job completely, use kill:

kill %1

Despite the name, kill does not have only one way to stop something. It sends a signal — a short, standard message the operating system delivers to a process, which the process can then react to. You have already been sending signals without knowing it: the Ctrl-C from Week 1 is one, and the "terminated by signal" exit codes from Week 2 are what a shell reports afterwards.

You doSignal sentWhat it means
Ctrl-CSIGINT"Please stop." The program can catch this and clean up first.
Ctrl-ZSIGTSTP"Please pause." This is what actually suspends a foreground job.
kill %1 (no options)SIGTERM"Please shut down." The default — a polite request the program can still catch.
kill -9 %1SIGKILL"Stop now." Cannot be caught or ignored; the kernel ends the process itself.

The practical rule is to try a plain kill first and give the program a moment to shut down properly — closing files, releasing locks, saving state. Reach for kill -9 only when the program ignores that and is still running, because SIGKILL gives it no chance to tidy up after itself.

The examples above use %1, but kill accepts a PID just as happily — and that is the case you need whenever the process did not come from this shell and so has no job number. This is where ps earns its place: find the PID, then signal it.

$ ps aux | grep long_task
student  48231  99.0  1.2  ...  python long_task.py
$ kill 48231          # polite SIGTERM, by PID
$ ps -p 48231         # still there? if so, escalate
$ kill -9 48231
Try this Run sleep 300 &, then jobs to see it listed, then kill %1 and jobs again. Watch the job disappear from the table.

Outliving the terminal: nohup and disown

Job control lasts only as long as the shell that started the job. Close the terminal and the shell sends its jobs a SIGHUP signal — short for "hang up" — and they normally stop with it. Two small tools get around this.

If you know in advance that a command must outlive the terminal, start it with nohup:

nohup python3 long_task.py &   # ignores SIGHUP from the start

nohup runs the command with SIGHUP ignored, and by default sends its output to a file called nohup.out, so the output still has somewhere to go once the terminal is gone.

If the command is already running and you only now realise you need it to survive, disown fixes it after the fact. It removes the job from the shell's job table, so the shell no longer tracks it or signals it on exit:

jobs             # find the job number, e.g. [1]
disown %1        # detach it — closing the terminal no longer stops it

Think of these as three levels of the same problem. Job control manages commands inside one shell session. nohup and disown keep a single command alive after that shell closes. When you want a whole working session — several commands, several panes, an editor left open mid-file — to survive a closed terminal or a dropped connection, you need the tools in the next section.
