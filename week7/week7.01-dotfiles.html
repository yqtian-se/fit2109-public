7.1 What Dotfiles Are, and What They Do For You

Every setting in this week — your prompt, your aliases, your key bindings, your history — has to be stored somewhere, or it would vanish the moment you close the terminal. That somewhere is a dotfile. This short section defines what a dotfile is and what it is for; the two sections after it show which dotfiles your shell reads, and which other programs use them.

This week covers Bash Everything in Week 7 is written for Bash, the default shell on most Linux systems and the one this unit uses throughout. Other shells exist — most notably zsh, which has been the default on macOS since 2019 — and the concepts here carry across to them almost unchanged: they all have startup files, a search path, aliases, a prompt variable, job control, and a history. What differs is the file names. A zsh user edits ~/.zshrc where this week says ~/.bashrc, and ~/.zprofile where it says ~/.bash_profile. If you are on a Mac and your terminal says zsh, learn the ideas here and then look up the equivalent file names for your shell — or run bash to follow along exactly.

The definition

A dotfile is a configuration file whose name begins with a dot. That leading dot is the whole trick: by convention, tools that list files treat a name starting with . as hidden, so ls will not show it unless you ask with ls -a.

$ ls ~
Desktop  Documents  Downloads  bin
$ ls -a ~
.        .bashrc         .gitconfig  .profile  Desktop    Downloads
..       .bash_profile   .inputrc    .vimrc    Documents  bin

Beyond being hidden, there is nothing special about these files. They are ordinary text. You can open ~/.bashrc in any editor from Week 3, read it, and change it — no special command or permission is involved.

Try this Run ls -a ~ on your own machine and count how many dotfiles are already there. Most people are surprised: you have been accumulating them since the first time you used the terminal, and if you set up Git in Week 4 you created one yourself without being told that is what it was.

What they are for

Dotfiles exist to make settings persist and to keep them out of the way. Without them, every preference would have to be retyped in every new terminal. With them, your environment is described once, in a file, and rebuilt automatically each time a program starts. Broadly they serve three purposes:

PurposeExample filesCovered in
Set up your shell when it starts~/.bashrc, ~/.bash_profile, ~/.profile7.2, and what to put in them in 7.5
Change how the command line behaves as you type~/.inputrc7.3
Configure individual programs you use~/.vimrc, ~/.gitconfig, ~/.tmux.conf7.3

Why they are worth taking seriously

The real payoff is repeatability. A dotfile turns your environment from something you rebuild from memory into something you can declare. Think about what that saves you. Without dotfiles, every reinstall means re-configuring by hand, and every new lab server means typing the same five setup commands again. With them, you copy a few files across and you are done. Better still, keep those files in a Git repository — the same version control from Weeks 4 and 5 — and setting up a new machine becomes a single git clone. This is the same theme of reproducible environments the unit keeps returning to, applied to your own tools rather than to a project.

One rule of thumb before you start editing them: use dotfiles to make the command line predictable, not chaotic. Keep them readable, add a comment explaining why each setting is there, and avoid turning them into a large pile of copied internet snippets you do not understand. A configuration you cannot explain is one you cannot debug — and a broken ~/.bashrc affects every terminal you open afterwards.
