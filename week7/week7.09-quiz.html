7.9 Check Your Understanding

Quiz — 10 questions

These questions check concepts, not syntax recall. Think through each one — and commit to an answer — before opening the answer key at the bottom.

Question 1
You open a new tab in a typical Linux terminal emulator. Which file in your home directory does Bash read as it starts?
Question 2
A shell script you wrote does not see an alias you defined in ~/.bashrc. Why not?
Question 3
In an interactive Bash shell you define a shell function foo, and you also have an executable /usr/local/bin/foo on your $PATH. Which one runs when you type foo?
Question 4
You are running Bash. You add set editing-mode vi to ~/.inputrc, but line editing in the terminal you are sitting in does not change. Why?
Question 5
What is the key difference between an alias and a shell function?
Question 6
You set PS1='\u@\h:\w\$ '. What does the \$ at the end display?
Question 7
You start python3 train.py, press Ctrl-Z, then run jobs and see [1]+ Stopped. What does typing bg %1 do next?
Question 8
What is the practical difference between kill %1 and kill -9 %1?
Question 9
You start a long job with plain & and forget to nohup it. You are about to close the terminal. What can you do to stop it dying with the shell?
Question 10
Why would you reach for tmux or screen instead of just using nohup?
Answer key — open only after committing to your answers
  1. ~/.bashrc, because this is an interactive non-login shell
    Opening a tab does not log you in — you are already logged in, and the terminal simply starts another shell. That shell is interactive (you type at it) but non-login, and the file for that case is ~/.bashrc. The first option is the login-shell answer, which is what you would get by connecting over SSH; the third is the script answer. Remember that macOS Terminal.app is the exception that breaks this rule — it opens login shells (7.2).
  2. Scripts run in non-interactive shells, which do not read ~/.bashrc at all
    A non-interactive shell reads no startup file unless BASH_ENV is set, and it normally is not — so nothing ever defines your alias inside the script. There is actually a second reason, which is worth knowing because it defeats the obvious workaround: alias expansion itself is switched off in non-interactive shells (shopt expand_aliases reports off). So even if you forced the script to source ~/.bashrc, the alias still would not expand. This is exactly why aliases belong to interactive convenience and functions or scripts belong to automation (7.2, 7.5).
  3. The function, because Bash checks functions before builtins and before $PATH
    The lookup order after alias expansion is function → builtin → $PATH, and it stops at the first hit. Your function shadows the executable completely. This is the mechanism behind a common trick — wrapping a real command in a function of the same name — and behind a common confusion, when a forgotten function silently overrides a program. type -a foo shows every candidate in priority order, which is how you diagnose it. Note the question specifies an interactive shell: in a script the function would not even be defined, so the $PATH executable would run (7.4).
  4. The change only applies to shells started afterwards
    A dotfile is read once, at startup. Your current shell read ~/.inputrc when it began, so it is still using the settings from that moment — open a new terminal and vi mode will be there. The general rule from 7.3 is that editing a program's dotfile affects the next run of that program, not the one already running. Readline does offer an escape hatch here: pressing Ctrl-x Ctrl-r re-reads ~/.inputrc in the current shell. The other options are all false — the file name is right, and ~/.inputrc has nothing to do with GUI editors (7.3).
  5. Functions can use arguments, conditionals, and multiple commands; aliases are simple text substitutions
    An alias is replaced textually before the command runs, so there is no mechanism for it to receive an argument in the middle of the expansion — anything you type lands on the end. A function is real shell code with $1, $2, conditionals and loops available. The practical rule: alias for a fixed shorthand such as gs='git status', function as soon as an argument or a decision is involved, script once it deserves its own file (7.5).
  6. $ for a normal user, and # when running as root
    \$ is a prompt escape, not a literal dollar sign, and its whole purpose is to warn you: the moment your prompt ends in # you are root, and a mistyped command can affect the whole system. That is why leaving \$ in your prompt is worth doing even if you never customise anything else. The first option is what you would see only if the backslash were itself escaped, which is not what this prompt does (7.5).
  7. Resumes the job in the background, freeing up your terminal
    Ctrl-Z suspended the job — Stopped means frozen, using no CPU, not finished. bg sends it a continue signal and lets it run on without holding the prompt; fg would resume it in the foreground instead, which is the third option. Nothing here kills or restarts it. One caveat: a job moved to the background that then tries to read from the terminal will stop again immediately, because only the foreground job may take your keyboard input — so bg suits output-only work such as a build or a test run (7.7).
  8. kill %1 sends SIGTERM, which the process can catch and clean up after; kill -9 %1 sends SIGKILL, which cannot be caught or ignored
    Despite its name, kill just delivers a signal, and the process decides how to react. SIGTERM is a request: a well-written program uses it to flush buffers, remove temporary files, and close database connections before exiting. SIGKILL is not a request — the kernel removes the process, giving it no chance to tidy up, which is how you end up with stale lock files and half-written output. So try plain kill first and only escalate to -9 if the process ignores it (7.7).
  9. Run disown %1 to remove it from the shell's job table before closing
    Closing the terminal makes the shell send SIGHUP to its jobs. disown takes the job out of that table, so the shell no longer signals it and the process survives. The difference from nohup is timing: nohup must be used when you start a command, whereas disown rescues one already running — which is why "it is too late" is wrong. One practical catch: disown does not redirect output, so anything the job still prints goes to a terminal that no longer exists. For long jobs, redirect the output to a file when you start them (7.7).
  10. They give you back a full interactive session that you can detach and reattach
    nohup keeps one command alive but hands you nothing to work in: you cannot see its progress, run a second command beside it, or change your mind. A multiplexer keeps a whole session — several panes, an editor left open mid-file, a running server — that you detach from and reattach to later, from the same machine or a different one. That is why it suits real work over SSH, where the connection is the fragile part. The remaining options are all false: nohup is independent of tmux, both work fine on remote machines, and neither replaces job control inside a single shell (7.8).
