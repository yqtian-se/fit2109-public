7.3 Dotfiles Beyond the Shell, and Why They Work

Bash is not the only program that reads a dotfile. Your editor does, Git does, tmux does. Once you see the pattern behind all of them, an unfamiliar tool's configuration stops being a mystery — you know what kind of file to look for and where.

The mechanism: each program reads its own file at startup

There is no central settings system on a Unix machine, and the shell is not involved in any of this. The convention is simply that a program, when it starts, looks in your home directory for a file named after itself and reads it if it exists. Vim looks for ~/.vimrc. Git looks for ~/.gitconfig. tmux looks for ~/.tmux.conf. Nothing coordinates them; each program does its own lookup, at its own startup, entirely independently.

Two consequences follow, and they explain most confusion in this area:

  • Each file is written in that program's own language, not in shell syntax. ~/.bashrc contains shell commands because Bash runs it as shell commands. ~/.vimrc contains Vim commands, ~/.tmux.conf contains tmux commands, and ~/.gitconfig is a plain key-value file. Shell syntax such as export or if does not work in the non-shell ones.
  • The file is read at that program's startup — not yours. Editing ~/.vimrc changes the next Vim you open; editing ~/.bashrc changes the next shell. Nothing you change takes effect in a program that is already running, unless it offers a "reload config" command of its own.

The rc in so many of these names is a historical leftover meaning "run commands" — a file of commands run at startup. You will see it in bashrc, vimrc, inputrc, and screenrc.

~/.inputrc — how the command line feels to type into

This one is worth its own explanation, because it sits closest to the shell without belonging to it. When you edit a command line — moving the cursor, deleting a word, recalling earlier commands — that editing is not done by Bash itself but by Readline, a line-editing library that Bash and many other command-line programs use. Readline reads ~/.inputrc:

# ~/.inputrc
set editing-mode vi
set show-all-if-ambiguous on

Keeping this separate from shell startup is deliberate: how you like to edit text is a personal preference, independent of what your shell does. You may prefer Emacs-style editing — Readline's default, and the same family of bindings behind the Ctrl-A and Ctrl-E shortcuts from Week 1 — or vi-style bindings, which reuse the modal editing commands of Vim from Week 3. With editing-mode vi, the command line gains the same normal and insert modes you used in Vim, so h, j, k, l, w and dd work on the line you are typing.

Because Readline is a shared library rather than a shell feature, one ~/.inputrc changes the editing behaviour of every Readline-based program at once — which is exactly the point of putting it in a library.

If your shell is not Bash ~/.inputrc configures Readline, and Readline is the library Bash links against — it is not shared by every shell. zsh, the macOS default, has its own line editor and ignores ~/.inputrc completely, which is a common source of "I customised my line editing and nothing changed". The idea is the same; the file is not. Check which shell you are running before editing anything.

~/.vimrc — configuring your editor

Week 3 introduced Vim but left its configuration alone. ~/.vimrc is where it lives: a file of Vim commands, run every time Vim starts, exactly as if you had typed each one after opening the editor.

" ~/.vimrc — comments in Vim start with a double quote
set number
set expandtab
set tabstop=4
syntax on

Note the comment character. In ~/.bashrc a comment starts with #; in ~/.vimrc it starts with ". That is the "own language" point made concrete — and a good reason not to copy lines between dotfiles without checking.

Finding the dotfile for an unfamiliar tool

When you meet a new command-line program, you do not have to guess. Its manual page names its configuration file. Many manuals collect these under a FILES heading near the end; others simply mention the file in the description, so search the page rather than assuming a fixed layout:

$ man bash          # a FILES section listing ~/.bashrc, ~/.bash_profile, ~/.inputrc
$ man tmux          # no FILES section; ~/.tmux.conf appears in the description

Inside the pager, type / followed by a search term and press Enter — /\.conf or /FILES will usually find it quickly. This is the same habit as looking up a flag rather than memorising it: the documentation tells you which file a tool reads, and the convention above tells you roughly what to expect inside it.
