3.12 Multi-File Editing: Split Views and Multi-Cursor

Most authentic programming work is multi-file. Even a small change can involve a source file, a test file, a configuration file, and perhaps a build script or README entry. You have to move beyond the idea that editing means "modify one file, save, and close." VS Code's interface is designed explicitly for this broader style of work: you can open as many editors as needed side by side, vertically and horizontally, and editor groups can hold stacks of open items. That gives you a physical way of seeing relationships between files — a function definition on one side, a call site on another, a failing test below or beside them. That layout is not cosmetic; it changes how easily you can reason about a change.

Compare before changing

One of the first multi-file habits worth building is compare before changing. If you're renaming a function, updating a configuration value, or aligning a test with an implementation, it often helps to keep both files visible simultaneously. Split editing reduces unnecessary context switching and lowers the chance of "change one thing, forget the related place." A multi-file codebase becomes easier to understand when its related pieces can be seen in parallel rather than only serially.

How to split the editor

A split creates a second editor group next to the one you're in — the file you already have open stays put, and the new group is empty until you put something in it. There are three ways to create one:

MethodHowBest for
Split EditorCtrl+\ (Cmd+\), or the split icon in the top-right of the tab barSplitting the file you're already looking at, so you can scroll the two halves independently
Open to the SideCtrl+Enter (Cmd+Enter) after selecting a file in Quick Open (3.10), or Alt+click (Option+click on macOS) a file in the ExplorerOpening a different file directly into a new group, in one step
Drag a tabDrag any tab to the left, right, top, or bottom edge of the editor areaChoosing exactly where the new group lands — dragging to the bottom splits horizontally instead of side by side

Once you have more than one group, Ctrl+1, Ctrl+2, Ctrl+3 (Cmd+1/2/3) jump your cursor focus straight to group 1, 2, or 3 without touching the mouse. Ctrl+W (Cmd+W) closes the active editor in whichever group has focus; closing a group's last editor removes the split.

Multiple cursors and multiple selections

For repeated changes inside or across files, multiple cursors and multiple selections are extremely useful. Repeated edits are everywhere in code: renaming several lines in a config block, inserting the same prefix into several declarations, or adjusting similar function calls. Multi-cursor editing is faster than manual repetition, but its real value is not only speed — it helps you maintain visual control over a repeated change. You can see exactly which places are being affected before you commit the edit. That is an excellent habit in software work, where unintended text changes are costly.

Four ways to add a cursor

VS Code gives you several ways to create more than one cursor, and each suits a different situation:

MethodShortcutBest for
Alt+ClickAlt+click (Option+click on macOS)Placing cursors at specific, unrelated spots by eye
Add Selection to Next Find MatchCtrl+D (Cmd+D)Selecting one occurrence, then adding the next ones one at a time so you can skip any you don't want
Select All OccurrencesCtrl+Shift+L (Cmd+Shift+L)Changing every match of the current selection at once
Insert Cursor Above/BelowCtrl+Alt+↑/↓ (Cmd+Option+↑/↓)Editing a vertical column of similar lines, one directly above or below the last
Column (box) selectionShift+Alt+drag (Shift+Option+drag on macOS)Selecting a rectangular block across lines, instead of whole lines

Whichever method you use, Esc collapses everything back down to a single cursor.

The distinction between the middle two matters. Ctrl+D selects matches one at a time, so if the fourth occurrence of a word is not one you actually want to change, you simply stop pressing it before you reach that one. Ctrl+Shift+L selects all matches immediately — faster, but with the same blind-spot risk as search-and-replace in 3.13: it cannot tell a variable name from an identical word inside a comment or string.

Column selection for aligned edits

Multi-cursor placement assumes you want to edit the same text in several places. Column (box) selection is different: it selects a rectangular region across several lines regardless of what text is there, which is exactly what you want when adding the same prefix or suffix to a block of otherwise-different lines. Hold Shift+Alt (Shift+Option on macOS) and drag from the top-left to the bottom-right corner of the block.

Try this Open a file with a repeated word (several similar variable declarations, or a repeated string). Double-click one occurrence to select it, then press Ctrl+D (Cmd+D on macOS) a couple of times to add the next matches one at a time. Type a replacement and watch every selected occurrence update together. Then try Shift+Alt+drag (Shift+Option+drag on macOS) down the start of a few lines and type a short prefix, to feel the difference between matching-text cursors and column selection.

Not every repeated change should be done this way, though — sometimes search-and-replace or a language-aware refactor is the safer or faster tool. That decision is the subject of 3.13.
