3.14 Debugging in the Editor

Up to this point, "understanding what a program does" has meant reading it — navigating definitions, searching for names, tracing structure. But an editor connected to language tooling can also let you watch a program while it runs, one step at a time, instead of only reading it standing still. Many students' first debugging tool is a print statement sprinkled through the code and removed again afterwards. A modern editor's built-in debugger replaces most of that guesswork with a direct view of the program's live state — one of the clearest ways a plain text editor differs from an IDE.

Breakpoints: pausing a running program

The central idea is the breakpoint: a marked line where, if execution reaches it, the program should pause instead of continuing. In VS Code you set one by clicking in the gutter next to a line number, then start the file under the debugger from the Run and Debug view rather than running it normally. When the paused line is reached, the editor highlights it, and the running program is frozen at exactly that point — every variable still holding whatever value it had at that moment.

Reading a paused program

Once paused, three panes do most of the work:

  • The Variables pane shows the names and values in the current scope, so you can check whether a value is what you expected rather than guessing from a printed line.
  • The Call Stack pane shows the chain of function calls that led to where execution stopped — answering not just "what is this value," but "how did we get here."
  • The Watch pane lets you add your own expressions, so a value you care about stays visible as you continue stepping, instead of re-inspecting it manually each time.

Stepping through execution

ControlShortcut (all platforms)Effect
ContinueF5Run until the next breakpoint
Step OverF10Run the current line without descending into any function it calls
Step IntoF11Follow execution into a called function to see what happens inside it
Step OutShift+F11Finish the current function and return to wherever it was called from

Choosing between them is itself a skill: stepping into every function call quickly becomes overwhelming, so knowing when to step over versus step into is part of debugging efficiently rather than exhaustively.

Conditional breakpoints and logpoints

Two refinements make breakpoints more practical than an all-or-nothing pause. A conditional breakpoint only pauses when an expression you supply evaluates to true — useful when a bug only appears on, say, the hundredth iteration of a loop rather than the first. A logpoint prints a message to the console when hit, without pausing execution and without needing a print statement added to (and later removed from) the source itself. Both exist because pausing on every single pass through a loop is rarely what you actually want.

While paused, the Debug Console also acts as a small REPL scoped to the current stopped state: you can type an expression and see its value immediately, which is often faster than adding a watch or restarting the whole program to check one thing. Getting a debugger to start at all usually depends on a launch configuration and, for most languages, a language-specific debugger extension — the same way linting and formatting in 3.9 depend on installed language tooling rather than existing generically in every editor.

This vs. Week 8 This page is about the mechanics of the tool: how to set a breakpoint, read the paused state, and step through code. Week 8 is about the mindset of debugging: how to form a hypothesis about a bug, reduce it to a minimal reproducible example, and reason systematically instead of randomly. The debugger is what lets you observe a program's state directly; knowing what to do with that observation is a separate, and arguably harder, skill that Week 8 builds on top of it.
