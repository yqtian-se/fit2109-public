Week 3: Editor / Modern IDE

Pre-reading · FIT2109 · Monash University

By the end of this week you should be able to

  1. Explain what an editor actually manages underneath the interface: files, buffers, modes, and selections.
  2. Open a file in Vim or VS Code, make a small edit, save, and quit — without panicking.
  3. Navigate an unfamiliar project by name, symbol, and text search rather than by scrolling.
  4. Choose the right tool for a repeated change: direct edit, multi-cursor, search-and-replace, or a language-aware refactor.
  5. Explain why editors support remote development, and use that to start reading a codebase you did not write.

A scenario

You've just been added to a group project repository. Forty-odd files, no README worth trusting, and a bug report that just says "crashes sometimes." You did not write any of it. Where do you even start?

The instinct is to open a random file and start reading top to bottom, hoping understanding will arrive eventually. It rarely does. What actually works is treating the editor as more than a typing surface — as a set of tools for finding the likely entry point, searching for a name from the error message, comparing a call site against its definition side by side, and stepping through the program to watch it fail instead of guessing why.

That is what this week is really about. Not "how do I type code faster," but "how do I use an editor to understand and change code I didn't write, safely and efficiently." We will use Vim as the terminal example and VS Code as the GUI/IDE example, but the underlying ideas — buffers, modes, navigation, refactoring, debugging — show up in some form in almost every serious editor you will ever use.

Concept check — before you start When you save a file in an editor, what exactly changes — and what was different a moment before you pressed save? Keep this question in mind for 3.4 — Buffers vs Files.
