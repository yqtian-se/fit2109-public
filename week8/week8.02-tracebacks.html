8.2 Reading Error Messages and Tracebacks

An error message is the program telling you where to start. Reading it carefully is the single highest-leverage debugging action you can take — yet many developers glance at it and immediately start changing code instead.

Python tracebacks: read from the bottom up

Python prints a traceback that shows the entire call chain from the outermost call down to the exact line that failed. The structure can look overwhelming, but there is a simple rule: always start at the bottom.

Traceback (most recent call last):
  File "app.py", line 18, in <module>
    result = process(data)
  File "app.py", line 9, in process
    return data[index]
IndexError: list index out of range

Reading order:

  1. Bottom line — the error type (IndexError) and its message (list index out of range). This tells you what went wrong.
  2. Line immediately above — the exact file and line number where the exception was raised. This tells you where to look first.
  3. Stack above that — the chain of calls that led there. Scan upward to find the last line of your own code (not library code) — that is often the true root cause.
Common mistake Scanning the traceback from the top leads you to the outermost call — usually framework or library code that you did not write and cannot fix. Start at the bottom and work upward only as far as needed.

Java exceptions

Java prints a stack trace that reads the same way as Python — bottom of the meaningful part is where the failure happened, and the top-most frame in your code is usually the root cause. The key difference: Java distinguishes checked exceptions (the compiler forces you to handle them) from unchecked ones (runtime surprises, like Python's exceptions).

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 5 out of bounds for length 3
    at com.example.App.getItem(App.java:12)
    at com.example.App.process(App.java:7)
    at com.example.App.main(App.java:3)

Reading order: the first line names the exception class and message. The stack trace below lists frames innermost-first — getItem at line 12 is where the crash happened; main at line 3 is where execution began. Common Java exceptions:

ExceptionWhat it means
NullPointerExceptionA method or field was accessed on a null reference — the most common Java runtime error.
ArrayIndexOutOfBoundsExceptionAn array was accessed at an index that doesn't exist.
ClassCastExceptionAn object was cast to an incompatible type.
StackOverflowErrorInfinite or unbounded recursion exhausted the call stack.
NumberFormatExceptionA string could not be parsed as a number (e.g. Integer.parseInt("abc")).

C runtime errors

C has no exceptions. Errors manifest as unexpected behaviour, wrong output, or a crash signal from the OS. The most common signals you will encounter:

Segmentation fault (core dumped)    # accessed memory you don't own
Abort trap: 6                        # assert() failed or heap corruption detected
Floating point exception             # integer division by zero

"Segmentation fault" (or "segfault") is the most common. It means the program tried to read or write a memory address it was not allowed to access — typically from a NULL pointer dereference, a buffer overrun, or using memory after it was freed. On its own, the message tells you nothing about where in your code the fault happened — that is why you need a debugger (see section 8.6). Compile with gcc -g and run under GDB to get the exact line.

C errors are silent until they crash Unlike Python and Java, C will happily write past the end of an array without crashing — until the corrupted memory causes a crash many lines later, in completely unrelated code. This is why the crash location in C is often far from the actual bug. A tool like AddressSanitizer (gcc -fsanitize=address) catches memory errors at the point they occur, making them far easier to diagnose.

Shell command errors

Shell commands communicate failure through exit codes rather than exceptions. An exit code of 0 means success; anything non-zero means failure. Use echo $? immediately after a command to see its exit code. Error messages from shell commands also typically include the command name and a short reason — read the whole line before searching online.

$ cat nonexistent.txt
cat: nonexistent.txt: No such file or directory
$ echo $?
1
Try this Write a small Python script with an intentional KeyError (access a dictionary with a key that doesn't exist). Run it and practice reading the traceback: identify the error type, the failing line, and the call that triggered it. Then fix it.
