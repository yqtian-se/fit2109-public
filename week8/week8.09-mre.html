8.8 Minimal Reproducible Examples

A Minimal Reproducible Example (MRE) — sometimes called a Minimal Working Example or MCVE — is the smallest possible program that still triggers the bug. Every line that is not required to produce the failure has been removed.

Why bother making one?

  • Faster to reason about. A 10-line program is far easier to understand than a 500-line one. You can hold the whole thing in your head.
  • Reveals the true cause. Irrelevant code hides the bug. When you strip everything else away, the culprit is often obvious.
  • Required for good bug reports. Stack Overflow, GitHub Issues, and mailing lists all expect an MRE. Without one, maintainers cannot reproduce your problem and will often close the issue.
  • Making the MRE often is the fix. As you simplify, you frequently discover the assumption that was wrong — before you even finish reducing.

Before and after

Suppose your 200-line data pipeline crashes with IndexError: list index out of range. After creating an MRE:

# The MRE -- just 4 lines
data = [1, 2, 3]
index = len(data)        # off-by-one: valid indices are 0, 1, 2
print(data[index])       # IndexError: list index out of range

The full pipeline had authentication, file I/O, logging setup, and three helper classes — none of which mattered.

How to create an MRE manually

  1. Copy the failing code into a fresh, empty file.
  2. Remove all imports that are not needed to trigger the bug. Run after each removal to confirm the bug persists.
  3. Delete helper functions and classes unrelated to the failure.
  4. Replace file I/O, network calls, and database queries with hardcoded literal data (a list, a dict, a string).
  5. Simplify inputs to the smallest values that still trigger the bug (e.g. a list of 3 items instead of 10,000).
  6. Repeat until removing any single additional line makes the bug stop reproducing.
The golden rule After every removal, run the program and confirm the bug still appears. If you remove too much at once and the bug disappears, you don't know which removal was responsible.
Rubber duck debugging The act of explaining your bug to someone else — or to an imaginary rubber duck — forces you to articulate precisely what is happening. This often reveals the cause before you finish explaining. Creating an MRE has the same effect: the process of stripping away irrelevant code forces you to think clearly about what is actually necessary for the bug.

MREs in Java and C

The process is the same regardless of language — strip everything that is not required to trigger the bug.

  • Java: create a new class with a single main method. Replace database calls, network I/O, and framework setup with hardcoded literals. Aim for a single file that compiles and reproduces the exception with javac Repro.java && java Repro.
  • C: copy the failing code into a new .c file. Remove unrelated functions, replace file I/O with hardcoded arrays, and confirm the crash still occurs with gcc -g -o repro repro.c && ./repro. A good C MRE for a segfault is often under 10 lines.
Try this Take any bug you have seen recently — in your own code or a class exercise. Create a new file in whichever language applies (Python, Java, or C) and build an MRE from scratch. Aim for under 15 lines. Share it with a classmate and see if they can identify the cause in under one minute.
