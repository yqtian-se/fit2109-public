Week 8: Debugging — Systematic Bug Hunting

Pre-reading · FIT2109 · Monash University

"Everyone knows that debugging is twice as hard as writing a program in the first place. So if you are as clever as you can be when you write it, how will you ever debug it?" — Brian Kernighan

By the end of this week you should be able to

  1. Understand a practical debugging workflow: reproduce → isolate → inspect → fix → verify.
  2. Interpret error messages and logs to identify likely causes of failure.
  3. Apply a structured debugging process to resolve common problems.
  4. Use practical debugging tools — logging, static analysis, GDB/LLDB, and the VS Code debugger — to locate defects.
  5. Simplify problems by constructing minimal reproducible examples and using Perses to reduce them automatically.
  6. Identify and resolve bugs caused by differences in environment (local, remote, containerised).

A scenario

It is 10 pm, the assignment is due at midnight. Your program crashes with KeyError: 'email' — but only on some inputs, not all. You have been changing lines at random for 45 minutes. You fixed one thing, broke two others. You are not sure whether your last change made it better or worse, and you have no idea where the real problem is.

This is the experience that structured debugging is designed to eliminate. The developers who get out of this situation quickly are not smarter — they have a method. They reproduce the failure on demand, isolate it to a specific function, inspect the actual state of the program at that point, fix the root cause, and verify the fix holds. The whole process takes minutes, not hours.

This week gives you that method: the mindset, the tools (logging, linters, GDB, VS Code debugger, Perses), and the discipline to use them in order.

Concept check — before you start Think of the last bug you fixed. Did you reproduce it reliably first, or did you start changing code straight away? As you read, map your past habits onto the structured workflow introduced here.
