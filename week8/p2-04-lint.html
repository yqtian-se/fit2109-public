8.4 Static Analysis: Catching Bugs Before Runtime

Static analysis tools examine your source code without running it and report problems — unused variables, type mismatches, style violations, suspicious patterns. They act like a second pair of eyes that never gets tired and never misses a typo.

The key insight: a bug caught by a linter before you even run the program costs nothing to fix. The same bug caught in production costs far more.

What static analysis finds

  • Unused imports and variables (dead code that clutters reasoning)
  • Variables used before they are defined
  • Type mismatches — passing a string where an integer is expected
  • Unreachable code after a return
  • Style violations that reduce readability (PEP 8 for Python)
  • Common security-sensitive patterns (e.g. eval(), shell injection risks)

Tools by ecosystem

pylint
Python. Comprehensive linter: style, logic errors, and a score out of 10. Start here for a full picture. pip install pylint
flake8
Python. Lightweight PEP 8 style checker. Fast enough to run on every save. pip install flake8
mypy
Python. Static type checker — catches type errors without running the program. Needs type annotations to be most useful. pip install mypy
Checkstyle
Java. Enforces coding style (indentation, naming, Javadoc). Integrates with Maven and Gradle. Run: mvn checkstyle:check
SpotBugs
Java. Finds real bugs — null dereferences, resource leaks, infinite loops — by analysing bytecode. Run: mvn spotbugs:check
clang-tidy
C/C++. LLVM-based linter and static analyser. Catches memory errors, undefined behaviour, and style issues. Run: clang-tidy file.c --
shellcheck
Bash/sh. Catches quoting mistakes, undefined variables, and logic pitfalls that cause scripts to fail silently.
ESLint
JavaScript/TypeScript. Highly configurable linter. Catches unused variables, type issues, and enforces team style rules. npx eslint .

Reading pylint output

$ pylint bad_script.py
bad_script.py:4:0: W0611 (unused-import) Unused import os
bad_script.py:9:8: E0602 (undefined-variable) Undefined variable 'resut'
bad_script.py:12:4: C0103 (invalid-name) Variable name "x" doesn't conform to snake_case

Your code has been rated at 4.50/10

Each line follows the format: file:line:col: CODE (id) Message. The code prefix tells you severity: E = error, W = warning, C = convention, R = refactor. Fix errors first.

shellcheck on a Bash script

$ shellcheck bad_script.sh
In bad_script.sh line 5:
  for f in $(ls *.txt); do
                ^-- SC2045: Iterating over ls output is fragile.
                    Use a glob instead: for f in *.txt; do
Lint before every commit Many teams run linters automatically in CI — every push triggers a lint check and the build fails if there are errors. Even without CI, running lint before committing catches issues before they reach code review.
Try this Install pylint (pip install pylint) and run it on any Python file you have written recently. Read the output from top to bottom, fix the highest-severity issues (E codes), and re-run to confirm they clear.
