8.3 Log Levels — Separating Noise from Emergencies

Logs are a program's running commentary on what it is doing. Without structure, they become a wall of text that is impossible to read under pressure. Log levels give every message a severity, so you can filter for exactly the signal you need.

The five standard levels

Python's logging module (and most logging frameworks in other languages) defines five severity levels from lowest to highest:

LevelNumeric valueUse forShow by default?
DEBUG10Fine-grained detail useful only during investigation — variable values, loop counts, intermediate results.No
INFO20Normal milestones — "server started", "file loaded", "job complete".No
WARNING30Something unexpected happened but the program can continue — "config key missing, using default".Yes
ERROR40A recoverable failure — an operation failed but the program can keep running.Yes
CRITICAL50Fatal failure — the program cannot continue.Yes

Setting a level acts as a filter: only messages at that level or higher are shown. Setting level=logging.WARNING hides all DEBUG and INFO messages, giving you a clean view of problems only.

Python logging setup

import logging

# Configure once, usually near the top of your main script
logging.basicConfig(
    level=logging.DEBUG,
    format='%(levelname)-8s %(name)s: %(message)s'
)

logger = logging.getLogger(__name__)

logger.debug("loop iteration %d, value=%r", i, val)
logger.info("processing complete: %d items", count)
logger.warning("retrying after timeout")
logger.error("failed to write output: %s", e)
logger.critical("database unreachable, shutting down")
Why use logging instead of print? print() always outputs and cannot be filtered or redirected easily. A logger.debug() call costs almost nothing when the level is set to WARNING — the message is never formatted. When you need detail, turn the level down; when you want silence, turn it up. No code changes needed.

Rule of thumb

  • In production: set level to INFO or WARNING. Operators see milestones and problems without noise.
  • While debugging: set level to DEBUG. See everything.
  • In libraries: always use logging.getLogger(__name__) — never basicConfig. Let the application decide the level.

Logging in Java and C

The same five-level model exists across languages. The API differs, but the concept — filter by severity without touching the log call sites — is identical.

Java — the standard is SLF4J with a backend such as Logback. The five levels map directly: trace (≈ DEBUG detail), debug, info, warn, error.

// SLF4J (most common Java logging API)
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger logger =
    LoggerFactory.getLogger(MyClass.class);

logger.debug("loop iteration {}, value={}", i, val);
logger.info("processing complete: {} items", count);
logger.warn("retrying after timeout");
logger.error("failed to write output", e);

C has no built-in logging framework. The minimal convention is to write diagnostic output to stderr (so it stays separate from program output on stdout) and use a severity prefix in the message. Larger C projects adopt libraries such as log.c that add level filtering.

/* minimal C logging to stderr */
#include <stdio.h>

fprintf(stderr, "[DEBUG] loop iteration %d, value=%d\n", i, val);
fprintf(stderr, "[ERROR] failed to open file: %s\n", path);

/* syslog -- for system daemons on Linux/macOS */
#include <syslog.h>
openlog("myapp", LOG_PID, LOG_DAEMON);
syslog(LOG_DEBUG,  "loop iteration %d", i);
syslog(LOG_ERR,    "failed to open file: %s", path);
