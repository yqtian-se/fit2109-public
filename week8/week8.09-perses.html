8.9 Perses: Automated Program Reduction

Creating an MRE manually works well for small programs. For a 500-line script with dozens of functions, the manual process is tedious and error-prone. Perses automates it: you provide the buggy program and a test that checks whether the bug is present, and Perses systematically removes code while keeping the test passing.

How Perses works

Perses uses the grammar of the programming language to guide its reductions. Rather than deleting arbitrary bytes, it removes syntactically valid units — statements, expressions, function bodies — so the reduced output is always a valid program. This is the key advantage over simpler line-deletion tools like creduce: Perses never produces broken syntax that wastes a test run.

The algorithm is a variant of delta debugging:

  1. Start with the original buggy program.
  2. Try removing a chunk of code. Run the test script on the result.
  3. If the bug is still present (test exits 0), keep the removal and continue.
  4. If the bug is gone (test exits non-zero), restore the removed chunk and try a different one.
  5. Repeat until no further removal preserves the bug.

Step 1 — Prerequisites: install Java

Perses is distributed as a self-contained JAR file and requires Java 11 or later. Check whether Java is installed:

$ java --version
openjdk 21.0.2 2024-01-16

If the command is not found, install Java first:

# macOS (via Homebrew)
$ brew install openjdk

# Ubuntu / Debian
$ sudo apt install default-jdk

Step 2 — Download the Perses JAR

Go to the Perses releases page on GitHub and download the latest perses_deploy.jar. Save it somewhere permanent — you will reuse it across projects.

# Or download directly from the terminal
$ curl -L -o perses_deploy.jar \
    https://github.com/uw-pluverse/perses/releases/latest/download/perses_deploy.jar

# Confirm it works
$ java -jar perses_deploy.jar --help

Step 3 — Prepare the buggy file

Start with the simplest reproduction you have — the file Perses will reduce further. Save the following as big_bug.py:

# big_bug.py
import os, sys

def load_config():
    return {"host": "localhost", "port": 5432}

def get_users():
    return ["alice", "bob", "carol"]

def process(users):
    for i in range(len(users) + 1):   # off-by-one bug
        print(users[i])

if __name__ == "__main__":
    load_config()
    process(get_users())

Step 4 — Write the test script

The test script is the heart of the process. After each reduction attempt, Perses copies your input file and test script into a temporary directory, sets the working directory there, and calls bash test.sh with no arguments. Your script must reference the input file by its literal filename — not via $1.

Do NOT use $1 — reference the file by name A common mistake is writing python3 "$1". Perses passes no argument, so $1 is empty and Python fails silently. Use the filename directly: python3 big_bug.py.
Exit code convention is reversed from normal shell Exit 0 means the bug is still present — Perses should keep reducing. Exit non-zero means the bug is gone — stop this path. This is the opposite of normal shell conventions. 
#!/bin/bash
# test.sh — exit 0 if big_bug.py still triggers IndexError
# Do NOT use $1 — Perses sets CWD to the candidate dir and passes no argument.
python3 big_bug.py 2>&1 | grep -q "IndexError"
# grep -q exits 0 when the pattern is found  (bug present → keep reducing)
# grep -q exits 1 when the pattern is absent (bug gone   → stop this path)

Make it executable and verify it works before handing it to Perses:

$ chmod +x test.sh
$ bash test.sh && echo "bug confirmed"
bug confirmed

Step 5 — Run Perses

Use absolute paths for both flags — Perses changes directories internally and relative paths can silently fail:

$ java -jar perses_deploy.jar \
    --test-script "$(pwd)/test.sh" \
    --input-file "$(pwd)/big_bug.py"

INFO  Language: PYTHON
INFO  Removed 50 token(s). Reduction ratio is 43/93=46.24%
$ cat perses_result/big_bug.py
def a():
    return ""
def b(a):
    for b in range(1):
        a[b]
b(a())

Perses stripped all imports and reduced variable names — the logic that triggers IndexError is preserved in minimal form.

Test scripts for Java and C

The same rule applies: reference the input file by its literal name, not $1.

#!/bin/bash
# Java: exit 0 if Repro.java still throws ArrayIndexOutOfBoundsException
javac Repro.java 2>/dev/null || exit 1
java Repro 2>&1 | grep -q "ArrayIndexOutOfBoundsException"
#!/bin/bash
# C: exit 0 if crash.c still produces a segfault
gcc -g -o /tmp/repro crash.c 2>/dev/null || exit 1
/tmp/repro 2>/dev/null
[ $? -eq 139 ]   # 139 = 128 + SIGSEGV(11)

Useful flags

FlagWhat it does
--input-file FILEThe buggy file to reduce.
--test-script SCRIPTThe test script (must be executable).
--output-dir DIRWhere to write the result (default: perses_result/).
--threads NRun N tests in parallel — speeds up reduction on multi-core machines.
--keep-original-code-formatPreserve original whitespace and formatting in the output.

Perses automatically selects the grammar based on the file extension and supports Python, C, C++, Java, Go, Rust, JavaScript, and more.

When to use Perses vs manual reduction Use Perses when the buggy file is more than ~50 lines or when you need to attach a minimal test case to a formal bug report. For shorter files, manual reduction is faster. Perses shines on compiler crashes, parser bugs, or any situation where stripping code by hand would take more than 10 minutes.

Troubleshooting: "initial sanity check failed"

This is the most common error when running Perses for the first time. The error message looks like:

SEVERE The initial sanity check failed.
* The script exit code is ExitCode(intValue=1)
* #interesting: 0, #uninteresting: 6

It means Perses ran your test script and it returned exit code 1 every time — telling Perses the bug is not present. Perses refuses to start because there is nothing to reduce. Work through this checklist:

1. Using $1 in the test script — the most common mistake Perses does not pass the candidate file as an argument. It copies the file into a temp directory, sets CWD there, and calls bash test.sh with no arguments. If your script uses python3 "$1", $1 is empty and Python fails silently — Perses sees exit code 1 and refuses to start. Fix: use the filename directly. 
# Wrong — $1 is always empty
python3 "$1" 2>&1 | grep -q "IndexError"

# Correct — reference the file by its literal name
python3 big_bug.py 2>&1 | grep -q "IndexError"
2. Use absolute paths when calling Perses Perses changes directories internally. Relative paths for --test-script and --input-file can silently fail. Always use $(pwd)/: 
java -jar perses_deploy.jar \
    --test-script "$(pwd)/test.sh" \
    --input-file "$(pwd)/big_bug.py"
3. Verify the test script manually before running Perses Always run the test script yourself first from the same directory as the buggy file. If this command does not print "bug confirmed", Perses will fail: 
$ bash test.sh && echo "bug confirmed" || echo "FAIL: bug not detected"
Fix the test script first; only then run Perses.
4. CRLF line endings (Windows / WSL users) If you created or edited test.sh on Windows — including in WSL with a Windows editor — the file likely has \r\n line endings instead of Unix \n. Bash silently fails to execute such scripts, causing Perses's sanity check to always return exit code 1. Fix: 
# Option 1: use dos2unix
$ dos2unix test.sh

# Option 2: use sed if dos2unix is not installed
$ sed -i 's/\r//' test.sh

# Confirm: file should say "ASCII text", not "CRLF"
$ file test.sh
5. Python command not found The test script uses python3. On some systems the command is python instead. Check: 
$ python3 --version   # if this fails, use python instead
$ which python3
Edit test.sh and replace python3 with the correct command for your system.
6. Test script not executable Perses requires the test script to be executable. If you forgot this step: 
$ chmod +x test.sh
$ ls -la test.sh   # should show -rwxr-xr-x
7. Wrong error string in grep The grep -q "IndexError" pattern must exactly match what Python prints. Run the buggy file directly and check the output: 
$ python3 big_bug.py 2>&1
Traceback (most recent call last):
  ...
IndexError: list index out of range
# Confirm grep matches it:
$ python3 big_bug.py 2>&1 | grep "IndexError"
If grep produces no output, the pattern does not match — update the string in test.sh to match the actual error text.
