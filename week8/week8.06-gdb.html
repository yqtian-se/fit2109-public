8.6 GDB and LLDB: Inspecting Native Programs

When a C or C++ program crashes, you often get little more than "Segmentation fault". A debugger lets you run the program under controlled conditions, pause at any point, and inspect every variable and the full call stack at the moment of failure.

GDB (GNU Debugger) is the standard on Linux. LLDB is part of the LLVM project and is the default debugger on macOS, but it also runs on Linux and other platforms where LLVM is available. Their commands are nearly identical — the differences are noted below.

Step 0: compile with debug symbols

Without debug symbols, a debugger can only show raw memory addresses, not line numbers or variable names. Always add -g when compiling code you plan to debug:

$ gcc -g -o crash crash.c   # -g embeds line numbers and variable names
-g and optimisation don't mix well If you also pass -O2 or higher, the compiler reorders and eliminates code, making the debugger show unexpected line numbers. For debugging, use -g alone or with -O0 (no optimisation).
Side note — -g can itself introduce bugs Adding -g does more than embed line numbers — it changes the information available to the compiler, which can subtly alter code generation and trigger latent compiler bugs that are otherwise invisible. In other words, a crash that appears only with -g may be a compiler bug, not a bug in your code.

This phenomenon is studied in Compilation Consistency Modulo Debug Information (ASPLOS 2023), which systematically shows how debug-information generation can interact with compiler optimisation passes and produce miscompilations. If you ever encounter a bug that disappears when you remove -g, this is the likely explanation — and it is worth filing a compiler bug report.

Essential GDB and LLDB commands

GDBLLDBWhat it does
gdb ./crashlldb ./crashStart the debugger with your program.
break mainb mainSet a breakpoint at the start of main.
break crash.c:12b crash.c:12Set a breakpoint at line 12 of a specific file.
runrunStart (or restart) the program.
nextnextExecute the next line, stepping over function calls.
stepstepExecute the next line, stepping into function calls.
continuecontinueResume running until the next breakpoint or crash.
print totalp totalPrint the current value of a variable.
backtracebtShow the full call stack at the current pause point.
frame 1frame select 1Move to frame 1 in the call stack to inspect its locals.
listlistShow the source code around the current line.
quitquitExit the debugger.

Typical crash investigation session

$ gdb ./crash
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x000000000040115a in fill_array (arr=0x0, n=10) at crash.c:8
8           arr[i] = i * 2;
(gdb) backtrace
#0  fill_array (arr=0x0, n=10) at crash.c:8
#1  main () at crash.c:17
(gdb) frame 1          # jump to the calling frame
(gdb) print arr        # arr is NULL -- malloc was never called
$1 = (int *) 0x0
First command after a crash: backtrace Run backtrace (or bt) the moment your program crashes inside the debugger. It shows exactly where you were and the full chain of calls that got you there — the single most useful piece of information you can collect.
Try this Write a small C program that dereferences a NULL pointer (e.g. int *p = NULL; *p = 1;). Compile with gcc -g, run it under GDB, let it crash, then run backtrace and print p to confirm the cause.
