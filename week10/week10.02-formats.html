10.2 Common Data Formats in Practice

The first step in wrangling is recognising what you actually have. Three formats cover a huge share of everyday work: plain text, CSV, and JSON. All three are text, but they behave differently enough that you should not treat them as interchangeable.

Plain text: structure by convention

A log file is the classic line-oriented example. There is no schema file, but there is an informal pattern — a timestamp, a severity, then key=value details — and that consistency is enough for ordinary text tools to exploit:

2026-10-01 09:00:01 INFO  user=alice action=login
2026-10-01 09:00:05 ERROR user=bob code=503
2026-10-01 09:00:09 WARN  user=alice retry=1

CSV: deceptively simple

CSV looks more structured. RFC 4180 documents the common form: records separated by line breaks, fields by commas, with quoting rules so that commas, quotes, and even line breaks can appear inside a field.

date,customer,category,amount
2026-10-01,"ACME, Inc.",hardware,1250.00
2026-10-02,Globex,software,799.00

At a glance this is trivial to split on commas — until you reach "ACME, Inc.". That comma is part of the customer name, not a separator. Splitting on every comma is therefore unsafe for general CSV, and this is why CSV is easy right up until real-world quoting appears.

CSV has dialects RFC 4180 is an informational description of common practice, not a strict standard that every exporter follows. In the wild you will meet tab-separated files (TSV), semicolon-separated files (common in locales where the comma is the decimal mark), files with a byte-order mark at the start, and files whose header row is missing. Always look before you parse.

JSON: a tree, not lines

RFC 8259 defines JSON as a lightweight, text-based, language-independent data-interchange format built from objects, arrays, strings, numbers, booleans, and null.

{
  "orders": [
    {"id": 101, "status": "pending", "total": 49.95},
    {"id": 102, "status": "shipped", "total": 99.50}
  ]
}

JSON is not naturally line-oriented. The useful questions are structural: "what is orders[0].status?" or "how many objects in orders have status == "pending"?" Tools such as jq are designed around exactly that. The same document could be written on one line or fifty and mean the same thing — which is precisely why line-based tools are the wrong fit.

Inspect before you process

A good diagnostic habit is to look at the format first, using a command that suits it:

$ head app.log
$ head -n 3 sales.csv
$ jq '.' orders.json

jq '.' is the JSON equivalent of head: the identity filter . validates the file (it fails loudly if the JSON is broken) and pretty-prints it so nested structure is easy to read.

Try this Create the three-line CSV above as sales.csv, then run cut -d',' -f2 sales.csv and read the output carefully. What happens to the customer name ACME, Inc.? We come back to this in 10.7.
