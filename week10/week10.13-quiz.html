Quiz — 10 questions

10.13 Check Your Understanding

These questions check concepts, not syntax recall. Think through each one — and commit to an answer — before opening the answer key at the bottom.

Question 1
orders.json is a minified API response: the whole document is on a single line, shaped like {"orders":[{"id":101,"status":"pending",…},…]}. Which command lists only the orders whose status is pending?
Question 2
A row of sales.csv is 2026-10-01,"ACME, Inc.",hardware,1250.00. What does cut -d',' -f2 print for that row?
Question 3
You run awk '{print $3}' app.log | uniq -c and get six lines, with ERROR and INFO each listed more than once, instead of one line per severity. What is the problem?
Question 4
On a larger log, grep -c ERROR app.log reports 5, but awk '$3=="ERROR"' app.log | wc -l reports 4. What is the most likely explanation?
Question 5
You open an exported CSV and every é shows as �. file --mime-encoding reports iso-8859-1. What is the best next step?
Question 6
What does echo '<b>x</b> <b>y</b>' | sed -E 's/<.*>//' print?
Question 7
sed -E 's/.*code=([0-9]+).*/\1/' app.log prints the status codes, but also prints the full INFO and WARN lines unchanged. How do you print only the extracted codes?
Question 8
You import nums.csv into SQLite with .mode csv and .import, letting SQLite create the table. The file is a header v followed by the values 9, 10, and 100. What order does SELECT v FROM nums ORDER BY v return?
Question 9
What does echo '[{"id":1,"total":5},{"id":2}]' | jq -c '[.[].total]' print?
Question 10
A script runs grep ERROR "$1" | sort | uniq -c and is given a file name that does not exist. grep prints an error message. Without set -o pipefail, what exit status does the pipeline report, and why?
Answer key — open only after committing to your answers
  1. jq '.orders[] | select(.status=="pending")' orders.json, because it selects objects by the value of a key
    JSON is a tree, not a list of lines: the same data could be written on one line or fifty and mean the same thing. Here the whole document is one line, so grep pending prints the entire document, every order included. cut splits that line at commas and would show only a fragment such as the first order's "status":"pending", and sed 's/pending//' prints the whole document with the word deleted. jq steps through each order in the array and keeps those whose status equals "pending" (10.2, 10.8).
  2. "ACME
    cut splits at every comma, including the one inside the quoted name, so field 2 is the first half of the name along with its opening quote. The most dangerous part is that there is no error: the output looks plausible and any total built on it is quietly wrong. This is exactly why real CSV needs a CSV-aware tool (Miller, SQLite, or a CSV library) instead of comma-splitting (10.7).
  3. uniq only collapses adjacent duplicates, so the input needs sort first
    uniq -c counts runs of identical neighbouring lines. In the unsorted stream INFO, ERROR, WARN, ERROR, ERROR, INFO, ERROR, the only adjacent pair is the two ERROR lines in the middle, so you get six separate runs instead of three totals. sort brings equal values together, and then uniq -c has something to count. That is why the idiom is always sort | uniq -c (10.7, 10.10).
  4. One line has ERROR somewhere other than the third field, such as in a user name, and grep matches it anywhere
    grep ERROR is a substring search over the whole line, so a line like INFO user=ERROR_handler started counts. The awk pattern $3=="ERROR" tests only the severity field, for an exact match. When a value lives in a particular field, test the field. awk does not skip lines, and grep -c counts each matching line once (10.4, 10.6).
  5. Convert it with iconv -f ISO-8859-1 -t UTF-8 and use the converted copy
    The file is syntactically fine; the bytes are just not UTF-8, so a tool that assumes UTF-8 shows a replacement character. Converting once, to a new file, makes everything downstream consistent and keeps the original intact. Remember that file only guesses the encoding, so check that accented names look right after converting. jq is for JSON, not for repairing encodings (10.3).
  6. An empty line
    .* is greedy: it matches as much as it can. The pattern <.*> therefore starts at the first < and runs to the last > in the line, so the substitution removes everything and leaves an empty line. To strip each tag individually, use a negated class such as s/<[^>]*>//g, which stops at the nearest > and produces x y (10.5).
  7. Add -n and end the substitution with p
    sed prints every line by default, whether or not the substitution matched, which is why the INFO and WARN lines come through untouched. -n switches off that automatic printing, and the p flag prints a line only when the substitution succeeded. The g flag is about repeated matches within one line, and -i would edit the original file, which is not what you want here (10.5).
  8. 10, 100, 9, because the columns were created as text
    When .import creates the table, every column is TEXT, and text compares character by character: 1 sorts before 9, so 10 and 100 come first. Use ORDER BY CAST(v AS INTEGER) or declare the column type before importing. Nothing fails, which is what makes this trap easy to miss (10.9).
  9. [5,null]
    Asking jq for a key an object does not have gives null rather than an error. That is convenient, but it means a missing key can slip into a result unnoticed, and an object lacking a key can be silently dropped by select. When completeness matters, check with has("total") or supply a default with // (10.3, 10.8).
  10. Zero, because a pipeline reports the exit status of its last command
    grep does print an error and exit non-zero (it does not ignore the missing file), but sort and uniq then run on empty input and exit 0, and by default 0 is what the pipeline reports. A script using set -e alone would carry on, producing an empty report that looks successful. set -o pipefail makes the pipeline fail if any stage fails (10.11).
