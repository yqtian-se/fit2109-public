10.1 What Is Data Wrangling?

In software and systems work, raw data is rarely ready to use. Log files are full of noise, CSV exports mix useful values with missing or inconsistent fields, and a JSON response often contains far more structure than you need to answer one question. Data wrangling is the process of turning that raw material into something that answers a real question: filtering out irrelevant records, extracting the fields that matter, repairing common problems, and summarising the result.

The aim is not just to "clean data". It is to produce information that supports debugging, monitoring, reporting, or a decision — and to produce it in a way you (and someone else) can check and repeat.

Three files, three different questions

Suppose three files arrive from different parts of one system:

FileShapeQuestion you want answeredNatural tools
app.logLine-oriented textHow many ERROR lines occurred today?grep, sed, awk, sort, uniq
sales.csvRows and columns, with quoting rulesWhich product category earns the most revenue?cut/awk if simple; a CSV-aware tool or SQL if not
orders.jsonNested objects and arraysWhich orders are still pending?jq

These are all data-wrangling tasks, but they call for different tools because they have different shapes. A log is lines; a CSV is a table; JSON is a tree. The core skill is matching the processing model to the format in front of you rather than forcing every file through one favourite tool.

The four recurring stages

For app.log, that might be: look at the first few lines with head; keep error lines with grep; pull out one field with awk; count repeated values with sort | uniq -c. For sales.csv: check the header and quoting, select columns, convert types if needed, then aggregate. For orders.json: pretty-print it, extract the relevant keys, then count or group. The tools change; the thinking pattern does not.

Real data is messy by default

Even when a file is technically well-formed, the data in it may be hard to use. Text can arrive in an unexpected encoding, dates can appear in several formats, identifiers can be inconsistent, and a missing value can be an empty string, NULL, N/A, or simply an absent key. A good wrangling workflow treats these as normal rather than exceptional: inspect carefully, make your assumptions explicit, and pick tools that match the structure of the data.

Why the command line? Small tools that each do one job, joined by pipes, let you test one step at a time, see every intermediate result, and rerun the whole thing later. That is what makes a wrangling result trustworthy, not just fast. You met pipes in Week 1; this week they become an analysis technique.
