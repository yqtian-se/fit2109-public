10.10 Summarising and Reporting Results

Wrangling is only useful if it ends in a result a person can interpret: a count, a grouped total, a top-N list, a filtered extract, or a compact report. The command line is strong here because the same small tools that did the extraction extend naturally into summarisation. sort | uniq -c counts lines; awk accumulates totals; jq emits selected fields; SQL handles relational summaries.

The counting pattern, and choosing what to count

Suppose you want the most frequent error code in app.log. A pipeline built from tools you have now met:

$ awk '$3 == "ERROR" {print $5}' app.log | sort | uniq -c | sort -nr
   3 code=503
   1 code=504
  1. awk narrows to ERROR records and extracts the one field to group on.
  2. sort clusters identical values together.
  3. uniq -c counts each cluster.
  4. sort -nr orders the counts numerically, largest first.

Each step is easy to explain and inspect, which makes the report easier to trust. Add | head -n 3 for a top-3 list.

Common trap — grouping on the wrong thing The pattern only counts what you put into sort. If you strip the timestamp and group on the whole remaining line, the user name is still part of every line: 
$ grep ERROR app.log | sed -E 's/^[0-9-]+ [0-9:]+ ERROR //' |
    sort | uniq -c | sort -nr
   1 user=erin code=503
   1 user=dave code=503
   1 user=carol code=504
   1 user=bob code=503
Every line is "unique", so every count is 1 and the report says nothing. The grouping key has to be the thing you actually want to count — here, the code. Always ask "what is the unit I am counting?" before you write the pipeline.

Grouped totals

For tabular data a summary usually means grouped totals. With sales.csv loaded into SQLite (10.9), revenue by category is one readable query — clearer and safer than reproducing the same logic with fragile shell parsing:

SELECT category, ROUND(SUM(amount), 2) AS total_revenue
FROM sales
GROUP BY category
ORDER BY total_revenue DESC;

The point is not that everything must stay as plain text all the way through. It is that your pipeline can move between tools — CSV imported, queried, exported again — while staying reproducible.

Changing representation

Reporting often means converting between shapes: nested JSON in, a compact table out.

$ jq -r '.orders[] | select(.status=="pending") |
    [.id, .total] | @csv' orders.json
101,49.95
103,15.00
104,220.00

A summary can quietly change the data it reports, so know what your tools do to values on the way through. @csv quotes strings but leaves numbers bare, and number formatting can differ between jq versions (older releases print 15.00 as 15). If the exact format matters to your reader, check the output — or round and format explicitly with SQL ROUND or printf.

State your assumptions

A good report states, at least implicitly, the decisions behind it. Did you ignore malformed rows? Skip the CSV header? Treat blank values as missing? Assume UTF-8? The more real the dataset, the more these decisions matter — and a one-line command can encode all of them. Comments and command history are valuable for this reason: they turn "something I typed once" into a repeatable workflow.
