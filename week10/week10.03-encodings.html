10.3 Encodings, Line Endings, and Schemas

A data format tells you how data is represented. A schema tells you what the fields are expected to mean: column names, value types, which fields are required or optional, and sometimes constraints such as "this must be unique" or "this must be a date". CSV does not enforce a schema, and neither does JSON — RFC 8259 says what counts as valid JSON, not which keys any particular dataset must contain. That gap is why schema thinking matters: it separates a file that is syntactically valid from a dataset that is usable.

Valid format, doubtful data

Consider this CSV:

date,customer,amount
2026-10-01,ACME,1250.00
01/10/26,Globex,799
,Initech,500.00

Every parser will read it, but the data quality is already questionable: the date format is inconsistent (and 01/10/26 is ambiguous — 1 October, or 10 January?), one row has no date, and the amounts mix decimal styles. None of these are CSV syntax problems; they are data-quality problems, and a parser will happily accept them while your analysis quietly becomes misleading.

You can find such rows with the same tools you will use for analysis. Here is a quick check for rows whose date is missing or not in YYYY-MM-DD form:

$ awk -F, 'NR>1 && $1 !~ /^[0-9]{4}-[0-9]{2}-[0-9]{2}$/ {print NR": "$0}' \
    messy.csv
3: 01/10/26,Globex,799
4: ,Initech,500.00
Fun fact The ISO 8601 form YYYY-MM-DD is not just unambiguous — it also sorts correctly as plain text, because the biggest unit comes first. That is why log files and filenames use it, and why sort works on dates without any date parsing.

Encodings

A second major source of trouble is encoding: how characters are stored as bytes. UTF-8 is the dominant encoding today; it preserves the full ASCII range while supporting far more characters. But not every file you receive is UTF-8. If a file was exported as Windows-1252 or ISO-8859-1 and you read it as UTF-8, accented characters come out as � or other garbage.

First diagnose the encoding, then convert it. file makes an educated guess; iconv converts between encodings, with -f for the input encoding and -t for the output encoding:

$ file --mime-encoding raw.csv
raw.csv: iso-8859-1
$ iconv -f WINDOWS-1252 -t UTF-8 raw.csv > cleaned.csv
$ cat cleaned.csv
name
José

iconv is only as good as your knowledge of the original encoding, and file is a guess, not a guarantee — but the principle matters: some wrangling happens before any filtering or summarising, simply to make the text readable and consistent.

Two invisible troublemakers

  • Windows line endings (CRLF). A file exported on Windows ends each line with \r\n. The invisible \r becomes part of the last field on every line, so comparisons that look correct silently fail. Check with file; fix with tr -d '\r' (or dos2unix where installed).
  • A byte-order mark (BOM). Some exporters put three invisible bytes at the very start of a UTF-8 file. The first header then reads \xEF\xBB\xBFdate rather than date, so a lookup by column name mysteriously fails.
$ file crlf.csv
crlf.csv: ASCII text, with CRLF line terminators
$ awk -F, 'NR==2 {print ($2=="ERROR") ? "match" : "NO MATCH"}' crlf.csv
NO MATCH
$ tr -d '\r' < crlf.csv |
    awk -F, 'NR==2 {print ($2=="ERROR") ? "match" : "NO MATCH"}'
match

The same issue in JSON

A JSON document can be perfectly valid and still awkward: keys present in some objects and absent in others, numbers sometimes written as strings, nested arrays that appear only for certain records. Nothing in the format guarantees every object in an array has the same shape, so inspect a few representative records before you write a pipeline.

Two separate questions

Always ask both, and keep them apart:

  1. Can my tools parse this file? — syntax and encoding.
  2. Is the data consistent enough for the question I want to answer? — schema and quality.

A "yes" to the first says nothing about the second. Good wrangling needs both.
