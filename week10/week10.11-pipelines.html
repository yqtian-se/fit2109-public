10.11 Designing Reliable Data-Wrangling Pipelines

A good pipeline is not just a clever chain of commands. It is a sequence of steps whose purpose is understandable, whose assumptions are visible, and whose output can be checked. That matters because data wrangling usually fails quietly: a wrong delimiter assumption, an encoding mismatch, a header row counted as data, or a regex that matches more than intended all produce plausible-looking output. The best defence is to build the pipeline incrementally and verify each stage before trusting the end.

The command line makes this practical: each tool reads standard input and writes standard output, so every intermediate result can be inspected. sed is literally a stream editor and jq is documented as filter-based JSON processing — both reinforce the pipeline mindset.

A reliable workflow

  1. Inspect a small sample (head, jq ., file).
  2. Write the simplest working extraction.
  3. Validate the intermediate output — does it look the way you expected?
  4. Add transformation and summarisation one step at a time.
  5. Rerun on the full dataset, and sanity-check the totals.
  6. Save it as a script if it is worth repeating.

For a CSV export, do not begin with a ten-stage pipeline. Look at the header and check whether quoting is present. If the file is simple, cut and awk are fine; if not, switch early to Miller or SQLite rather than patching around CSV complexity with a fragile regex. This is not tool purity — it is reliability.

Build up, checking as you go

# 1. does the filter keep the right lines?
$ grep ERROR app.log | head -n 3

# 2. does the extraction give codes?
$ grep ERROR app.log | awk '{print $5}' | head -n 3
code=503
code=504
code=503

# 3. now summarise:
$ grep ERROR app.log | awk '{print $5}' | sort | uniq -c | sort -nr
   3 code=503
   1 code=504

If step 2 had printed the wrong column, you would have found out one command in, not after a ten-stage pipeline had produced a confident wrong answer.

Match the pipeline to the data's structure

Consider: "How many pending orders are there per customer city, from a JSON API dump?" A sensible pipeline stays structure-aware as long as it can:

  1. Inspect with jq '.' orders.json.
  2. Extract just what you need with jq (.customer.city of each pending order).
  3. Once the result is flat, hand it to sort | uniq -c — or import it into SQLite if you need richer grouping.

That is much safer than forcing the original JSON through line-oriented tools immediately. Conversely, "which error code appears most often this week?" can stay in text tools the whole way. Reliability starts with matching the pipeline to the structure.

Validate early, fail loudly

Syntax validity and analytical usefulness are not the same, so validation is a first stage, not an afterthought. Some cheap checks:

# does it parse at all?
$ jq empty orders.json && echo "valid JSON"

# is the header what I expect?
$ head -n 1 sales.csv

# rows with the wrong field count (simple CSV):
$ awk -F, 'NF != 3 {print NR": "$0}' scores.csv

# duplicated lines:
$ sort sales.csv | uniq -d
Common trap — a pipeline reports only its last command By default, the exit status of a pipeline is the exit status of its last command. If the first command fails, the pipeline can still "succeed": 
$ grep ERROR nope.log | sort | uniq -c
grep: nope.log: No such file or directory
$ echo $?
0
An empty report and an exit status of 0: a script would carry on as if nothing was wrong. In a script, add set -o pipefail (with set -eu) so a failure anywhere in the pipeline fails the whole thing — the reliable-scripts habits from Week 2 (2.10).

Design for re-running

A pipeline you expect to use again belongs in a commented script, so that when next week's data differs slightly you know exactly where to adjust. Here is the error-code report from 10.10 as a small script, with an argument check, a readability check, and the field layout documented:

#!/usr/bin/env bash
# error-report.sh — count ERROR lines per status code in a log
set -euo pipefail

log="${1:?usage: error-report.sh app.log}"
[ -r "$log" ] || { echo "cannot read $log" >&2; exit 1; }

# fields: 1=date 2=time 3=LEVEL 4=user=... 5=code=...
awk '$3 == "ERROR" { print $5 }' "$log" | sort | uniq -c | sort -nr
$ ./error-report.sh app.log
   3 code=503
   1 code=504
$ ./error-report.sh nope.log
cannot read nope.log
$ echo $?
1

Prefer transparency over cleverness. A five-step pipeline you can explain is usually better than a one-liner nobody understands — including your future self. Data wrangling in the shell is powerful not because it is obscure, but because it lets you assemble understandable steps that can be rerun, inspected, revised, and shared.
