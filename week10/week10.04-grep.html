Tool focus: grep

10.4 Filtering and Extracting Text with grep

When data is mostly line-oriented text, regex-based tools are often the fastest way to start pulling signal out of noise. You met grep and regular expressions in Week 2 (2.5) and 2.6; here we use them as the filter/extract stage of a wrangling pipeline. A regular expression is a pattern describing a set of strings. grep understands basic (BRE) and extended (ERE) regular expressions, and grep -E is the everyday choice because +, ?, |, and parentheses work without extra backslashes.

We use the seven-line app.log from 10.1:

2026-10-01 09:00:01 INFO  user=alice action=login
2026-10-01 09:00:05 ERROR user=bob code=503
2026-10-01 09:00:09 WARN  user=alice retry=1
2026-10-01 09:00:13 ERROR user=carol code=504
2026-10-01 09:00:20 ERROR user=dave code=503
2026-10-01 09:00:31 INFO  user=bob action=login
2026-10-01 09:00:42 ERROR user=erin code=503

Start simple, then extend

Begin with the most readable pattern that answers the question; resist the cleverest regex first.

$ grep 'ERROR' app.log                  # the matching lines
$ grep -c 'ERROR' app.log                 # how many? (count, not the lines)
4
$ grep -nE 'ERROR|WARN' app.log           # either level, with line numbers
2:2026-10-01 09:00:05 ERROR user=bob code=503
3:2026-10-01 09:00:09 WARN  user=alice retry=1
4:2026-10-01 09:00:13 ERROR user=carol code=504
5:2026-10-01 09:00:20 ERROR user=dave code=503
7:2026-10-01 09:00:42 ERROR user=erin code=503

The first of our three questions — how many ERROR lines? — is already answered by grep -c.

The flags that matter for wrangling

FlagEffectWrangling use
-cPrint the number of matching linesQuick counts
-nPrefix each match with its line numberLocating a problem in a long file
-vInvert: keep lines that do not matchDropping noise (grep -v INFO)
-oPrint only the matched part, not the whole lineExtracting a value
-EExtended regular expressions|, +, {n}, groups
-iIgnore caseInconsistent capitalisation

-o combined with a counting pipeline turns grep into an extractor:

$ grep -oE 'code=[0-9]+' app.log | sort | uniq -c | sort -nr
   3 code=503
   1 code=504

Anchors and classes as validation

Anchors and character classes let you test the structure of your data, not only search it. ^ anchors to the start of a line, [0-9] matches a digit, and {4} or {2} set repetition counts. To confirm every line starts with a date, count the lines that do not:

$ grep -vcE '^[0-9]{4}-[0-9]{2}-[0-9]{2}' app.log
0

A result of 0 says the file has the structure you assumed. Any other number tells you where to look next.

Common trap — a pattern that matches too much grep 'ERROR' app.log matches the text ERROR anywhere in a line. A line such as INFO user=ERROR_handler started would be counted as an error even though its level is INFO. When the severity is a specific field, test that field instead — with awk '$3=="ERROR"' (see 10.6) — or anchor your pattern to the right position.
Portability grep -P (Perl-compatible regular expressions) exists in GNU grep but is not available in every grep you will meet — macOS ships a different one. Stick to -E for scripts you want to run on both your laptop and a Linux server.

Regex tools work best when your patterns stay readable, you test them incrementally, and you stop using them when the data becomes too structurally rich for line-based assumptions. For extracting and rewriting parts of a line, the next step is sed.
