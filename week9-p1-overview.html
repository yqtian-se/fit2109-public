Week 9: Profiling & Performance

Pre-reading · FIT2109 · Monash University

"Premature optimization is the root of all evil." — Donald Knuth, 1974

By the end of this week you should be able to

  1. Explain the difference between benchmarking and profiling, and choose the right tool for each question.
  2. Measure execution time reliably with time and timeit, accounting for variability and warm-up effects.
  3. Use cProfile to identify which function consumes the most CPU time.
  4. Use line_profiler to pinpoint the specific line inside a hot function.
  5. Measure peak memory usage with memory_profiler and apply generator-based fixes.
  6. Apply the optimise → measure → verify loop, and evaluate trade-offs between performance, readability, and correctness.

A scenario

Your data-processing script is correct — the output matches the expected results. But it takes 3 hours to run on the full dataset, while your teammate's version finishes in 4 minutes. You assume the bottleneck is the file I/O, so you rewrite the loading logic. Still 2.7 hours. You try caching some results. Still 2.5 hours. Forty minutes of changes, barely any improvement.

You run a profiler for the first time. It tells you that 94% of the runtime is spent in a single function — one you never considered. Inside that function, a line that checks if item in results_list is called a million times. The list has 50,000 entries; each check scans the whole thing. Replacing it with a set is a one-line change. Runtime drops to 11 minutes.

This is what profiling reveals: not what you think is slow, but what actually is slow. This week gives you the tools to measure time and memory precisely, find the real bottleneck, apply a targeted fix, and verify the improvement is real.

Concept check — before you start Think of a program you have written that felt slow. Where did you assume the bottleneck was? After reading this week's material, run a profiler on it and see whether your assumption was correct.
