8.5 Reproduce Before You Fix

The most important rule in debugging: never attempt a fix until you can trigger the bug on demand. A bug you cannot reproduce reliably is a bug you cannot fix reliably. If you change code and the bug disappears, you have no idea whether you fixed it or whether it simply didn't trigger this time.

What "reproducing" means

To reproduce a bug, you need to capture three things:

  1. Exact inputs — the specific data, files, or user actions that trigger it.
  2. Environment — OS, Python version, library versions, environment variables, working directory.
  3. Steps — the precise sequence of commands or actions, in order.

Write this down as if you were filing a bug report. The act of writing it often reveals the cause.

Intermittent bugs If the bug happens only sometimes, look immediately for timing, ordering, or concurrency issues. Race conditions, file system delays, and random seeds are common culprits. Add logging around the suspected area and run many times to capture the failure.

Isolating with binary search

Once you can reproduce the bug, isolate where it lives by dividing the code in half repeatedly — the same principle as binary search on a sorted list.

Imagine your program has a pipeline of functions: A → B → C → D → crash. You don't know which step introduces the bad state. Binary search:

  1. Check the output of B — is the data correct here? If yes, the bug is in C or D.
  2. Check the output of C — wrong! The bug is inside C.
  3. You have narrowed 4 functions down to 1 in two steps.
# Quick isolation with a temporary print
def process(data):
    step1 = transform(data)
    print("after transform:", step1)   # is this what I expect?
    step2 = filter_records(step1)
    print("after filter:", step2)         # still correct?
    return aggregate(step2)
Git bisect for large codebases If a bug appeared in a recent commit but you don't know which one, git bisect automates binary search over your commit history. You mark a known-good commit and a known-bad commit, and Git checks out the midpoint each time. In 10 steps you can pinpoint the offending commit out of 1,000.

Reproduce checklist

QuestionWhy it matters
Does it reproduce on a clean run (no prior state)?Rules out state carried over from a previous run.
Does it reproduce with the same inputs every time?Rules out randomness or external data changes.
Does it reproduce on another machine or in a container?Rules out machine-specific environment issues.
Does it reproduce on the current main branch?Confirms it's not already fixed.
Try this Next time you encounter a bug, write down the exact command or steps before touching any code. Then verify: running those exact steps on a fresh terminal produces the bug every time. Only then should you start changing anything.
