4.8 Constructing Clean Commit History

A technically correct Git repository is not necessarily a well-structured one. Good Git practice is not only about making commits, but about making clear, reviewable commits. A clean commit history helps other people understand your work, but it also helps your future self. When each commit represents one logical step, it becomes easier to read history, diagnose regressions, and review changes.

Eight habits worth building now

1. Logical grouping. If you fix a bug and also reformat several unrelated files, those changes probably do not belong in the same commit. Because git add stages selected content for the next snapshot, Git supports this discipline directly.

Suppose you are working on a small Flask app. While tracking down why login sometimes rejects valid emails, you fix the regex in validators.py. Along the way you also notice utils.py and config.py are inconsistently indented, so you reformat them, and you rename a confusingly named variable tmp to session_token in auth.py. That is three unrelated changes sitting in your working tree at the same time. Because none of them depend on each other, they belong in three separate commits, staged and recorded one at a time:

$ git add validators.py
$ git commit -m "Fix email regex rejecting valid addresses"

$ git add utils.py config.py
$ git commit -m "Reformat utils.py and config.py to consistent indentation"

$ git add auth.py
$ git commit -m "Rename tmp to session_token in auth.py"

Three reviewable commits, each explainable in one sentence, instead of one commit that mixes a bug fix with unrelated cleanup. If unrelated changes happen to sit inside the same file rather than separate files, git add -p lets you stage individual hunks of a file interactively, so file-level staging is not the only option.

2. Inspection before commit. git status tells you what is staged and unstaged, while git diff and git diff --staged show the textual changes on each side of that boundary. Get used to reading these outputs before committing — it is much easier to correct a staging mistake before the commit than to explain a confusing commit afterward.

Suppose that while debugging the same regex, you temporarily added a line to print every email as it was checked. You fix the regex, then stage the file out of habit. Before committing, git diff --staged shows exactly what would be recorded:

$ git diff --staged
diff --git a/validators.py b/validators.py
index 4a1f2e8..9c3d7b1 100644
--- a/validators.py
+++ b/validators.py
@@ -12,6 +12,7 @@ def is_valid_email(email):
-    pattern = r"^[\w.]+@[\w]+\.\w+$"
+    pattern = r"^[\w.+-]+@[\w-]+\.\w+$"
+    print("checking:", email)
     return re.match(pattern, email) is not None

That print line has no place in the commit. Catching it here means deleting it and re-staging, rather than needing a follow-up commit — or an amend — just to remove debug output from the history.

3. Writing meaningful commit messages. Begin with a single short line summarising the change, followed by a blank line and a fuller description when needed. The text up to the first blank line is treated as the commit title and used throughout Git — in logs, reviews, and history summaries. Compare these two messages:

update

versus

Add input validation for student ID parsing

The second tells a reviewer or future maintainer something concrete about the purpose of the snapshot. For anything more involved than a one-line change, the blank line makes room for detail the title cannot fit:

Add input validation for student ID parsing

Student IDs were being parsed as integers, which failed
whenever a leading zero was present (e.g. 08213445).
Parse them as zero-padded strings instead and validate
the length explicitly.

Notice the title uses the imperative mood — "Add input validation", not "Added" or "Adding". This matches the convention Git itself uses: a good title completes the sentence "If applied, this commit will ___", and keeps every entry in the log reading the same grammatical way.

4. Avoiding "commit everything that changed." Git supports shortcuts such as git commit -a for tracked files. The command is convenient, but such shortcuts can include unwanted changes. Suppose you are fixing that same regex, but you also have an experimental change sitting in config.py — a local database URL you swapped in temporarily to test against a copy of production data, and which must never be committed. Running git commit -a -m "Fix email validation" would stage and commit every modified tracked file, including that experimental config change, without you necessarily noticing. Explicit git add validators.py only ever stages what you name.

5. Fixing the most recent commit, not stacking a new one on top. If you notice a typo in your last commit message, or realise you forgot to include a file, and that commit has not been shared yet, you can fix it in place instead of stacking a new commit on top. git commit --amend replaces the tip commit — the most recent commit on your branch — with a corrected one:

$ git commit -m "Add student ID validation"
# realise you forgot a file
$ git add tests/test_validation.py
$ git commit --amend --no-edit

--no-edit keeps the existing commit message; leave it off if you also want to edit the message. Amending is not only for forgotten files — if only the message was wrong, skip staging entirely and just rewrite it:

$ git commit --amend -m "Fix email regex rejecting valid addresses"
Only amend what is still yours to rewrite Amending rewrites the commit's identity — it is, technically, a brand new commit object built from the old one. Only amend a commit that exists solely on your own machine so far, one you are certain no one else has copied or built on. Amending a commit that has already been shared with others creates the same kind of confusing divergent history that rewriting any shared commit causes — Week 5 covers exactly what "sharing" a commit involves.

6. Committing early and often — but at meaningful checkpoints. Waiting until an entire feature is finished before committing anything is risky: if something goes wrong along the way, there is no intermediate state to compare against or fall back to. Committing after every single keystroke is just as unhelpful, producing a history of noise instead of a history of decisions. Aim for the middle — commit whenever you reach a point that is complete and explainable on its own, even if the feature as a whole is not finished yet: "Add validators.py skeleton", then "Implement email regex", then "Wire validators into login route".

7. Keeping every commit in a working state. Where possible, each commit should leave the project able to run and pass its tests, not paused halfway through a change. This matters more than it might first seem: Section 5.7 covers git bisect, which searches history by checking out and testing individual commits one at a time. A commit that does not build or run cannot be tested, and breaks that search.

8. Never committing secrets or machine-specific files. API keys, passwords, and database credentials should never appear in a commit. Once a secret exists in history, deleting the file in a later commit does not remove it — the secret still exists in every snapshot before that deletion. Section 4.7 covers .gitignore, which is how you keep these files out of Git in the first place. If a secret is committed by accident, treat it as compromised and rotate it immediately, rather than trying to scrub it from history.

Good commit history is a craft The repository model gives you the mechanics, but reviewable history depends on decisions: what belongs together, what should be left for a later commit, what the message should emphasize, and whether the staged snapshot truly matches the change you mean to record.
