4.4 Commits, Snapshots, and Git History as a DAG

A commit in Git is best understood as a snapshot plus metadata. When you make a commit, Git stores a commit object containing a pointer to the snapshot of the content you staged, along with metadata such as author name, email, message, and pointers to the commit or commits that came before it. For an initial commit there are zero parents, for a normal commit there is one parent, and for a merge commit there can be multiple parents — a merge commit is one that ties two lines of development back together, shown a little later in this section. Each commit is a node that points backward to earlier commits — this is the foundation of Git history.

Why "DAG"?

This is why it is useful to describe Git history as a directed acyclic graph (DAG). That structure of commits is directed because the pointers go from newer commits to older parent commits, and it is acyclic because commits do not loop back around to become their own ancestors. Git history diagrams are always described in terms of lines of development diverging and reconverging — exactly the behavior a DAG is meant to represent.

A simple linear history might look like this:

A -- B -- C

Here, commit C points to parent B, and B points to parent A. A branch name such as main is not the history itself — it is just a label pointing to one particular commit in that history. When you make another commit, the branch label moves forward to the new commit. A branch is a lightweight movable pointer to one of the commits.

A more interesting history with branching and merging might look like this:

A -- B -- C ------ E
       \          /
        D --------

In this example, work diverged after B. One line of work continued to C; another created D; then the two were merged into E. When two lines of development reconverge, the merge commit has more than one parent — this means E can point to both C and D. That single fact explains why Git history is not just a list; it is a graph of relationships between snapshots.

The git log command is one of the main tools for reading this graph. It lists commits that are reachable by following parent links from the given commit or commits, and can answer questions such as "commits reachable from one branch but not another." That is why git log is more than just a chronological journal — it is a graph traversal tool with different views into history.

Seeing git log in practice

Sticking with the diverge-and-merge example above: say A, B, and C are commits on main, and D is a commit on a branch called feature-notes that split off at B. In a real repository, each of these has its own hash rather than a bare letter — the examples below show the same five commits, A through E, using the short hashes Git would actually assign them. Before merging, you might want to check exactly what feature-notes adds that main does not have yet — this is the "commits reachable from one branch but not another" question from above, answered directly:

$ git log main..feature-notes
6e2b9f4 Add release notes

main..feature-notes means "commits reachable from feature-notes but not from main." Right now that is just commit D, hash 6e2b9f4.

Once feature-notes is merged into main, Git records the merge commit E (hash 8d4c7a1) with both C and D as parents — exactly as in the diagram above. Run on its own, git log prints full detail for every reachable commit — full hash, author, date, and message:

$ git log
commit 8d4c7a1f9e6b3c2d5a8f1e4b7c0d9a2f5e8b1c4d (HEAD -> main)
Merge: 1c8f5a3 6e2b9f4
Author: Ada Lovelace <ada@example.com>
Date:   Thu May 16 12:00:00 2024 +0000

    Merge branch 'feature-notes'

commit 6e2b9f4a3d7c1e8b5f2a9d4c7e1b8f5a2d9c6e3b (feature-notes)
Author: Ada Lovelace <ada@example.com>
Date:   Wed May 15 16:40:00 2024 +0000

    Add release notes

commit 1c8f5a3e7b4d9c2f6a1e8d5b3c7f4a9e2d6b8c1f
Author: Ada Lovelace <ada@example.com>
Date:   Wed May 15 15:00:00 2024 +0000

    Update README

That much detail per commit is often more than you need. --oneline condenses each commit to its abbreviated hash and message, and adding --graph --decorate --all draws the branch and merge structure with ASCII art — this is about as close as you can get to literally seeing the DAG on screen:

$ git log --oneline --graph --decorate --all
*   8d4c7a1 (HEAD -> main) Merge branch 'feature-notes'
|\
| * 6e2b9f4 (feature-notes) Add release notes
* | 1c8f5a3 Update README
|/
* 4b7e2d8 Add shared setup
* 9f3a1c2 Initial commit

Notice the shape: every commit is marked with a *, while the |, \, and / characters are just connecting lines. Matched against the diagram above, 9f3a1c2 is A, 4b7e2d8 is B, 1c8f5a3 is C, 6e2b9f4 is D, and 8d4c7a1 is E — the graph splits after B, runs down two parallel lines through C and D, and the merge commit E at the top ties them back together, exactly the "diverge, then reconverge" pattern from the plain-text diagram earlier in this section.

CommandWhat it does
git logFull detail for every reachable commit: hash, author, date, message.
git log --onelineOne line per commit — short hash and message, easy to scan.
git log --oneline --graph --decorate --allASCII graph of branching and merging across every branch, not just the current one.
git log -5Only the 5 most recent commits (replace 5 with any count).
git log --author="name"Only commits written by a specific author.
git log branchA..branchBCommits reachable from branchB but not from branchA.
Reframing history as a DAG, not a list Once you see history this way, three things you already know look different. A commit is not merely "the 14th save" — it is a node in a graph of development decisions. A branch is not a separate copy of the project — it is a name pointing into that graph. A merge commit is not just "combine changes" — it is a commit whose parent structure records that two lines of work were brought together.
