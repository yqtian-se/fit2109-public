4.7 Ignoring Files with .gitignore

Not every file in your working tree belongs in version control. Build output, dependency folders, compiled binaries, editor settings, and local secrets all change constantly or are specific to one machine, and committing them clutters history and can even leak information. Git's answer to this is the .gitignore file: a plain text file, usually placed at the root of your repository, that tells Git which paths to leave out of git status, git add ., and similar commands.

A .gitignore file lists one pattern per line:

# Python
__pycache__/
*.pyc

# Node
node_modules/

# Editors
.vscode/
.DS_Store

A trailing / matches a directory and everything inside it. A * is a wildcard that matches any run of characters, so a pattern like *.pyc matches by extension rather than by exact filename. A # starts a comment. You can also negate a pattern with ! to re-include something a broader pattern would otherwise exclude, for example !important.log after a *.log rule.

Two things that catch people out

First, .gitignore only affects files Git does not already track. If a file was committed before you added a rule for it, that rule has no effect and Git will keep tracking it. To stop tracking a file without deleting it from disk, you need to explicitly remove it from the index and then commit that removal:

$ git rm --cached secrets.env
$ echo "secrets.env" >> .gitignore
$ git commit -m "Stop tracking secrets.env"

Second, .gitignore itself should be committed. It is project-specific configuration that every collaborator benefits from, so it belongs in the repository just like any source file. Personal preferences that have nothing to do with the project, such as your own editor's temporary files, are better placed in a global ignore file that applies across every repository on your machine:

$ git config --global core.excludesFile ~/.gitignore_global
Good habit When starting a new project, pull in a ready-made .gitignore template for your language or framework rather than writing one from scratch, since the common exclusions for a given ecosystem are already well understood.
