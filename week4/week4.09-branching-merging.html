4.9 Branching and Merging

Branching is one of Git's most powerful ideas, and it is powerful partly because Git's branches are so lightweight. Recall that a branch in Git is simply a lightweight movable pointer to a commit — this means a branch is not a full duplicate repository, but a named pointer into the existing commit graph. That is why creating a feature branch is cheap enough to do routinely. Git documents git branch for creating a branch and git switch for changing which branch is current.

A simple local feature workflow looks like this:

$ git switch -c feature-readme
# edit files
$ git add README.md
$ git commit -m "Improve project README"
$ git switch main
$ git merge feature-readme

git switch -c <new> creates a new branch and checks it out, while git switch <branch> updates the working directory to reflect the version referenced by that branch. This keeps experimental or task-specific work separate from the main branch until you are ready to integrate it.

Fast-forward merges

When you merge, Git may perform a fast-forward. If the current branch head is an ancestor of the branch being merged, Git can simply move the branch pointer forward without creating a new merge commit. This is why some merges look almost like pointer updates rather than combination events.

True (three-way) merges

When the branches have diverged, Git performs a true merge. The branches are tied together by a merge commit that has both branch tips as parents — a new snapshot created from a three-way merge. This is where the commit graph becomes visibly non-linear.

A branch is a movable pointer to a commit Creating a branch gives you a separate line of local development without copying the whole repository. Merging integrates that line back into another branch. If the histories do not diverge, the merge may fast-forward. If they do diverge, Git creates a merge commit.
