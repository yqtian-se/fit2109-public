Week 4: Version Control with Git — Foundations

Pre-reading · FIT2109 · Monash University

By the end of this week you should be able to

  1. Explain why version control exists and how Git's snapshot model differs from simply keeping copies of files.
  2. Set up your identity in Git and describe the three places Git keeps track of a project's state.
  3. Record changes in deliberate steps, and inspect what has changed before and after each one.
  4. Keep files that don't belong in version control — like build output, dependencies, and secrets — out of your project's history.
  5. Write a clean, reviewable history of changes, and correct your most recent mistake without adding clutter.
  6. Create separate lines of work, bring them back together, resolve conflicts when they overlap, and set aside unfinished work temporarily.

A scenario

You are building a small app for a project, and it has been working fine for weeks. This afternoon you decide to rewrite the part that handles user logins, because the way you first built it was messy. The rewrite touches five different files. Two hours in, nothing works, and you cannot tell whether the problem is your rewrite, some other small edit you made along the way, or something else entirely. You want to compare your code exactly as it was this morning — the last point where everything worked — against what you have now. But you never explicitly marked that moment. You just kept editing the same files, the way most people do before they have a better system.

This is one of the problems version control exists to solve, and Git is the tool almost the entire software industry has settled on for solving it. Every serious codebase you will touch — a startup's first commit, a solo side project, a large engineering team's monorepo — is under Git from day one, precisely so that "what did this look like before I broke it?" always has a real answer. Instead of you inventing an ad-hoc naming scheme to fake a history, Git records one for you automatically — every meaningful change, who made it, why, and how it relates to every other change — so you can always get back to a known-good state without guesswork. This week is about building a solid mental model of how Git actually works underneath the commands, so that later, more advanced Git behaviour never feels like magic.

Recovering from your own mistakes is only part of the picture. The same recorded history is what lets two people edit the same project without silently overwriting each other's work, lets a reviewer see exactly what changed in a proposed update before approving it, and lets a team figure out — months later — exactly which change introduced a bug. Version control turns "who changed what, and why" from a question nobody can answer into one Git can answer automatically. This week focuses on the foundations you need before any of that: history, snapshots, and recovery on your own machine, working alone. Week 5 builds directly on top of these same ideas once a second person and a shared remote enter the picture.

Concept check — before you start If you have never used Git before, think about how you currently keep old versions of a file "just in case." As you read, notice every place where Git replaces that habit with something more precise.
