Core commands

4.6 Core Git Operations

In Git, there is a small set of core commands. The first two are about getting a repository. git init creates an empty Git repository, essentially by creating a .git directory and an initial branch with no commits yet. git clone creates a full local copy of an existing repository, history and all, and remembers where that copy came from so you can stay in sync with it later — exactly how that syncing works is covered in Week 5. In practice, git init is what you use when starting a brand-new local project, while git clone is what you use when beginning from an existing repository.

CommandWhat it does
git initCreates a new, empty repository in the current folder.
git clone <url>Copies an existing repository, including its full history, to your machine.
git statusShows what is staged, modified, and untracked right now.
git add <file>Stages a snapshot of the file's current content for the next commit.
git commit -m "..."Records the staged snapshot in the repository history.
git diffShows unstaged changes — what you have edited but not yet added.
git diff --stagedShows what is already staged for the next commit.
git logShows commit history by following parent links.

Once you have a repository, the next key command is git status. It shows the state of the working tree relative to the index and the current HEAD commit — what is staged, what is modified but unstaged, and what is untracked. This is why a good beginner habit is to run git status frequently, rather than guessing what Git thinks is happening. The short form git status -s is also useful once the long output becomes familiar.

git add is the command that stages content. It is used for both new and modified files, and in both cases it takes a snapshot of the specified content and stages it in the index for the next commit. If you change a file after running git add, the staging area still contains the earlier snapshot, so you need to run git add again if you want the latest version included in the next commit. Git stages content as it exists at the moment of git add, not as it might look later when you finally commit.

git commit records the staged snapshot in the repository history. This means git commit should be thought of as "record exactly the staged snapshot," not "save whatever currently exists in my folder." That distinction is the key to making reviewable history.

git diff and git log are the two most important inspection commands. git diff by itself shows changes between the working tree and the index, while git diff --cached or git diff --staged shows what has already been staged relative to the last commit. That means git diff answers "what have I changed but not staged yet?" and git diff --staged answers "what will go into the next commit if I commit now?"

Scenario 1: Starting a Brand-New Project

Say you are starting a small script for a unit assignment, and you want every step recorded from the very first line of code. Here is exactly what happens, command by command.

1. Create the repository. There is nothing to look at yet — no files, no commits, just a fresh .git directory:

$ git init
Initialized empty Git repository in /home/student/hello-app/.git/

2. Create a file. This only touches the working tree — Git has not been told about app.py yet:

$ echo "print('Hello')" > app.py

3. Check status. Git confirms exactly that: the file exists, but it is untracked:

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	app.py

nothing added to commit but untracked files present (use "git add" to track)

4. Stage it. No output on success — but running git status again now would show app.py under "Changes to be committed" instead of "Untracked files":

$ git add app.py

5. Commit. The staged snapshot becomes a permanent part of the repository's history:

$ git commit -m "Add initial app script"
[main (root-commit) 3f8a2c1] Add initial app script
 1 file changed, 1 insertion(+)
 create mode 100644 app.py

root-commit is Git telling you this is the very first commit in the repository — it has no parent.

6. Confirm it landed:

$ git log
commit 3f8a2c1d9e6b4a7f2c5d8e1b6a9f4c7d2e5b8a1f (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Mon Jun 10 09:00:00 2024 +0000

    Add initial app script

One commit, matching exactly what was staged — nothing more, nothing less.

Scenario 2: Changing the Code

Continuing from Scenario 1: suppose you come back later and change app.py to greet a name instead of printing a fixed string:

1. Check status. This time Git recognises app.py as modified, not new — it is already tracked:

$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   app.py

no changes added to commit (use "git add" and/or "git commit -a")

2. Stage the change:

$ git add app.py

3. Review it:

$ git diff --staged
diff --git a/app.py b/app.py
index 3b18e51..8a4f2c9 100644
--- a/app.py
+++ b/app.py
@@ -1 +1,4 @@
-print('Hello')
+def greet(name):
+    print(f"Hello, {name}!")
+
+greet("world")

Those - and + lines are the entire point of diff: a precise, line-by-line record of what changed — one line removed, four added.

4. Commit the change, and check the history:

$ git commit -m "Make greeting configurable by name"
[main 9c7e2a4] Make greeting configurable by name
 1 file changed, 4 insertions(+), 1 deletion(-)
$ git log --oneline
9c7e2a4 (HEAD -> main) Make greeting configurable by name
3f8a2c1 Add initial app script

Two deliberate steps in the history, each reviewable on its own — not one undifferentiated blob of changes.

Scenario 3: Joining a Project That Already Exists

Now the opposite situation: your tutor has sent you a link to your group's assignment repository, and you need to get set up on your own machine for the first time.

1. Clone it. This downloads the entire history of the project, not just its current files — every commit anyone on the team has made so far:

$ git clone https://github.com/fit2109-group12/assignment.git
Cloning into 'assignment'...
remote: Enumerating objects: 142, done.
remote: Counting objects: 100% (142/142), done.
remote: Compressing objects: 100% (98/98), done.
Receiving objects: 100% (142/142), 48.21 KiB | 2.41 MiB/s, done.
Resolving deltas: 100% (61/61), done.

2. Move into the new folder. git clone creates it for you, named after the repository:

$ cd assignment

3. Check status. A fresh clone always starts perfectly in sync with where it came from:

$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

4. Look at what came before you. Even though you have not written a line yet, the full history is already sitting on your machine:

$ git log --oneline
9d4e7b0 (HEAD -> main, origin/main) Add unit tests for parser
5c1f6a8 Fix off-by-one error in tokenizer
b2e9a3d Initial project skeleton

Three commits from your teammates, fully readable, before you have made a single change — this is exactly what "every developer has a complete local repository" (Section 4.1) means in practice.

The basic Git cycle Create or obtain a repository, inspect its state, make changes, stage selected content, review that staged content, commit it, and inspect history. That cycle is the heart of Git foundations.
