Package managers have boundaries

There is no single package manager for everything on a computer. pip, npm, apt, and Homebrew each manage a particular collection of software and install it into particular locations.

Scope: what a manager is responsible for

A package manager can discover releases, resolve dependencies, install files, record installed state, and remove software. Its scope defines which packages and locations it manages.

ScopeExample managerTypical responsibility
Python environmentpipPython packages imported by a selected interpreter.
JavaScript projectnpmPackages used by a Node.js project.
Ubuntu or Debian systemaptCommands, libraries, and services installed into the operating-system filesystem.
macOS software ecosystemHomebrewCommands and libraries installed into directories managed by Homebrew.

One manager does not automatically satisfy dependencies owned by another scope. A Python installer cannot generally install an arbitrary operating-system command, and an operating-system manager does not know which package set belongs inside a particular Python venv.

One application can cross several scopes

Consider a media-report application. Its Python source imports an image-processing library, launches a separate video-conversion executable, reads a font installed on the operating system, and sends results to a remote service. These are four different dependency types:

  • a Python package resolved by the selected Python environment;
  • a system executable discovered through PATH;
  • a data file located in the operating-system filesystem; and
  • an external service reached over the network.

Successfully installing the Python package proves only that one layer is present. It does not prove that the executable, font, network, or remote service is available.

Repositories connect package names to releases

An operating-system repository is a configured source of package metadata and files. The operating-system release determines which repositories and package families are compatible. Two machines can use the same package name but receive different releases because their operating-system versions or repository configurations differ.

Repositories also change over time as maintainers publish security fixes and updates. A setup instruction written today may select a different package release when it is repeated later.

System state is often shared

Operating-system packages commonly install into shared directories. Several applications may use the same executable or dynamically loaded library. Upgrading that shared component for one application can affect another, while keeping incompatible system versions side by side may require extra configuration.

Permissions are part of this boundary. Modifying shared operating-system state often requires administrator authority, whereas installing into a project-owned environment may not.

Documentation is not isolation

A setup guide can record the package name and installation procedure. This is useful and may be sufficient for a simple local tool. However, the command still operates on each user's operating system, repositories, permissions, and existing shared state. Recording an instruction does not record the result that the host will produce.

If those host differences keep causing failures, the project may need to carry more of its filesystem and configuration with the application. That is the problem containers are designed to address.

Key points
  • Package managers operate within different scopes.
  • An application can depend on language packages, system software, files, and external services at the same time.
  • Operating-system releases, repositories, permissions, and shared state influence system installations.
  • A setup guide documents host changes; it does not isolate them.
