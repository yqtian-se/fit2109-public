6.9 Package Managers Across Ecosystems

You have now seen pip and venv in depth. The good news: every language ecosystem uses the same underlying pattern. The names differ, but the concepts — install tool, manifest, lockfile, local packages directory — are identical. Once you understand one, you can pick up any other in minutes.

The universal pattern

Every package manager answers the same four questions:

  1. How do I declare what my project needs? → the manifest
  2. How do I pin the exact versions that were installed? → the lockfile
  3. Where do installed packages live? → the local packages directory
  4. How do I recreate the environment from scratch? → one install command reads the lockfile

Quick reference across ecosystems

Ecosystem Install tool Manifest Lockfile Local packages dir Commit lockfile?
Python pip + venv pyproject.toml or hand-written requirements.txt requirements.txt output of pip freeze .venv/ Yes — ignore .venv/
Node.js npm package.json package-lock.json node_modules/ Yes — ignore node_modules/
Java mvn (Maven) pom.xml No separate lockfile — Maven resolves from a shared local cache ~/.m2/repository/ (global) Commit pom.xml; ignore ~/.m2/
Rust cargo Cargo.toml Cargo.lock ~/.cargo/registry/ (global cache) Yes for applications; optional for libraries
Ruby bundle Gemfile Gemfile.lock vendor/bundle/ or system gems Yes — ignore vendor/bundle/
Go go mod go.mod go.sum ~/go/pkg/mod/ (global cache) Yes — both files

What the commands look like in each ecosystem

The surface commands differ, but the conceptual moves are always the same. Here is the same workflow — add a dependency, install, reproduce — across four ecosystems:

TaskPython (pip)Node.js (npm)Rust (cargo)Ruby (bundler)
Add a dependency python3 -m pip install requests npm install express cargo add serde bundle add rails
Lock versions pip freeze > requirements.txt Auto-generated into package-lock.json Auto-generated into Cargo.lock Auto-generated into Gemfile.lock
Recreate from lockfile pip install -r requirements.txt npm install cargo build bundle install

The main structural difference: isolation

Where installed packages live varies more than the commands do:

  • Python (pip) — global by default, which is why venv exists as a deliberate extra step. Most other ecosystems learned from this and made local installs the default.
  • Node.js (npm) — local to the project (node_modules/) by default. No separate isolation step needed for packages; but the Node runtime version itself is still global.
  • Rust (cargo) and Go — use a global download cache but build compiled output into the project. Isolation is achieved through the build system, not a virtual environment.
  • Java (Maven) — downloads to a global ~/.m2/ cache, no lockfile. Version conflicts between projects are resolved by convention (explicit version declarations in pom.xml) rather than isolation.
Why Python needed venv Python predates the modern per-project isolation pattern. Its default pip install is global because early Python was primarily a scripting and system tool — multi-project isolation was not a design goal. Newer Python tooling (uv, poetry, pipenv) makes isolation automatic, matching the Node/Rust experience. If you use these tools in future projects you will not need to manually create a .venv.
Concept check You join a project that uses Rust. You clone the repo and find Cargo.toml and Cargo.lock. Without knowing any Rust, which file ensures reproducible installs, and what single command would recreate the environment? Use the pattern from the table above to reason it out.
