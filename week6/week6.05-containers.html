Processes, filesystems, and isolation

A venv, a container, and a virtual machine do not create the same kind of boundary. Comparing them starts with three pieces: the running process, the files it can see, and the operating-system kernel doing the low-level work.

A process is a running program

A program file is stored code. A process is a running instance of that code with memory, open files, environment variables, permissions, and a current working directory. Starting the same program twice creates two processes with separate runtime state.

A process can use only what the operating system makes available through paths, permissions, environment variables, network interfaces, and services. Change that view and the process may behave differently.

The kernel and user space

The kernel is the core of an operating system. It manages hardware, memory, filesystems, networking, and process scheduling. Ordinary applications and most libraries run outside the kernel in user space and request kernel services when they need low-level work.

The host is the machine or managed environment that provides the kernel and runs the isolation software. A guest is a separate operating system running on virtualised hardware.

Three boundaries

ToolPrimarily separatesStill shared or inherited
Python venvPython launcher and package locationHost processes, filesystem, system commands, and kernel
ContainerApplication processes, user-space filesystem view, and selected configurationA Linux kernel supplied by the host or a managed Linux environment
Virtual machineA complete guest operating system on virtualised hardwarePhysical host resources managed by a hypervisor

A hypervisor is the software layer that creates and manages the virtual hardware presented to a VM.

Do not choose by asking which tool is “strongest.” Ask where the troublesome dependency lives. If it is only a Python package, a venv may be enough. If the application also needs system files and commands, a container covers more. A complete guest operating system calls for the larger VM boundary.

Image and container are different states

A container image is a reusable package of user-space filesystem contents and runtime configuration. A container is an instance created from an image. This is similar to the distinction between a program file and a process: one stored artifact can create many runtime instances.

Changes made by one container do not rewrite the original image. A new container starts again from the image's recorded contents. Storage that must outlive a disposable container needs an explicitly managed location outside that temporary runtime state.

Files inside and outside the boundary

A container can give an application a predictable internal directory structure even when users store the project in different host locations. Files can also be mounted from the host when the application must read changing source or data. Mounted files remain host-controlled and can therefore reintroduce differences in paths, permissions, and contents.

What these boundaries do not guarantee

A container image does not contain the host kernel, processor architecture, network services, secrets, or live input. A VM includes a guest kernel but still depends on virtual hardware, external services, and runtime data. Isolation reduces selected variation; it does not make every execution identical.

The further-reading chapter on virtual machines introduces common local and cloud VM software. The workshop will revisit the container/VM boundary through concrete requirements.

Key points
  • A process is runtime state created from stored program files.
  • A venv, container, and VM isolate different layers of an environment.
  • A container packages user-space state but uses an existing Linux kernel.
  • An image is a reusable artifact; a container is one runtime instance.
