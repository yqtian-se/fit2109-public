6.10 Lockfiles

A manifest declares what your project wants. A lockfile records what was actually installed. The distinction matters because a manifest typically allows a range of versions, so two people running "install" at different times can end up with different packages. A lockfile eliminates that ambiguity.

Manifest vs lockfile

ManifestLockfile
PurposeDeclares intent — what the project needs.Records fact — what was actually installed.
VersionsOften ranges: requests>=2.0, "express": "^4.18"Exact: requests==2.31.0, "express": "4.18.2"
Transitive depsUsually only direct dependencies.Includes every dependency of every dependency.
Written byYou, the developer.The package manager automatically.
Committed?Yes.Yes — this is the point of it.

Why this matters in practice

Consider a dependency requests>=2.0 in a Python manifest. On Monday you install and get requests==2.31.0. On Friday your colleague clones the repo and installs — a new release was published, they get requests==2.32.0. The APIs are compatible, but a subtle bug was introduced in 2.32.0. Their tests fail; yours pass. Without a lockfile, you are debugging a version difference, not a code bug.

pip freeze caveat — platform-specific packages pip freeze pins packages by version, but some packages contain compiled C extensions (e.g., psycopg2, cryptography). A pinned version that compiled on macOS may fail to install on Linux or a different CPU architecture because the pre-built binary does not match. If your team uses mixed platforms, prefer pip compile (from pip-tools) which generates a platform-aware lockfile, or run your installs inside a Docker container to guarantee a consistent platform.
Three rules for lockfiles
  • Always commit the lockfile. It is useless if it is not in version control.
  • Never hand-edit a lockfile. It is machine-generated. Editing it manually produces an inconsistent state.
  • Do not commit the installed packages. node_modules/ and .venv/ belong in .gitignore.

The big picture

Reproducibility across all layers requires both containers and lockfiles:

  • Containers lock the OS and system library layer.
  • Lockfiles lock the language library layer.

Together, they eliminate "works on my machine" at every level. A container without a lockfile still exposes you to library version drift. A lockfile without a container still exposes you to OS and runtime differences.

Side note — reproducibility in research Lockfiles and containers are not just developer tools. Computational science has a reproducibility crisis: results published in papers often cannot be reproduced because the exact software environment was not recorded. Tools like Binder and repo2docker wrap Jupyter notebooks in Docker containers with pinned environments, making research results verifiable. The same engineering principle applies to both production software and scientific code.
Concept check Your package.json specifies "lodash": "^4.17.0". Your lockfile specifies "lodash": "4.17.21". A colleague deletes the lockfile and runs npm install. What version of lodash might they get, and why could this be a problem?
