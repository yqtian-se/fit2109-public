One Python environment per project

Recording a version answers “what should pip install?” A virtual environment answers “which project-specific package location should pip use?”

The conflict

Suppose App A requires messagekit==1.4, while App B has been updated for messagekit==2.0. If both applications use one shared Python package location, installing the version for one application can make the other application fail.

Shared environment

Only one installed messagekit version is selected by that Python environment. App A or App B may be broken.

One venv per project

App A uses .venv-a with 1.4. App B uses .venv-b with 2.0. Both can run.

Create, activate, and install

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

Activation places the venv's launchers at the front of the shell's PATH. After activation, python and python -m pip refer to the project environment.

Inspect the active environment

python -c "import sys; print(sys.executable)"
python -c "import messagekit; print(messagekit.__file__)"

Both paths should point inside .venv. This is evidence that the shell is using the project environment.

A venv does not supply a new operating systemIt is created from the Python interpreter you select. It isolates Python packages, but it does not change that Python version, provide system commands, or start a separate kernel.

pip3 and python3 -m pip

pip3 is normally a pip executable associated with a Python 3 installation. python3 -m pip makes the relationship explicit by running pip through the selected interpreter. Inside the activated venv, use python -m pip so the destination is clear.
