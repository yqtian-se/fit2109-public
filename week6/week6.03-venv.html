Description and installed state

A dependency file and a .venv/ directory may sit beside the same source code, but they play very different roles. One describes what the project needs; the other is a local installation produced from that description.

Four kinds of project information

CategoryExampleRole
Sourceapp.pyInstructions written by the project.
Dependency descriptionrequirements.txt or pyproject.tomlPackage constraints the project records and reviews.
Installed state.venv/ and its site-packages/Files produced when an environment is created and packages are installed.
Runtime evidenceInterpreter path, package path, and version outputObservations showing which environment a process actually used.

Source and dependency descriptions normally belong in version control. Each checkout rebuilds its own installed state. When something looks wrong, interpreter paths, package paths, and version output show what the process actually used.

Where Python finds packages

A Python interpreter searches configured directories when resolving an import. One important location is commonly called site-packages, where third-party packages are installed. If several projects use the same interpreter and the same package location, changing that shared state for one project can affect the others.

A Python virtual environment, or venv, creates a project-specific Python environment with its own package location. It is created from an existing Python interpreter, so it inherits that interpreter's Python version rather than downloading a different one.

project/
├── source files
├── dependency description
└── .venv/
    ├── Python launcher
    └── site-packages/

Activation changes command lookup

The shell variable PATH is an ordered list of directories searched for executable commands. Activating a venv places the environment's launcher directory near the front of PATH in the current shell. A command named python then resolves to the venv launcher before a system-wide launcher.

Activation does not copy the environment, start a new operating system, or permanently reconfigure the machine. It changes command lookup for one shell session. A new terminal has its own shell state and normally needs its environment selected again.

The interpreter decides where pip installs

A machine can contain several Python interpreters, each with its own package locations. Running pip through a specific interpreter makes the relationship explicit: that interpreter determines which Python environment receives the installed package. This is why the workshop will inspect both the Python executable path and the imported package path rather than trusting the prompt alone.

Why installed environments are rebuilt, not shared

A venv can contain platform-specific installed files and references to the interpreter used to create it. Copying a venv between machines can therefore fail even when the directory names look identical.

The usual handoff is the project description, not the generated directory. Each developer creates local installed state from the recorded description. The .venv/ directory is normally excluded from Git, while dependency declarations remain reviewable with the source.

The boundary of a venvA venv separates Python package state. It does not provide system commands, isolate running processes, create a separate filesystem, or supply another operating-system kernel.
Key points
  • Dependency declarations and installed packages are different kinds of state.
  • A venv provides a project-specific Python package location and inherits its creator's Python version.
  • Activation changes command lookup in one shell; it does not create a new machine.
  • Developers share the description and rebuild the generated environment locally.
