Packages, dependencies, and resolution

Installing one package can add many packages to an environment. It can also produce a different result next month, even when the command has not changed. Dependency resolution explains both behaviours.

Packages come from an ecosystem

A package is a distributable unit of software. A package usually has a name, a version, metadata, and its own dependencies. A package index is an online service that publishes metadata and distributes package releases. Python's main public index is the Python Package Index (PyPI).

An installer such as pip does more than download a named file. It reads the project's requested constraints, examines package metadata, considers the selected Python version and platform, and chooses a set of releases that can be installed together. This choice is called dependency resolution.

Direct and transitive dependencies

A package named directly by an application is a direct dependency. That package may depend on other packages, which become transitive dependencies of the application.

your application
└── reportlib             direct dependency
    ├── template-core     transitive dependency
    └── text-utils        transitive dependency

The application may never import template-core itself, yet a compatible release is still required for the environment to work. A declaration containing one direct dependency can therefore create many installed packages.

A requirement is a constraint, not an installed package

A project declaration describes acceptable software. It is an input to the resolver; it is not the installed environment itself. Common constraint styles include:

Example declarationMeaningConsequence
reportlibNo version constraint is stated.A later installation may choose a newer release.
reportlib==3.2.1Request one exact release.The direct version choice is repeatable while that release remains available.
reportlib>=3,<4Allow a range of releases.The resolver can choose different releases at different times.

Ranges are useful when a library supports several compatible releases. Exact pins are useful when a team wants to repeat a tested choice. Neither form proves that the selected software works correctly; compatibility still requires tests.

Why resolution can change

Resolution depends on more than the text in one file. New package releases appear, old releases can be withdrawn, transitive dependencies change, and some releases support only particular Python versions, operating systems, or processor types. Two installations can therefore differ when the declaration leaves any of those choices open.

Installation is therefore not a permanent, one-time decision. Dependency updates can provide security and reliability fixes, but the newly selected set still needs to be reviewed and tested with the application.

Requirements files and lockfiles

Python projects often use requirements.txt to record package requirements. The file format can contain exact pins, ranges, or a mixture. The filename alone does not guarantee that every transitive version has been fixed.

A tool-generated lockfile normally records a complete resolved set, often with additional integrity or platform information. Different ecosystems and Python tools use different lockfile formats. In short, a declaration says what may be installed; a lockfile records one resolution result.

Still outside this layerPackage declarations do not choose the operating system, provide system commands, select an installation location, or isolate one project from another. Later chapters introduce those boundaries.
Key points
  • A resolver chooses direct and transitive package releases from an ecosystem.
  • A declaration states constraints; installed packages are generated state.
  • Exact pins and ranges make different tradeoffs between repeatability and permitted updates.
  • A requirements file is not automatically equivalent to a complete lockfile.
