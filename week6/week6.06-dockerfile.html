6.6 Dockerfiles

A Dockerfile is a plain-text recipe that describes how to build a Docker image. Every instruction adds a layer to the image. Running docker build executes those instructions in order, producing a reproducible, versioned artifact that anyone can use to recreate the same environment.

Core instructions

InstructionWhat it does
FROMSet the base image to start from. Every Dockerfile must begin with FROM. Common bases: ubuntu:22.04, python:3.12-slim, node:20-alpine.
WORKDIRSet the working directory inside the image for subsequent instructions. Creates the directory if it does not exist.
COPYCopy files from the build context (your host) into the image.
RUNExecute a shell command during the build. Used to install packages, compile code, and set up configuration.
ENVSet an environment variable that will be present at both build time and runtime.
EXPOSEDocument which port the application listens on. Does not actually publish the port — use -p when running.
CMDThe default command to run when a container starts. Can be overridden by passing a command to docker run.

A Dockerfile for a Python application

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
ENV PYTHONDONTWRITEBYTECODE=1   # no .pyc files during install or at runtime
RUN pip install --no-cache-dir -r requirements.txt
# --no-cache-dir: skip pip's download cache → smaller image
COPY . .
CMD ["python", "app.py"]

Building and running

# Build the image from the current directory (where Dockerfile lives)
$ docker build -t myapp .

# Run it
$ docker run --rm myapp

Layer caching: why order matters

Docker caches each layer. If a layer's instruction and its inputs are unchanged since the last build, Docker reuses the cached layer and skips re-executing it. This makes rebuilds fast — but only if you write the Dockerfile to take advantage of it.

The critical ordering rule: copy files that change rarely before files that change often.

  • requirements.txt changes only when you add or remove dependencies.
  • Your source code changes on every edit.

If you write COPY . . first and then RUN pip install, every source code change invalidates the pip install layer — Docker reinstalls all packages on every rebuild. By copying requirements.txt first and running pip install immediately after, the install layer is only invalidated when dependencies actually change.

Common mistake: COPY . . before pip install This forces a full pip install on every rebuild, even when only a single source file changed. Keep dependency installation as early as possible in the Dockerfile.

Pay attention to: why python:3.12-slim and not python:3.12 (without the -slim suffix)? Why --no-cache-dir? Why is ENV placed before RUN pip install? Why is COPY . . last?

Advanced: multi-stage builds

Some applications need heavy build-time tools (compilers, test runners, build systems) that should never end up in the final deployed image. A multi-stage build uses multiple FROM instructions in one Dockerfile — each stage produces an intermediate image, and the final stage copies only the compiled output.

# Stage 1 — build: has Maven + JDK, compiles the app
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
COPY . .
RUN mvn -q -DskipTests package   # produces target/app.jar

# Stage 2 — runtime: tiny JRE only, no Maven, no source code
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=build /src/target/app.jar .   # copy artifact from the build stage
CMD ["java", "-jar", "app.jar"]

The final image contains only the JRE and the compiled .jar. The Maven installation, source code, and intermediate build files are discarded. This is the standard pattern for Java, Go, and any compiled language where the build toolchain is large.

Why this matters A Maven + JDK image is ~500 MB. A JRE-only image is ~200 MB. Shipping the build toolchain to production wastes bandwidth, increases attack surface, and slows deployments. Multi-stage builds eliminate all three problems in one Dockerfile.
