Descriptions, recipes, and artifacts

Three things are easy to mix up: the instructions for creating an environment, the result created from those instructions, and a running instance of that result. In Docker, these are the Dockerfile, image, and container.

How the terms map to different tools

Recorded input is usually text that a team can review and version. The constructed state may be large, platform-specific, or expensive to recreate. Starting it adds temporary process state and live input.

Not all constructed state is a handoff artifact. A local venv is normally rebuilt by each developer. A tested container image or VM image may be stored and distributed as an artifact.

A recipe describes a process; an artifact records one result

A Dockerfile tells Docker how to build an image. The image contains the resulting user-space files and runtime configuration. Starting that image creates a container.

If a developer shares only the recipe, the receiver must perform another build. If the developer shares a tested image, the receiver starts from the files produced by that particular build. Image registries store and distribute these built artifacts.

Construction time and run time

Construction-time actions prepare the artifact: select a starting environment, install dependencies, create directories, and copy source files. Their results become part of the image. Run-time configuration chooses what process starts when a container instance is created.

Installing a dependency during the build changes the image being created. Starting a container later uses the files already captured in that image; it does not normally repeat the installation.

Build inputs need a boundary

A container build receives a selected directory of input files called the build context. The recipe can copy files from that context into the image. Files outside it are unavailable to the build.

A .dockerignore file excludes unnecessary or sensitive paths from the context. Typical exclusions include local virtual environments, generated caches, temporary files, and credentials. A smaller, deliberate context makes builds faster and reduces accidental inclusion of host-specific state.

Why the same recipe can produce a different artifact later

Recipes often refer to inputs that can change: a base-image tag, an operating-system repository, a package range, or a remote download. Repeating the same recipe later may therefore select updated inputs and produce a different artifact.

Reusing the same already-built image is more repeatable than rebuilding the same Dockerfile at different times. Teams still rebuild deliberately to receive security and dependency updates, then test the new artifact before replacing the old one.

Why source changes do not update an old image

A build copies the source available at construction time. Editing the host source later does not rewrite the existing image. A new runtime instance created from that old image still receives the old captured files. The changed source appears only after constructing a new image or explicitly mounting host files at runtime.

Further detail: instruction order and build caching

Container builders can reuse earlier construction results when their instructions and inputs have not changed. Projects often install dependencies before copying frequently changing source, allowing the expensive dependency step to be reused when only application code changes.

Caching improves build speed, but it does not make an old image update itself. Changed inputs still require a new build.

Check the environment that actually ran

A description states intent, and an artifact records constructed contents. Runtime evidence shows what a process actually received. Useful evidence can include version output, executable and package paths, file locations, process exit status, and automated test results.

A practical workflow is to record the important inputs, build from a clean state, run the result, and inspect what actually happened. The workshop will follow those steps with a concrete Dockerfile. The recipe is useful, but the running result is the final check.

Key points
  • Descriptions, generated artifacts, and runtime instances are different kinds of state.
  • A recipe can be versioned, while an artifact records one result of executing that recipe.
  • Build time prepares image contents; run time creates a process from those contents.
  • Mutable external inputs mean the same recipe can produce a different artifact later.
  • Reproducibility requires recorded inputs and observable verification.
