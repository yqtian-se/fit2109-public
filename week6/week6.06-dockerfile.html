Dockerfile, image, and container

The Dockerfile is the build recipe. docker build uses that recipe and the build context to create an image. docker run creates a container from the image.

The Week 6 example

The earlier messagekit timeline isolated the version-drift idea. The runnable seminar example has three files:

pyapp/
├── app.py              # imports requests and launches curl
├── requirements.txt    # contains requests==2.31.0
└── Dockerfile           # records how to build the environment

The Dockerfile records both dependency layers: pip installs the Python package, while apt installs the system command.

FROM python:3.12-slim

RUN apt-get update \
    && apt-get install -y curl

WORKDIR /app
COPY requirements.txt .
RUN python -m pip install -r requirements.txt
COPY app.py .

CMD ["python", "app.py"]
InstructionIts job in this image
FROMSelect Python 3.12 and the starting Linux user-space filesystem.
RUNExecute installation commands while building the image.
WORKDIRGive later steps and containers the stable internal path /app.
COPYPlace declared dependencies and source files into the image.
CMDChoose the default command when the user supplies no replacement command.

Build and run

docker build -t fit2109-week6 .
docker run --rm fit2109-week6

Why an old image still contains old source

The build reads the files available at build time. Editing app.py on the host does not rewrite an existing image. Run the old image and it still starts from the old image contents. Run docker build again to capture the changed source in a new image.

One useful ordering ruleCopy requirements.txt and install dependencies before copying frequently changed source. Docker can often reuse the dependency installation when only app.py changes.

Concept check

You edit app.py from “version 1” to “version 2” and immediately run the existing image. Why does the container still print version 1?
