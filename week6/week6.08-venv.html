6.8 Python venv and pip

Python's default package installer, pip, installs packages into the Python that is currently active. Without isolation, all projects on a machine share the same global set of packages. This causes conflicts when two projects need different versions of the same library.

The problem with global installs

Suppose Project A needs Django==3.2 and Project B needs Django==4.2. A global pip install can only hold one version at a time. Installing for one project breaks the other. The solution is virtual environments.

pip — the Python package installer

There are two ways to invoke pip. You will see both in the wild:

FormWhat it doesWhen to use
pip3 install pkg Runs the pip3 executable from your shell's PATH. On most systems this is pip for Python 3, but on machines with multiple Pythons it may point to an unexpected interpreter. Fine on a single-Python machine or inside a virtual environment where PATH is unambiguous.
python3 -m pip install pkg Runs pip as a module of the specific python3 interpreter you invoked. Guarantees pip installs into exactly the Python you are using. Recommended when you have multiple Pythons, or when scripts and CI need to be explicit. This is what the Ed lesson uses.

Inside an activated virtual environment both forms install into the venv — pip, pip3, and python3 -m pip are all equivalent because the venv's bin/ is at the front of PATH.

$ pip3 install requests                      # shorthand form
$ python3 -m pip install requests            # explicit form — same result
$ python3 -m pip install requests==2.31.0    # pin a specific version
$ python3 -m pip uninstall requests
$ python3 -m pip list                          # all installed packages
$ python3 -m pip show requests               # details: version, location, deps
$ python3 -m pip freeze                        # all packages with pinned versions

venv — per-project isolation

A virtual environment is a self-contained directory tree containing a Python interpreter and a private set of installed packages. Activating it makes that interpreter and its packages the default for your shell session.

# 1. Create the virtual environment
$ python3 -m venv .venv

# 2. Activate it (prompt changes to show (.venv))
$ source .venv/bin/activate           # Linux / macOS
$ .venv\Scripts\activate               # Windows

# 3. Install packages (they go into .venv/, not the global Python)
(.venv) $ python3 -m pip install requests rich==13.7.1

# 4. Pin the exact versions for reproducibility
(.venv) $ python3 -m pip freeze > requirements.txt

# 5. Deactivate — .venv/ is untouched; PATH is restored
(.venv) $ deactivate
$

Sharing the environment

# A teammate clones the repo and recreates the exact same environment:
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ python3 -m pip install -r requirements.txt   # installs exact pinned versions

What to commit vs what to ignore

ItemCommit?Reason
requirements.txtYesLets teammates and CI recreate the environment deterministically.
.venv/No — add to .gitignoreContains compiled binaries that are platform-specific and can be hundreds of MB.
deactivate does not delete anything deactivate only restores your shell's PATH to point back at the global Python. The .venv/ directory and everything installed in it remain intact. You can reactivate and continue where you left off.
Try this Create a new directory, make a venv, activate it, install rich, and run python3 -c "from rich import print; print('[bold green]Hello[/]')". Then deactivate and run the same command — it should fail because rich is not in the global Python.
Concept check After running pip freeze > requirements.txt, you notice the file contains many packages you did not explicitly install — for example, you only installed requests, but the file also lists certifi, charset-normalizer, idna, and urllib3. Why? (Hint: think about what requests itself depends on to work.)
