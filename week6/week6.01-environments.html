6.1 Why Environments Differ

Two machines can run the same source code and produce different results. This is not a mystery — it is a consequence of all the invisible variables that make up a machine's environment. Understanding what those variables are is the first step to controlling them.

What makes up a software environment

When you run a program, it does not execute in isolation. It depends on a stack of components that may differ between machines:

ComponentExample differencesWhy it matters
Operating systemUbuntu 22.04 vs macOS 14 vs Windows 11File paths, process APIs, and available system calls differ.
System librarieslibc 2.35 vs 2.31, openssl 1.1 vs 3.0C extensions and cryptographic code may link to incompatible versions.
Language runtimePython 3.9 vs 3.12, Node 18 vs 20Syntax, standard library APIs, and default behaviour change between minor versions.
Package versionsrequests==2.28 vs requests==2.31Bug fixes, API changes, and new defaults may alter behaviour.
Environment variablesDEBUG=1 set locally but not in CICode that reads environment variables behaves differently without them.
Hardware and architecturex86-64 vs Apple Silicon (arm64)Native extensions must be compiled for the correct architecture.

Common consequences

  • Tests pass locally, fail in CI. CI runs on a clean Ubuntu image; your laptop has accumulated years of global installs.
  • A library upgrade on one machine breaks another. Someone ran pip install --upgrade without pinning, and the rest of the team gets a different version next time they install.
  • A deployed app crashes in ways that cannot be reproduced locally. Production runs Python 3.9; your laptop has 3.12. A walrus operator or a match statement that works locally fails silently — or loudly — elsewhere.
  • Debugging requires guessing the environment. Without knowing exactly what versions ran when the bug occurred, root-cause analysis is guesswork.
The hidden assumption Every time you run code without declaring its dependencies, you are implicitly assuming the environment is correct. That assumption breaks — not if, but when the code moves to a different machine, a future date, or a colleague's setup.

The solution: make the environment explicit

The fix is not to hope everyone has the same setup. It is to declare the environment as code. Reproducible environments rest on three principles:

  • Isolation — each project runs in its own contained environment, separate from the host and from other projects.
  • Portability — the same environment specification produces identical results on any machine: your laptop, a teammate's laptop, CI, and production.
  • Dependency management — every dependency (OS tools, language runtime, libraries) is declared explicitly with a version, not assumed to be present.

The remaining pages cover the tools that enforce these principles at each layer:

  • Virtual machines — isolate the full OS.
  • Containers — isolate the filesystem and process environment; portable across any Linux-based host.
  • Package managers — manage declared dependencies.
  • Lockfiles — pin exact versions so installs are deterministic.
Concept check You write a script that uses f-strings (fine since Python 3.6) and the int | str union shorthand in type hints (only valid from Python 3.10 — distinct from typing.Union[int, str] which works from 3.5). Your colleague has Python 3.8 and gets a TypeError. Which layer of the environment is mismatched, and which tool from the list above would fix it?
