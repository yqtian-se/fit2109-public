8.1 Debugging Is Disciplined Hypothesis Testing

Debugging is not guessing. It is applying the scientific method to software: form a hypothesis about the cause of a bug, design an experiment to test it, observe the result, and revise your hypothesis accordingly. Developers who debug systematically find bugs faster than those who change code at random hoping something sticks.

The scientific method applied to bugs

  1. Observe. What exactly goes wrong? Capture the precise error message, the exact inputs, and the environment. Vague observations produce vague hypotheses.
  2. Hypothesise. What could cause this specific symptom? List two or three candidates — don't jump to the first idea.
  3. Experiment. Make one change that would confirm or rule out your hypothesis, then re-run.
  4. Conclude. Did the symptom change in the way you predicted? If yes, you have a lead. If no, your hypothesis was wrong — update it and repeat.
Common trap Changing two things at once is not an experiment — it is chaos. If the bug disappears, you don't know which change fixed it. If it persists, you have learned nothing. Always isolate your variable.

The five-step debugging workflow

Every debugging session, regardless of tool or language, follows the same spine:

StepWhat you doWhy it matters
ReproduceWrite down the exact steps, inputs, and environment that trigger the bug reliably.A bug you cannot reproduce consistently is a bug you cannot fix reliably.
IsolateNarrow down where the bug lives — which function, which line, which condition.Working on the full system wastes time. A small target is fast to fix.
InspectUse logs, a debugger, or print statements to observe actual program state at the failure point.Assumptions about what the code does are often wrong. Measure, don't guess.
FixMake the minimal change that addresses the root cause, not just the symptom.Fixing symptoms leaves the root cause to resurface under different inputs.
VerifyRe-run the original reproduction steps and any related tests.Confirms the fix works and has not introduced regressions.

Common debugging traps

  • Assuming the bug is in someone else's code. It usually isn't. Start with your own code before blaming libraries or the OS.
  • Fixing the symptom, not the cause. If a variable is None when it shouldn't be, adding a None check only papers over the problem — find out why it became None.
  • Debugging by addition. Adding more code before understanding the bug makes the system harder to reason about. Reduce first.
  • Trusting memory over evidence. "I know this function works" is not evidence. Verify it with a breakpoint or a log.
Concept check You run your program and see wrong output — not a crash. Which step of the workflow do you need to be most careful about? (Hint: it's easy to skip the "Reproduce" step when there's no error message.)
