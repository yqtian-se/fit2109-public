9.8 The Optimise → Measure → Verify Loop

Finding the bottleneck with a profiler is only half the work. The other half is applying the fix correctly, confirming it helped, and knowing when to stop. This section covers the discipline of applying optimisations safely.

Three rules for every optimisation

  1. Measure first. Record a baseline number before touching any code. Without a baseline, you cannot know whether you improved anything. Write down: what you measured, how you measured it, and the result.
  2. One change at a time. If you change two things simultaneously and the benchmark improves, you don't know which change helped. If it worsens, you don't know which to revert. Treat each optimisation as an experiment with a single variable.
  3. Verify the improvement. Re-run the exact same benchmark on the modified code. A gain of less than 10% on a single run may be within timing noise — run three times and use the median.

Common Python bottlenecks and fixes

PatternProblemFix
String concatenation in a loop result += s creates a new string object on every iteration — O(n²) total allocations. Collect strings in a list, then call ''.join(parts) once at the end — O(n).
List membership test in a loop if x in big_list scans every element — O(n) per check, O(n²) total. Convert to a set or dict first — O(1) lookup, O(n) total.
Repeated computation inside a loop Calling len(items) or re.compile(pattern) on every iteration when the result never changes. Hoist the computation above the loop — compute once, use many times.
Loading a full file into memory lines = open(f).readlines() loads the entire file before processing begins. Use for line in open(f): to stream one line at a time.
Nested loops over large data O(n²) or worse algorithmic complexity — a 10× larger dataset makes it 100× slower. Restructure using sorting, hashing, or vectorised operations. Algorithmic fixes outperform micro-optimisations by orders of magnitude.

Trade-offs: performance vs readability vs correctness

Every optimisation has a cost beyond runtime. Before applying one, consider:

  • Readability. A generator chain can be harder to read than a for loop. A bitwise trick is faster than integer division but nearly impossible to maintain. Prefer the readable version unless the profiler demands otherwise.
  • Correctness risk. Many optimisations — caching, lazy evaluation, in-place mutation — introduce subtle correctness bugs if applied carelessly. Always run your test suite after each change.
  • Maintainability. An optimised, opaque function is harder to debug when requirements change. Comment why the unusual pattern exists (e.g., "using set for O(1) lookup on hot path").
Amdahl's law Even if you optimise one part of your program to run infinitely fast, the overall speedup is limited by the fraction of time spent in the rest of the program. If the bottleneck you fixed accounts for 50% of runtime, the maximum possible speedup is 2×. This is why profiling to find the dominant bottleneck matters so much — targeting the wrong 5% function gives you at most a 5% improvement.
When to stop Stop optimising when the program is fast enough for its use case — not when you can find nothing left to improve. Every further optimisation trades away readability and correctness safety for diminishing returns. Define your target before you start, and stop when you hit it.
Try this Take a function you have profiled and identified as slow. Apply one fix (e.g. replace a list with a set for membership tests). Benchmark before and after with time or timeit. Run your tests to confirm correctness is unchanged. Document the change with a brief comment explaining why the unusual pattern exists.
