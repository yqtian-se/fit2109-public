9.1 Correctness Before Speed

Donald Knuth's famous warning — "premature optimization is the root of all evil" — is often quoted but rarely understood in full. The complete passage is more nuanced: "We should forget about small efficiencies, say about 97% of the time. Yet we should not pass up our opportunities in that critical 3%."

The lesson is not "never optimise." It is: don't optimise before you know where the bottleneck is, and don't sacrifice correctness or readability for a speed improvement you haven't measured.

The three-stage rule

  1. Make it work. Write code that produces the correct output for all expected inputs.
  2. Make it correct. Add tests, handle edge cases, fix bugs. This is Week 8's territory.
  3. Make it fast. Only now, if it's actually too slow for its use case, should you measure and optimise.

Skipping stage 1 or 2 and jumping to stage 3 is the trap. Optimising incorrect code is doubly wasteful: you spend time on performance and then discover the output is wrong.

The most common performance mistake Guessing the bottleneck and optimising the wrong part. Developers consistently overestimate the cost of I/O-bound code and underestimate the cost of algorithmic complexity. Always profile first — the bottleneck is almost never where you expect.

When is "fast enough"?

Performance has a use-case target, not an absolute ideal. A script that runs nightly can take 10 minutes. A web request handler must respond in under 200ms. An interactive editor must respond in under 16ms (60 fps). Before optimising, define your target. Stop when you reach it — not when you can find nothing left to optimise.

The 3% that matters Knuth's "critical 3%" refers to the hot path — the code that runs millions of times or blocks the user from making progress. A 10× speedup in a function that accounts for 1% of runtime gives you a 9% overall improvement. A 2× speedup in a function that accounts for 80% of runtime gives you a 60% overall improvement. Profile first to find the 80%.
