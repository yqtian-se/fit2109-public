9.2 Measuring Time

Before you can improve performance, you need a reliable baseline. The simplest tool is the shell's built-in time command, which measures how long a program takes to run and breaks the result into three components.

The three time values

$ time python3 slow.py
real    0m2.134s
user    0m2.098s
sys     0m0.036s
ValueWhat it measuresWhen it matters
realWall-clock time — the actual elapsed time you experience waiting.Always. This is the number users care about.
userCPU time spent inside your program's code (in user space).When diagnosing CPU-bound work. If user ≈ real, the CPU is the bottleneck.
sysCPU time spent in OS kernel calls made on behalf of your program (e.g. reading files, allocating memory).When real >> user + sys, the program is probably waiting on I/O or sleeping.

Timing is noisy

A single run is unreliable. OS scheduling, CPU frequency scaling, background processes, and memory cache state all add variance. The first run is almost always slower than subsequent ones because:

  • The program's code and data must be loaded from disk into RAM.
  • CPU instruction and data caches are cold — the hardware hasn't seen these memory addresses yet.
  • The OS may need to page in dependencies.

This first-run penalty is called warm-up. To get a stable measurement: run 3–5 times, discard the first result, and use the median of the rest.

Don't compare a cold run to a warm run If you time your program before and after an optimisation but the "before" run is cold and the "after" run is warm, the comparison is meaningless. Always compare like with like — both warm, or both cold.

Reading the numbers: common patterns

PatternLikely cause
real ≈ user, sys smallCPU-bound. Your code is doing a lot of computation. Profile with cProfile.
real >> user + sysI/O-bound or sleeping. The program is mostly waiting — for disk, network, or a time.sleep(). CPU profiling won't help here.
sys is largeMany system calls — possibly excessive file I/O, memory allocation, or network traffic.
user > realParallelism — multiple CPU cores are being used simultaneously (e.g. via threads or multiprocessing).
real >> user + sys, GPU busyGPU-bound. The CPU launches work on the GPU and waits for results. Neither user nor sys captures GPU compute time — you need GPU-specific tools.

hyperfine: statistical benchmarking

For more rigorous comparisons, hyperfine runs a command many times, discards outliers, and reports mean, min, max, and standard deviation automatically:

$ hyperfine 'python3 slow.py' 'python3 fast.py'
Benchmark 1: python3 slow.py
  Time (mean ± σ):     2.134 s ±  0.042 s
Benchmark 2: python3 fast.py
  Time (mean ± σ):     0.218 s ±  0.009 s
  Ratio: 9.79 ± 0.43
Try this Pick any Python script that takes at least a second to run. Time it with time python3 script.py five times in a row. Record all five real values. What is the range? What would you report as the "true" runtime?

Benchmarking GPU-bound code

GPU compute time is invisible to time and timeit. The CPU launches operations on the GPU and continues immediately — by the time you stop the clock, the GPU may still be running. This means a naive timer will drastically under-report the actual runtime of GPU workloads.

GPU operations are asynchronous In PyTorch (and most GPU frameworks), calling torch.mm(a, b) returns control to the CPU before the GPU has finished the multiplication. If you measure time around this call without synchronising, you are timing only the cost of queuing the operation — not executing it. The measured time may be 100× smaller than the true GPU time.

Correct GPU timing in PyTorch

Call torch.cuda.synchronize() before stopping the clock — this blocks the CPU until all pending GPU operations are complete:

import torch
import time

a = torch.randn(4096, 4096, device="cuda")
b = torch.randn(4096, 4096, device="cuda")

# Wrong: GPU is still running when we stop the clock
start = time.perf_counter()
c = torch.mm(a, b)
elapsed = time.perf_counter() - start   # massively under-reported

# Correct: wait for GPU to finish before reading the clock
torch.cuda.synchronize()
start = time.perf_counter()
c = torch.mm(a, b)
torch.cuda.synchronize()                # block until GPU is done
elapsed = time.perf_counter() - start   # accurate GPU time

Using CUDA Events for higher precision

PyTorch's torch.cuda.Event records timestamps directly on the GPU timeline, eliminating CPU-GPU synchronisation overhead from the measurement itself:

start_event = torch.cuda.Event(enable_timing=True)
end_event   = torch.cuda.Event(enable_timing=True)

start_event.record()
c = torch.mm(a, b)
end_event.record()

torch.cuda.synchronize()
elapsed_ms = start_event.elapsed_time(end_event)   # milliseconds
print(f"GPU time: {elapsed_ms:.3f} ms")

Checking GPU utilisation

Use nvidia-smi to see whether the GPU is actually being used and how much memory it is consuming:

# Snapshot of current GPU state
$ nvidia-smi

# Refresh every second while your program runs
$ nvidia-smi -l 1

# Key columns to watch
GPU  Util%   Mem-Used / Mem-Total    Power
  0    94%   6821MiB / 8192MiB       180W

A GPU utilisation below 50% while your program "runs on GPU" usually means the bottleneck is actually on the CPU — either data loading, preprocessing, or host-device memory transfers. Profilers such as NVIDIA Nsight Systems (nsys profile python3 train.py) give a full timeline showing exactly where CPU and GPU are idle relative to each other.

Interactive monitoring: nvtop and htop

For a live, continuously updating view while your program runs, two terminal tools are indispensable:

nvtop
An interactive GPU process monitor — like htop but for GPUs. Shows per-GPU utilisation, memory usage, and per-process GPU activity in real time, with colour-coded bar graphs.

Install:
sudo apt install nvtop (Ubuntu)
brew install nvtop (macOS with AMD/Intel GPU)

Run: nvtop — then launch your program in another terminal and watch utilisation climb.
htop
An interactive CPU and memory monitor. Shows per-core utilisation, memory/swap usage, and a live process list. Useful alongside nvtop to confirm whether the CPU is the bottleneck (all cores near 100%) or is sitting idle waiting for the GPU.

Install:
sudo apt install htop (Ubuntu)
brew install htop (macOS)

Run: htop — press F6 to sort by CPU%, q to quit.
Reading both tools together Run nvtop and htop side by side in two terminal panes while your training script runs. If GPU utilisation is low but all CPU cores are saturated, your data pipeline is the bottleneck — consider more DataLoader workers or prefetching. If GPU utilisation is high and CPU is idle, you are using the hardware efficiently.
