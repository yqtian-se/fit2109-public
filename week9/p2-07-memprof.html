9.7 memory_profiler: Tracking Memory Growth

A program can be slow not because of CPU work, but because it allocates too much memory. Excessive allocation forces Python's garbage collector to run more often, and large intermediate structures can push the program's working set out of CPU cache or even into swap. memory_profiler measures memory usage line-by-line, revealing exactly where allocations happen.

Why memory matters for performance

  • Garbage collection pauses. Every large allocation eventually triggers GC. In a tight loop, this adds unpredictable latency.
  • Cache pressure. A 500 MB intermediate list does not fit in CPU cache. Streaming the same data with a generator keeps only one item in cache at a time.
  • OOM crashes. On memory-constrained systems (servers, CI, containers with limits), unnecessary allocations cause out-of-memory errors.

Installation and usage

$ pip install memory_profiler

# Add @profile to the function (same pattern as line_profiler)
# Run with -m memory_profiler -- no import needed
$ python3 -m memory_profiler leaky.py

Reading the output

Filename: leaky.py

Line   Mem usage    Increment   Contents
   5    48.0 MiB    48.0 MiB   def load_data(n):
   7   125.4 MiB   +77.4 MiB   big = list(range(n))
   8   163.2 MiB   +37.8 MiB   result = [x * 2 for x in big]
   9   163.2 MiB     +0.0 MiB   return result

Line 7 allocates 77.4 MiB for a list that is immediately iterated on line 8 and never used again. Replacing it with a generator expression eliminates this allocation entirely.

Increment is the key column Mem usage is the running total. Increment shows how much new memory each line allocated. A large positive Increment on a line you didn't expect is your fix target.

The list-to-generator fix

# Before: builds a full list in memory
result = [x * 2 for x in range(10_000_000)]
total = sum(result)

# After: streams one item at a time -- peak memory drops ~80%
total = sum(x * 2 for x in range(10_000_000))

The generator expression (x * 2 for x in ...) produces one value at a time and discards it immediately. sum only ever holds one integer in memory. The final result is identical; the peak memory is negligible.

Generators are not always faster on CPU Generators reduce memory allocation, but they add a small per-item overhead compared to list comprehensions (function call overhead on each __next__). For small data, a list comprehension is often faster on CPU. Use a generator when the data is large enough that memory or GC pressure is the bottleneck. Measure both and pick the winner for your specific case.

Other common memory patterns to look for

  • Loading a whole file into a list when you only need one line at a time — use for line in open(path) instead of open(path).readlines().
  • Keeping large intermediate results in variables that are no longer needed — reassign or del them to release memory earlier.
  • Repeated string concatenation — each result += s creates a new string object; use ''.join(parts) instead.
