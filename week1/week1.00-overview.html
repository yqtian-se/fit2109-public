Part 1 — History & Context

Optional depth — go as far as interests you

You do not need to memorise this history. But understanding why the shell looks and works the way it does makes many of its quirks feel deliberate rather than arbitrary.

1.1 Why Is It Called a Terminal?

In the 1960s and 70s, computers were large, expensive machines shared by many users. Users interacted with them through teletype machines — essentially electric typewriters connected over cables. These devices were placed at the terminal end of the wire — the furthest point from the computer itself — which is why they were called terminals.

Teletypes printed output on paper rolls. Later, glass TTYs replaced paper with screens, but the name stuck. Today, a "terminal" on your laptop is a software program that emulates that old hardware — which is why you'll also see it called a terminal emulator. The Linux kernel still uses the abstraction of a TTY (/dev/tty) internally, even though no physical teletype exists.

Wikipedia: Computer terminal Wikipedia: Teleprinter

1.2 Unix and the Culture of Small Tools

In 1969, Ken Thompson and Dennis Ritchie at AT&T Bell Labs created Unix. It was designed for multiple users, built around text, and structured around a simple idea: rather than one large program that does everything, build many small programs that each do one thing well, and connect them.

That philosophy — small composable tools connected by text streams — is still the foundation of how the shell works today. When you pipe grep into sort into wc, you are using a 50-year-old design idea.

Unix history by Dennis Ritchie Wikipedia: Unix philosophy

1.3 GNU, Linux, and Why You Hear Both Names

In 1983, Richard Stallman started the GNU project to build a free Unix-like operating system. GNU produced most of the command-line tools you use today: ls, grep, gcc, and many others.

In 1991, a Finnish student named Linus Torvalds wrote a Unix-like kernel and released it as Linux. Combined with the GNU tools, this became a complete usable operating system. That combination is why you sometimes hear "GNU/Linux" — the GNU tools plus the Linux kernel. When you open a terminal on Ubuntu or Debian, you're using both.

GNU: Linux and the GNU project About the Linux kernel

1.4 What Is Bash and Where Did It Come From?

The original Unix shell was the Bourne shell (sh), written by Stephen Bourne in 1979. It defined the basic syntax you still use: pipelines, redirection, variables, and scripting.

In 1989, Brian Fox wrote Bash (Bourne Again SHell) as a free replacement for the Bourne shell for the GNU project. Bash added interactive features like command history, tab completion, and job control. It became the default shell on most Linux distributions and on macOS (until 2019, when macOS switched to zsh by default).

Today there are many shells: bash, zsh, fish, dash. They share the same core ideas. In FIT2109, scripts use Bash when the exact shell matters.

Part 2 — Key Concepts

2.1 What Is a Shell?

A shell is not Linux itself. It is a program that runs on Linux and acts as a command interface. When you type a command and press Enter, the shell reads what you typed, interprets it, and asks the operating system to carry it out.

Think of it this way: the Linux kernel is the engine — it manages hardware, processes, and files. The shell is the cockpit — a programmable interface you sit in to operate the engine. You can swap shells (bash, zsh, fish) just like you could swap a steering wheel, and you can even use Linux without a shell (through a GUI), but for automation and precision the shell is indispensable.

2.4 The Filesystem: One Tree from /

On Linux, all files live in a single hierarchical tree. The top is called the root directory, written as /. Everything else — your home folder, system programs, even attached USB drives — is a branch somewhere beneath it.

This is different from Windows, where each drive gets its own tree (C:\, D:\). On Linux, a USB drive doesn't appear as a new tree — it gets mounted as a folder somewhere inside the existing tree, such as /media/usb.

Key directories you will encounter:

  • /home/ — home directories for each user (your files live here)
  • /usr/bin/ — most installed programs (ls, grep, etc.)
  • /etc/ — system-wide configuration files
  • /tmp/ — temporary files, cleared on reboot

2.5 Paths: How to Point at a File

A path is an address for a file or folder in the filesystem tree. There are two kinds:

  • An absolute path starts from / and gives the complete route: /home/student/week1/notes.txt. It always means exactly the same file, regardless of where you are.
  • A relative path starts from your current location: week1/notes.txt or ../data. It means "relative to where I am now."

Three special path shortcuts you will use constantly:

  • ~ — your home directory (e.g., /home/student). cd ~ always takes you home.
  • . — the current directory. ./script.sh means "run script.sh from here."
  • .. — the parent directory. cd .. goes one level up.
Try this in Ed Run these commands one by one and observe the output of pwd each time: 
$ pwd
$ cd /tmp
$ pwd
$ cd ~
$ pwd
$ cd ..
$ pwd
Can you explain each change in location?

2.6 Working Directory and File Manipulation

The working directory is where the shell is currently located. Every command that involves a file uses the working directory as the starting point unless you give an absolute path.

The core file manipulation commands:

# See where you are and what's here
$ pwd                          # print working directory
$ ls -la                       # list all files with details

# Create
$ mkdir week1                  # make a directory
$ touch notes.txt              # create an empty file

# Copy, move, remove
$ cp notes.txt backup.txt      # copy a file
$ mv notes.txt summary.txt    # rename/move a file
$ rm backup.txt               # delete a file (no undo!)
Caution rm does not move files to a Trash folder — it deletes them immediately. There is no undo. Always double-check the path before running rm.

Reading ls -la output is one of the most useful shell skills. Each line looks like this:

drwxr-xr-x  3 student staff  96 May 20 10:15 week1
-rw-r--r--  1 student staff 142 May 20 10:12 notes.txt

The columns mean: type+permissions, link count, owner, group, size, date, name. The first character is d for directory, - for file, l for symbolic link.

Try this in Ed 
$ mkdir -p ~/fit2109/week1
$ cd ~/fit2109/week1
$ touch notes.txt
$ mkdir data
$ cp notes.txt data/notes-copy.txt
$ mv notes.txt summary.txt
$ ls -la
What changed between each step? Which commands created something? Which renamed?

2.7 Permissions

Every file and directory has a set of permissions that controls who can read, write, or execute it. There are three classes of user (owner, group, others) and three permission bits for each (read, write, execute).

The chmod command changes permissions. Two styles:

# Octal (numeric): set all permissions at once
$ chmod 755 script.sh    # rwxr-xr-x: owner full, others read+exec
$ chmod 600 secret.txt   # rw-------: owner only

# Symbolic: change specific bits
$ chmod u+x script.sh    # add execute for owner
$ chmod o-rw secret.txt  # remove read+write from others
Try this in Ed 
$ touch foo.txt
$ ls -l foo.txt           # note the default permissions
$ chmod 600 foo.txt
$ ls -l foo.txt           # what changed?
$ chmod u+x foo.txt
$ ls -l foo.txt           # and now?

2.8 Scripts and the Execute Bit

A shell script is a plain text file containing shell commands. To make it runnable, you need two things:

  1. A shebang on the first line: #!/bin/bash — this tells the OS which interpreter to use.
  2. The execute bit set: chmod u+x script.sh.
# Create a simple script
$ echo '#!/bin/bash' > hello.sh
$ echo 'echo "Hello FIT2109!"' >> hello.sh
$ chmod u+x hello.sh
$ ./hello.sh
Hello FIT2109!

Notice ./hello.sh — the ./ is required. Without it the shell won't find your script. We'll explain exactly why in the next section.

2.9 $PATH and How the Shell Finds Programs

When you type ls, how does the shell know where ls lives? It searches a list of directories stored in an environment variable called $PATH. Each directory is separated by a colon.

$ echo "$PATH"              # see your PATH
$ which ls               # find where ls lives
$ type cd                # cd is a shell builtin, not in PATH
Why does cd not appear in which? cd is a shell builtin — it is part of the shell itself, not a separate program. It must be a builtin because it needs to change the shell's own current directory. An external program can't do that: it runs in its own process and exits, leaving the shell's directory unchanged.

2.10 Pipes and Redirection

Every program has three standard streams: stdin (input), stdout (normal output), stderr (error output). By default, stdin reads from your keyboard and stdout/stderr print to your terminal. Redirection and pipes change where these streams go.

# Redirection
$ echo "first line" > notes.txt    # write to file (overwrites)
$ echo "second line" >> notes.txt  # append to file
$ sort < notes.txt                 # sort reads from file via stdin

# Pipeline: count error types in a log
$ grep "ERROR" server.log | sort | uniq -c | sort -nr
Try this in Ed 
$ echo -e "banana\napple\ncherry\napple" > fruit.txt
$ cat fruit.txt
$ sort fruit.txt | uniq -c
What does the final output show? Which fruit appears more than once?

Part 3 — Tools Worth Bookmarking

Explore freely

These sites will make your shell learning faster and more enjoyable. Bookmark them now — you'll use them throughout the semester.

explainshell.com
Paste any shell command and see each part explained, matched against the actual man page text. Great for commands you find on Stack Overflow and want to understand before running.
tldr.sh
Community-written, example-first alternatives to man pages. Where man ls gives you everything, tldr ls gives you the five most common uses. Also installable as a CLI tool.
linuxjourney.com
Free, gentle interactive Linux lessons with short exercises. Good if you want to go deeper than this pre-reading at your own pace.
OverTheWire: Bandit
Gamified shell challenges — you SSH into a server and solve puzzles using shell commands. Starts very easy and gets progressively harder. Genuinely addictive.
shellcheck.net
Paste a shell script and get specific warnings about bugs and bad practices. More useful from Week 2 onwards, but good to know it exists.
commandlinefu.com
Community collection of shell one-liners. Fun to browse — you'll discover commands you didn't know existed. Combine with explainshell to understand what you find.
