2.4 Exit Status and Command Chaining

Every program that runs on Unix returns a number when it exits. This number — the exit status — is how commands communicate success or failure to the shell. Understanding exit status unlocks the ability to write commands that branch automatically based on whether something worked.

The convention: 0 is success

  • Exit status 0 means the command succeeded.
  • Any non-zero value (typically 1–255) means the command failed or encountered a problem. Different tools use different non-zero codes to distinguish kinds of failure.
# Check the exit status of the last command with $?
$ mkdir demo_dir
$ echo $?
0                  # success

$ mkdir demo_dir   # already exists — fails
mkdir: demo_dir: File exists
$ echo $?
1                  # failure
Read $? immediately $? is overwritten by each command, including echo itself. If you need to store the status of a command, capture it right away: status=$? before running anything else.

Conventional exit codes to know

While any non-zero value means failure, some values have conventional meanings that make debugging faster:

$ notacommand

$ echo $?

# 126: not executable
$ chmod -x script.sh
$ ./script.sh

$ echo $?

Command chaining with && and ||

The shell provides two operators that branch on exit status, making it possible to write conditional logic in a single line:

OperatorMeaningCommon use
cmd1 && cmd2 Run cmd2 only if cmd1 succeeded (exit 0). Chain dependent steps: compile then run.
cmd1 || cmd2 Run cmd2 only if cmd1 failed (non-zero). Provide a fallback or bail out on failure.
cmd1 ; cmd2 Run cmd2 always, regardless of cmd1's result. Sequence commands with no dependency. 
# && — second command only runs if first succeeds
$ mkdir build && echo "directory created"
directory created

$ mkdir build && echo "directory created"   # already exists
mkdir: build: File exists
# echo does NOT run

# || — second command only runs if first fails
$ cd "/nonexistent" || echo "cd failed, staying put"
cd failed, staying put

The most important pattern: bail out on failure

In scripts, the most common use of || is to stop immediately if a critical step fails. This prevents later commands from running in the wrong state — for example, deleting files from the wrong directory because cd silently failed.

# If cd fails, exit the script immediately instead of proceeding
cd "$target_dir" || exit 1

# grep exit status: 0 if match found, 1 if no match, 2 on error
# (-q = quiet: no output, exit status only — grep flags are covered in section 2.6)
$ grep -q "ERROR" app.log && echo "Errors found in log"
$ grep -q "CRITICAL" app.log || echo "No CRITICAL lines"
The silent cd failure trap Consider this script fragment: 
cd "$backup_dir"
rm -rf *
If cd fails without a guard, the shell keeps running and rm -rf * deletes everything in your current directory instead of the backup directory. Always guard cd with || exit 1: 
cd "$backup_dir" || exit 1
rm -rf *

Exit status in practice

# Check whether a file exists without printing anything
$ test -f notes.txt && echo "file exists"

# Create a directory only if it does not already exist
$ mkdir -p logs   # -p: no error if it already exists

# Chain: compile, then run, then clean up — all steps dependent
$ gcc -o prog main.c && ./prog && rm prog
Try this 
$ ls /nonexistent && echo "A" || echo "B"
Before running: which message will print, A or B, and why? Then try: 
$ ls /tmp && echo "A" || echo "B"
What changed?
The &&/|| chain is not if/else cmd1 && cmd2 || cmd3 looks like an if/else but is not safe as one. If cmd2 exits non-zero, cmd3 will also run — because || sees the combined non-zero status of cmd1 && cmd2. For reliable branching in scripts, use the if statement introduced in section 2.9.
