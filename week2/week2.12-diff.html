2.12 Comparing Files with diff

diff compares two text files line by line and reports exactly what would need to change to make the first file identical to the second. It is the engine behind git diff, patch files, and — most practically for you — automated test scripts that check whether a program's output matches expected output.

Basic usage and output

# Create two slightly different files
$ printf 'apple\nbanana\ncherry\n' > file1.txt
$ printf 'apple\nblueberry\ncherry\n' > file2.txt

$ diff file1.txt file2.txt
2c2
< banana
---
> blueberry

Reading the default output:

  • 2c2 — line 2 in the left file changed to become line 2 in the right file. Other codes: added, deleted.
  • Lines prefixed < — from the left (first) file.
  • Lines prefixed > — from the right (second) file.
  • --- — separates the two sides.
Exit status — the key to using diff in scripts
  • 0 — files are identical.
  • 1 — files differ.
  • 2 — an error occurred (e.g. file not found).
This makes diff directly usable in &&/|| chains and if statements.

Unified format: diff -u

The default output is compact but hard to read in context. Unified format (-u) shows surrounding context lines and uses +/- instead of </> — the same format used by git diff.

$ diff -u file1.txt file2.txt
--- file1.txt	2026-06-02 10:00:00
+++ file2.txt	2026-06-02 10:01:00
@@ -1,3 +1,3 @@
 apple
-banana
+blueberry
 cherry

Reading unified format:

  • --- / +++ — headers identifying the two files.
  • @@ -1,3 +1,3 @@ — hunk header: shows which line ranges in each file this chunk covers.
  • Lines starting with - — present in the left file, absent from the right.
  • Lines starting with + — absent from the left file, present in the right.
  • Lines with no prefix — context lines (unchanged), shown for orientation.
Why unified format? diff -u is the standard for patch files and code review. When you run git diff, you are reading unified format. Learning to read it now means git output will be immediately familiar.

Using diff as a test tool

The most practical use of diff for students is comparing a program's actual output against expected output. Because diff exits 0 when files are identical and 1 when they differ, it plugs directly into the &&/|| pattern from Section 2.4.

# Basic pattern: run your script, save output, compare to expected
$ ./my_script.sh input.txt > actual.txt
$ diff expected.txt actual.txt
# no output = files match = your script is correct

# One-liner pass/fail check
$ diff -q expected.txt actual.txt && echo "PASS" || echo "FAIL"

# Show exactly what differs when it fails
$ diff -u expected.txt actual.txt || echo "--- output did not match ---"

Process substitution — no temp file needed

What is process substitution? <(cmd) is a Bash-only feature (not available in plain sh). It runs cmd in a subshell and makes its output available as a temporary file-like path — Bash uses a named pipe (/dev/fd/N) behind the scenes. Any command that accepts a file path can use <(cmd) in its place. This lets you compare or process command output without ever writing a temp file to disk.

Applied to diff, this means you can compare a program's output against expected output in a single command:

# Compare program output directly against expected — no temp file
$ diff expected.txt <(./my_script.sh input.txt)

# Compare outputs of two different commands
$ diff <(./old_version.sh data.txt) <(./new_version.sh data.txt)

# In a test script
$ diff -q expected.txt <(./my_script.sh input.txt) && echo "PASS" || echo "FAIL"

A reusable test script skeleton

Here is a shell script pattern for testing multiple inputs at once. It uses shell functions, local variables, and arithmetic — constructs covered beyond Week 2. Read it as a reference template you can adapt, not as something to memorise now.

#!/usr/bin/env bash
set -u
set -o pipefail

pass=0
fail=0

run_test() {
    local desc="$1" input="$2" expected="$3"
    if diff -q "$expected" <(./my_script.sh "$input") >/dev/null 2>&1; then
        echo "PASS: $desc"
        ((pass++))
    else
        echo "FAIL: $desc"
        diff -u "$expected" <(./my_script.sh "$input")
        ((fail++))
    fi
}

run_test "empty input"   tests/empty.txt   tests/empty_expected.txt
run_test "single line"   tests/one.txt     tests/one_expected.txt
run_test "multiple lines" tests/multi.txt  tests/multi_expected.txt

echo ""
echo "Results: $pass passed, $fail failed"
[ "$fail" -eq 0 ]   # exit 0 if all passed, 1 if any failed

Other useful diff options

OptionWhat it does
-uUnified format — context + +/- prefixes. Use this by default.
-qQuiet — prints only whether files differ, not what differs. Good for scripts.
-iIgnore case differences.
-wIgnore all whitespace differences (spaces, tabs).
-bIgnore changes in the amount of whitespace (leading/trailing).
-ySide-by-side display — shows both files next to each other.
-rRecursively compare two directories.
 
# Ignore whitespace — useful when trailing spaces differ
$ diff -b expected.txt actual.txt

# Side-by-side view
$ diff -y file1.txt file2.txt

# Compare two whole directories recursively
$ diff -r expected_dir/ actual_dir/

# Quiet directory comparison: just list which files differ
$ diff -rq expected_dir/ actual_dir/
Watch out for trailing newlines A common source of unexpected failures: your script prints hello but the expected file contains hello\n (with a newline at the end). diff will report a difference. Make sure your script's output and expected files are consistent about trailing newlines. Use diff -b to temporarily ignore whitespace while debugging.
Try this Write a script that takes a number and prints its square. Then test it with diff: 
# 1. Create expected output
$ echo "25" > expected.txt

# 2. Write square.sh, then test it
$ diff expected.txt <(./square.sh 5) && echo "PASS" || echo "FAIL"

# 3. Deliberately break it and re-run — read the diff output
Notice that when it fails, you can immediately see exactly what was wrong — not just "test failed."
