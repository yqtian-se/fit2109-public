2.10 Writing Reliable Scripts

A script that runs without crashing is not the same as a script that behaves correctly. Shell scripts fail in silent, dangerous ways: they continue past errors, expand empty variables into blank arguments, and treat a failed pipeline stage as a success. Three habits prevent the most common failures.

The safe script header

Start every non-trivial script with this header:

#!/usr/bin/env bash
set -u
set -o pipefail

Habit 1: set -u — fail on unset variables

Without set -u, a typo in a variable name silently expands to an empty string, which can cause commands to run with wrong arguments:

# Without set -u: typo expands to empty string — rm sees just /
target_dir="/tmp/myapp"
rm -rf "$trget_dir/"   # typo: $trget_dir is empty → rm -rf /

# With set -u: Bash catches the typo immediately
set -u
rm -rf "$trget_dir/"   # error: trget_dir: unbound variable
The missing quote is dangerous too Even with set -u, an unquoted variable can cause harm if it contains spaces. Both set -u and quoting are needed — they guard against different failure modes.

Habit 2: set -o pipefail — catch pipeline failures

By default, a pipeline's exit status is the exit status of its last command only. This means a failing intermediate step is silently ignored:

# Without pipefail: grep fails (file missing), wc -l sees empty input
# exit status is 0 (wc -l succeeded) — no sign of the error
grep 'ERROR' missing.log | wc -l
echo $?   # prints 0 — misleading!

# With pipefail: the pipeline exit status is the last non-zero exit status
set -o pipefail
grep 'ERROR' missing.log | wc -l
echo $?   # prints 2 (grep's error code for file-not-found)

Habit 3: quote every variable

This is a repetition from Section 2.2, but it belongs in the safety checklist: any variable that might contain spaces, newlines, or glob characters must be quoted everywhere it appears in a script:

#!/usr/bin/env bash
set -u
set -o pipefail
file="$1"

# Every reference to $file is quoted
if [ -f "$file" ]; then
    wc -l < "$file"
else
    echo "File not found: $file" >&2
    exit 1
fi

Spotting problems in an unsafe script

Here is a script with six distinct problems. Can you find them all?

#!/usr/bin/env bash
file=$1
if [ -f $file ]; then
    grep ERROR $file | sort | uniq -c
else
    echo File not found: $file
fi

The problems:

  1. $1 not quoted on assignment line — safe here (no word-splitting on assignment), but inconsistent style that invites copy-paste errors elsewhere.
  2. $file unquoted in [ -f $file ] — if $file is empty or has spaces, the test expression breaks.
  3. $file unquoted in grep ERROR $file — word-splits a filename with spaces into multiple arguments.
  4. No set -u — if the script is called without an argument, $file is empty and the script proceeds silently with wrong behaviour.
  5. No exit 1 in the else branch — a caller using && would think the script succeeded.
  6. Error message to stdout — echo File not found: $file should be echo "File not found: $file" >&2.
Try this Copy the unsafe script above. Then:
  1. Run it with no arguments — what happens?
  2. Run it with a filename that contains a space — what happens?
  3. Add set -u and set -o pipefail, quote all variables, and fix the exit status. Run the same tests again.
Use shellcheck.net to check your fixed version — it will report any remaining issues.
