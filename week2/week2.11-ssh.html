2.11 SSH and Remote Access

SSH (Secure Shell) encrypts a connection between two machines, letting you run commands on a remote server as if you were sitting at its terminal. It is the standard tool for accessing cloud servers, compute clusters, and university lab machines. Key-based authentication replaces password prompts with a cryptographic proof of identity.

How key-based authentication works

SSH uses a key pair: two mathematically linked files generated together.

Private keyPublic key
Where it lives ~/.ssh/id_ed25519 — your machine only. ~/.ssh/id_ed25519.pub — copied to each server.
Who sees it Nobody. Never share it. Treat it like a password. The server stores it in ~/.ssh/authorized_keys.
What it does Signs a challenge from the server to prove your identity. The server uses it to verify the signature — no password needed.

When you connect, the server sends a challenge. Your SSH client signs it with your private key. The server verifies the signature using the stored public key. If they match, you are in — no password sent over the network.

Generating a key pair

# Generate a new Ed25519 key pair (modern, recommended over RSA)
$ ssh-keygen -t ed25519 -C "your@email.com"
Generating public/private ed25519 key pair.
Enter file in which to save the key (~/.ssh/id_ed25519):   # press Enter
Enter passphrase (empty for no passphrase):                # set one for security

# Check what was created
$ ls -la ~/.ssh/
-rw-------  id_ed25519      # private key — permissions must be 600
-rw-r--r--  id_ed25519.pub  # public key — safe to share
Permissions matter SSH will refuse to use a private key if it is readable by anyone other than you. If you see a permissions warning, fix it: chmod 600 ~/.ssh/id_ed25519.

Copying your public key to a server

# ssh-copy-id appends your public key to the server's authorized_keys
$ ssh-copy-id -i ~/.ssh/id_ed25519.pub user@hostname

# If ssh-copy-id is not available (e.g., older macOS), do it manually
$ cat ~/.ssh/id_ed25519.pub | ssh user@hostname 'mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys'

Connecting and running commands

# Open an interactive shell on the remote machine
$ ssh user@hostname

# Run a single command on the remote machine and return
$ ssh user@hostname 'pwd && uname -a'

# Run a remote command and capture its output locally
$ result=$(ssh user@hostname 'ls /var/log/*.log | wc -l')
$ echo "Remote has $result log files"
Quote the remote command carefully The remote command is passed as a single argument, so single-quote it to prevent the local shell from expanding variables or globs. Single quotes make everything literal locally — the text is sent as-is to the remote machine, where the remote shell then expands any variable references it finds.

Transferring files with scp

scp (secure copy) uses the SSH connection to transfer files. Its syntax mirrors cp: source then destination, with remote paths written as user@host:/path.

# Copy a local file to the remote machine
$ scp deploy.sh user@hostname:/tmp/

# Copy a file from the remote machine to the current local directory
$ scp user@hostname:/var/log/app.log .

# Copy a whole directory recursively (-r)
$ scp -r src/ user@hostname:~/project/

# Collect results after a long-running remote computation
$ ssh user@hostname 'python3 experiment.py > run.log 2>&1'
$ scp user@hostname:run.log .

Interactive file transfer with sftp

sftp provides a more interactive file-transfer experience over the same SSH transport. Instead of specifying everything on one command line, you get a prompt where you can browse and transfer files step by step — useful when you are not sure of the exact remote path.

# Start an sftp session
$ sftp user@hostname
sftp> pwd               # remote working directory
sftp> ls                # list remote files
sftp> put analysis.sh   # upload a local file
sftp> get results.txt   # download a remote file
sftp> mkdir output      # create a remote directory
sftp> quit
sftp commandWhat it does
ls / llsList remote / local files.
cd / lcdChange remote / local directory.
put fileUpload file from local to remote.
get fileDownload file from remote to local.
quitClose the session.

Why key-based auth matters in scripts

Password authentication cannot be automated — a script cannot type a password interactively. Key-based authentication works silently: the SSH client reads the private key from disk and signs the challenge without any user interaction. This is why CI/CD systems, deployment scripts, and cron jobs all use key pairs.

Putting it together Plan the sequence of commands to:
  1. Copy a script called report.sh to a remote server at /home/user/.
  2. Make it executable on the remote machine.
  3. Run it there and collect its output into a local file called report.txt.
Write the three commands before checking your answer in class. Think about which shell (local or remote) evaluates each part.
