12.4 Prompt Engineering for Agent Tasks

The quality of what an agent produces is almost entirely determined by the quality of what you ask for. "Vague input → vague output" is not a rule of thumb — it is a near-guarantee. Learning to write a good prompt is the most immediately transferable skill in this week's material.

The three ingredients of an effective prompt

  1. Task. What you want done. Be specific: name the function, file, or behaviour you want changed. "Fix the bug" is not a task — "In parse.py, parse_date() crashes on empty strings" is a task.
  2. Context. The language, framework, existing structure, and any relevant constraints the agent needs to understand your project. What it cannot see, it invents.
  3. Constraints. What the agent must not do. This is the most commonly omitted ingredient and the most common cause of runaway rewrites. "Do not change the function signature." "Do not add new dependencies." "Do not modify any file in tests/."

Vague vs specific

Vague prompt

"Fix my code."

The agent has no idea which file, which function, what the expected behaviour is, or what "fix" means. It will make something up — typically by rewriting whatever it finds first in a way that seems plausible to it.

Specific prompt

"find_matches() in data.py is O(n²) because it searches a list on every iteration. Rewrite it to use a set for the lookup. Do not change the function signature or modify any test files."

The agent knows exactly what to touch, why, how, and what to leave alone. The resulting diff is reviewable in under a minute.

The most common failure: missing constraints

When you give an agent a task with no constraints, it optimises for completeness. "Add error handling to my script" without constraints will often produce a full rewrite — because to the agent, the most thorough way to add error handling is to restructure the code. This is not malicious or stupid; it is the natural result of an agent trying to do a good job with incomplete instructions.

The fix is to treat prompts like code specifications. If a function spec is missing edge-case handling, the implementation will be wrong. If a prompt is missing scope constraints, the agent output will exceed scope.

No constraints means no scope An agent given "refactor this module" with no constraints may change the public API, rename functions, swap the data structures, add a dependency, and reorganise the file layout — all in one pass. Each change is individually reasonable; together they produce a diff you cannot review in an hour. Always say what must not change.
Try this Take a task you would normally Google — looking up how to sort a dictionary by value, or how to read a CSV file — and instead write a properly constrained agent prompt for it. Include the task, the language and framework, and at least two constraints. Notice how the constraints force you to think more precisely about what you actually want.
