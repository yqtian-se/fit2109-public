12.3 What AI Agents Do Well — and Where They Fail

AI coding tools can propose code, inspect files, and sometimes run checks. Their output is useful, but a fluent explanation or a passing test is not enough to show that the code meets your requirement. This page separates useful capabilities from the evidence needed to trust a result.

Strong at

  • Boilerplate and scaffolding. Setting up a project structure, writing repetitive initialisation code, generating configuration files.
  • Explaining existing code. Describing what a function does, translating code into plain English, summarising a module.
  • Language translation. Converting Python to JavaScript, rewriting a shell script in Python.
  • Test generation from a spec. Given a function signature and description, generating a suite of unit tests.
  • Completing familiar patterns. Any task that closely resembles code that appears frequently in training data.

Cannot guarantee by itself

  • Guaranteeing correctness. A generated answer alone is not proof that a program is logically correct.
  • Novel algorithms or proofs. Novel work may need additional reasoning, external evidence, and human review.
  • Knowing your specific codebase. Without being given relevant context, the model invents plausible but wrong assumptions about your project.
  • Persistent memory. Memory depends on the product and its configuration.
  • Security awareness. Security claims require review and appropriate tests.

Fluent output is not evidence of correctness

A model can produce code that follows familiar patterns. A tool-connected agent can go further: it can inspect the repository, run a test, observe a failure, and revise its code. Those steps provide evidence, but only for the cases the agent actually checked.

For example, an agent may change a CSV importer and run tests for valid rows. All tests pass, but no test checks a malformed row, so the agent has not established that the importer handles errors as required. A person needs to compare the change with the requirement and add a test for the missing case.

Another failure is a plausible but nonexistent function name, library import, or command flag. The explanation may sound confident even when the detail is wrong.

Hallucination looks like confidence AI-generated code can reference functions that do not exist in the library, use API flags that were deprecated years ago, or call methods with the wrong number of arguments — all while formatting the code perfectly and writing a plausible docstring. It may look valid until execution reaches that line. Check unfamiliar library calls against the version you are using.

What this means in practice

Model and tool capabilities change, but generated code still needs verification against the task and environment. Verification is not optional extra work — it is the cost of using the tool.

Strong coding knowledge is the control system AI is most useful when you can already read, trace, test, and debug the code yourself. If you cannot tell whether the generated code is correct, the tool has not removed the hard part — it has hidden it.
