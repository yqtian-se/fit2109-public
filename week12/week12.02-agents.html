12.2 From Chatbots to Coding Agents

Start with a familiar chatbot. You paste a function into a chat and ask why it fails on an empty file. The chatbot suggests a cause and perhaps a patch; you decide what to copy into your editor and which tests to run. This is a useful way to learn or brainstorm, but the chat has only the context and tools available in that session.

Now imagine giving a coding agent the same question inside your repository. With permission, it can inspect the function, read the tests, run a failing case, propose an edit, and run the test again. The important distinction is the enabled tools and permissions: what can the system read, change, or send? A chat product may also offer an agent mode.

A chatbot

  • You ask a question; it responds with text.
  • One turn at a time — you drive every step.
  • In a basic chat workflow, it only sees the context you provide.
  • You usually copy-paste its output into your editor manually.
  • Memory and connected tools depend on the product settings.

An agent

  • You give it a goal and access to selected tools.
  • It reads your files, runs commands, and inspects the output.
  • It loops through a read → plan → act cycle — until the goal is met or it is stuck.
  • It may propose or write changes, depending on permissions.
  • It can call external tools (search, databases, APIs) via protocols like MCP.

The read → plan → act loop

The fundamental unit of agent behaviour is a loop. Each iteration has three phases:

  1. Read context. The agent reads relevant files, past conversation, error messages, and tool results to understand the current state.
  2. Plan next action. Based on the context, the agent decides which tool to call next — read a file, run a command, write an edit, search for documentation.
  3. Act and observe. The agent executes the action and gets back a result. That result becomes new context for the next iteration.

The loop repeats until the agent judges that the goal has been met, or it runs out of steps, or it gets stuck and asks you for guidance. This is why agents can complete multi-step tasks that would require many back-and-forth exchanges with a chatbot.

Where the CLI and harness fit

A CLI is an interface for starting and guiding a coding agent from the terminal. It does not by itself make the model more reliable. The harness is the surrounding software that supplies context and tools, controls permissions and approvals, and records what happened. Those controls shape each pass through the agent's loop. Section 12.6 examines them in detail.

What actual CLI usage looks like

A CLI coding agent is normally used from inside a Git repository. The terminal command starts the conversation, but Git and tests are still your verification tools.

cd my-project
git status

codex --sandbox workspace-write \
  --ask-for-approval on-request \
  "Inspect this repo and suggest one safe first improvement."

git diff
make test

The same workflow shape applies to other CLI agents such as claude or gemini: start in the right directory, give a narrow prompt, watch what the agent reads and runs, inspect the diff, then test before accepting the change.

An agent does not have to run in your terminal. On GitHub, an eligible repository can assign an issue to Copilot cloud agent. It works on the issue and opens a pull request for human review. The interface and execution environment differ from a local CLI, but the need to define the task and review the result remains. Section 12.9 compares these interfaces.

In this example, the working directory limits the project context, the sandbox and approval settings constrain actions, and the diff and tests help you check the result. For commands and product options, use the tool reference page.
