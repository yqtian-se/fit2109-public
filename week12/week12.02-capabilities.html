12.2 What AI Agents Do Well — and Where They Fail

The most useful mental model for working with AI coding tools is not "this is smart" or "this is unreliable." It is more precise than that: AI predicts likely text, not correct logic. That distinction explains both its genuine strengths and its consistent failure modes.

Strong at

  • Boilerplate and scaffolding. Setting up a project structure, writing repetitive initialisation code, generating configuration files.
  • Explaining existing code. Describing what a function does, translating code into plain English, summarising a module.
  • Language translation. Converting Python to JavaScript, rewriting a shell script in Python.
  • Test generation from a spec. Given a function signature and description, generating a suite of unit tests.
  • Completing familiar patterns. Any task that closely resembles code that appears frequently in training data.

Reliably fails at

  • Guaranteeing correctness. The model has no way to verify that its output is logically correct — it produces what looks right.
  • Novel algorithms or proofs. Tasks that require genuine reasoning from first principles, not pattern completion.
  • Knowing your specific codebase. Without being given relevant context, the model invents plausible but wrong assumptions about your project.
  • Persistent memory. By default, there is no memory between sessions — the model starts fresh every time.
  • Security awareness. It will produce code with known vulnerability patterns unless explicitly told not to.

The key insight: prediction vs. correctness

A language model is trained to predict what text is likely to follow a given input. When the input is a coding task, it predicts what code would most plausibly appear next — based on billions of examples of similar tasks in its training data.

This is genuinely useful because most code tasks are variations on patterns that have been solved before. But it means the model has no internal check for logical correctness. It cannot run its own output in its head. It cannot guarantee that an algorithm terminates, that a boundary condition is handled, or that a function does what its name implies.

The result is hallucination with confidence: the model produces a function name, a library import, or a flag that does not exist — in fluent, well-formatted code with no indication that anything is wrong.

Hallucination looks like confidence AI-generated code can reference functions that do not exist in the library, use API flags that were deprecated years ago, or call methods with the wrong number of arguments — all while formatting the code perfectly and writing a plausible docstring. The code runs; it just crashes at that line. Always check that library calls you did not already know about actually exist in the version you are using.

What this means in practice

The failure modes above are not bugs that will be fixed in the next model release. They are structural: they follow directly from how the models work. This means your workflow needs to account for them permanently, not temporarily. Verification is not optional extra work — it is the cost of using the tool.

Strong coding knowledge is the control system AI is most useful when you can already read, trace, test, and debug the code yourself. If you cannot tell whether the generated code is correct, the tool has not removed the hard part — it has hidden it.
