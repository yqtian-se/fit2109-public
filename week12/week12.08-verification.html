12.8 Verification — Reading What the Agent Wrote

The most dangerous moment in an agent workflow is not when the agent acts — it is when you accept the result without reading it. Tests passing is a necessary condition for correctness, not a sufficient one. The four-step verification workflow below is the minimum responsible practice for any AI-generated code you intend to keep.

The four-step verification workflow

StepWhat to doWhat to look for
1. Read the diff Before running anything, open the diff and read every changed line. In Git: git diff or git diff --staged. Did the agent change files you did not ask it to touch? Did it remove error handling? Did it change a public API silently? Does any line surprise you?
2. Run the tests Run the full test suite, not just the tests for the changed function. Use make test or equivalent. Failing tests are an obvious signal. But also check: did the agent add new tests that pass trivially, or delete tests that were inconvenient? Passing tests on weaker coverage is not confidence.
3. Explain it For every function or block the agent changed, write one sentence in plain English describing what it does. If you cannot, you do not understand it yet. The inability to explain a function is the clearest signal that you have not actually verified it. This is the step that catches hallucinated logic — code that looks right but does something subtly different.
4. Check edge cases Manually test or reason through: empty input, maximum-size input, unexpected types, missing files, network errors — whatever the function is supposed to handle. Agents reliably under-test edge cases. The generated tests usually cover the happy path. Edge cases are where hallucinated logic tends to surface.

Academic integrity

Monash University permits the use of AI tools in FIT2109 when that use is allowed by the assessment instructions and disclosed appropriately. Permission to use a tool does not remove responsibility for the work. You should expect to explain code you submit: what each function does, why the design is appropriate, and how you checked it.

The rule is: you may use AI tools if you disclose it and can explain every line you submit. Submitting code you cannot explain is academic misconduct, regardless of who or what wrote it. The tool writes code; the responsibility is yours.

The four-step workflow above is not just good engineering practice — it is also how you ensure you can satisfy that standard. Strong coding knowledge is what makes this possible: without it, you cannot tell whether the AI helped, guessed, or quietly broke the program.

Tests passing is not the same as code being correct An agent can produce code that passes all existing tests while still being wrong. The tests may not cover the relevant cases. The agent may have changed the behaviour in a way the tests were not designed to catch. Tests increase confidence — they do not replace reading and understanding the code.
Try this Use any AI tool to generate a short function (10–20 lines) for a task of your choice. Then apply the four steps: read what it produced, run or mentally trace it, explain each line out loud as if to a classmate, and find one input it would handle incorrectly. The aim is to notice what the tool got right, what it missed, and which parts of your own programming knowledge let you tell the difference.
