12.7 Reviewing an Agent's Change

Verification in a real project is a decision about a specific change. Start with the task you agreed to, look at what the agent actually changed, and choose checks that address the remaining uncertainty. You may return to the agent, write a test yourself, keep part of the change, or reject it. There is no fixed sequence that proves every change correct.

A change that looks finished

Your team asks an agent to add a test for empty input to a log summariser. It adds the test, rewrites the parser, and adds a package. The existing test suite passes. You now have three different changes to judge, even though the agent presents them as one result.

ChangeQuestion to askUseful evidence
New testDoes it check the requested empty-input behaviour, or merely pass?Read its assertion and run it against the relevant code. If it is meant to catch a bug, check whether it fails on the old behaviour.
Parser rewriteWas changing production behaviour necessary for the requested test?Inspect the diff and try inputs the parser already supports, including malformed lines. Keep the rewrite only if you can justify it.
New packageWhy is this dependency needed for a small test?Ask for a reason, check the project rules, and look for a simpler change. Reject the dependency if it adds no needed value.

Choose checks to match the risk

  • Inspect scope. Start with the diff or change summary. Look more closely at unexpected files, deleted checks, changed interfaces, and new dependencies.
  • Test the requirement. Run a targeted check for the behaviour you asked for. Run broader tests when integration risk or project rules call for them. A passing suite answers only the cases it contains.
  • Investigate uncertainty. Trace a confusing branch, try a relevant edge case, consult documentation for an unfamiliar API, or ask the agent to explain its choice. Treat its explanation as a claim to check.
  • Decide and record. Keep, revise, or reject each part of the change. State the evidence and any remaining limitation in a short note a teammate can follow.

These actions form a loop, not a mandatory checklist. A failed test may send the change back for revision. A small, low-risk edit may need fewer checks than a change to authentication, data handling, or external access. Apply the project's required checks before merging.

What a passing test does and does not tell you It shows that the checked cases passed in that environment. It does not show that the requested behaviour was tested, that an extra dependency was justified, or that an untested input still works.

Accountability in assessed work

Follow the current unit assessment instructions for permitted AI use and disclosure. Your team remains responsible for code it submits. Keep enough evidence to explain what was delegated, what was checked, and who accepted the result. If you cannot explain a material change, investigate it, revise it, or leave it out.

Try this decision For the log summariser above, write three short decisions: one for the test, one for the parser rewrite, and one for the package. For each, say keep, revise, or reject; name one piece of evidence you would check; and say who on the team will review it.
