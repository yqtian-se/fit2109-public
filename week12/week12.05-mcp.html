12.5 How Agent Instructions and Tools Fit Together

Imagine asking a coding agent to fix a CSV importer after reading a GitHub issue. The model is one part of that workflow. Different layers tell the agent what to do, give it relevant context, connect it to data, and limit its actions.

QuestionLayerIn this example
What is the task now?Task promptFix malformed-row handling in the importer; keep the public API unchanged.
What is always true of this project?Project instructionsAGENTS.md in Codex or CLAUDE.md in Claude Code records the test command and project conventions.
Is there a repeatable way to do this?SkillA SKILL.md could describe a bug-fix workflow: reproduce, add a failing test, make a small change, and report evidence.
How can the agent reach the issue?Tool connectionA configured GitHub MCP server can provide issue data and actions. Local file and shell tools need no MCP server.
Which actions are allowed?Harness and permissionsThe agent's runtime controls file access, tool use, and approvals. Connecting a tool does not authorize every possible action.
Is the fix acceptable?Human verificationA developer reads the diff, runs relevant tests, and checks the malformed-row requirement.

Skill and MCP solve different problems

A skill is reusable guidance for a task. Codex and Claude Code can load skills from folders containing SKILL.md; a skill may include instructions, reference files, or scripts. A skill can tell an agent how to review a bug report. It does not, by itself, give access to GitHub.

Model Context Protocol (MCP) is a way for a client to connect to external tools and data. A configured MCP server can let an agent read the GitHub issue or query another service. It does not tell the agent what a good bug fix looks like. The agent can use a skill and an MCP connection together: one supplies a workflow, the other supplies the connection. For work entirely inside a local repository, the agent's built-in tools may be enough.

Some products already include the connection they need. GitHub's own Copilot cloud agent can receive an issue directly on GitHub; you do not need to add an MCP server for that built-in flow. If you are using an agent elsewhere and need an external service, MCP is one possible connection.

Where Codex and Claude Code fit Both can use project instructions, skills, and MCP connections. Their interfaces and file locations differ: Codex commonly uses AGENTS.md and repo-scoped skills under .codex/skills/; Claude Code uses CLAUDE.md and project skills under .claude/skills/. You do not need to create every layer for every task. Add a skill when a workflow repeats; add an MCP connection when the task needs an external system.

You can ask Codex to use a named skill with $skill-name; in Claude Code, you can invoke one with /skill-name. Both can also select a relevant skill from its description. Other extensions exist, such as subagents for separate pieces of work, hooks for event-based automation, and plugins that package related capabilities. They fit around the same workflow; they do not replace a clear task, appropriate permissions, or verification. The next page examines the harness and security boundaries in detail.
